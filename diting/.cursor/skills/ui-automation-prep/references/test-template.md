## 第一部分：测试用例

### 用例编写规范

#### 优先级定义

| 优先级 | 定义     | 说明                       |
| ------ | -------- | -------------------------- |
| P0     | 核心功能 | 主流程、核心业务，必须通过 |
| P1     | 重要功能 | 重要分支、常用功能         |
| P2     | 一般功能 | 边界条件、异常处理         |
| P3     | 低优先级 | 极端场景、优化建议         |

#### 类型定义（适用端）

| 类型     | 说明                      |
| -------- | ------------------------- |
| Web端    | 浏览器 Web 页面           |
| H5端     | 移动端 H5，含 Taro 小程序转 H5 后的浏览器可执行形态 |
| App端    | 原生/混合 App             |
| PC端     | 桌面客户端                |
| 管理后台 | 后台管理系统 Web          |
| 通用     | 多端共用或接口/无 UI 区分 |

#### 小程序 / Taro 执行口径

- 原生小程序当前不作为 Playwright 直接执行目标，不使用小程序 IDE、原生调试器或非 Playwright 执行器补跑。
- 多数小程序若基于 Taro 跨端框架，生成用例时优先按目标仓启动时提供的 H5 形态测试，类型标注为 `H5端`。
- `主入口URL/菜单` 或 When 首步必须写清 H5 入口来源，例如 `目标仓 npm run dev:h5 后的 TARGET_URL`、移动端 H5 路由或菜单路径。
- 只有无可用 H5 入口，或断言依赖微信授权、原生支付、订阅消息、扫码、蓝牙等原生专属能力时，才标注为 `本轮是否执行=否`、`环境前提=不可 UI 自动化`。

#### 场景类型定义

| 场景类型   | 说明                         |
| ---------- | ---------------------------- |
| 正向场景   | 主流程、正常操作、预期成功   |
| 边界场景   | 边界条件、校验规则、必填项校验 |
| 异常场景   | 接口失败、网络异常、系统错误提示 |
| 端到端场景 | 跨模块主流程、完整业务流程   |

#### 用例格式说明

- 采用 **Given-When-Then** 格式（BDD风格）
- **Given**：前置条件和测试数据准备
- **When**：执行的操作步骤（含具体导航路径，可直接映射为浏览器自动化 action）
- **Then**：预期结果验证（仅页面可观测结果，可直接映射为浏览器自动化 assertion）
- **场景类型**：每个用例必须在属性表中标注场景类型（正向场景、边界场景、异常场景、端到端场景）
- **覆盖范围**：每个用例必须标注为 `本次功能`、`全局回归`、`候选扩展` 或 `不纳入本轮`
- **本轮是否执行**：每个用例必须明确当前环境是否纳入执行；不可执行的候选 case 不进入 UI 自动化执行队列

## 附录：测试用例生成指南

### 强制要求

1. **用例覆盖完整性**：
   - 必须覆盖本次功能的核心验收点
   - 必须包含与本次改动可能互相影响的核心全局回归
   - 候选扩展、历史问题、当前环境不可执行场景不得强行纳入本轮执行

2. **用例格式规范**：
   - 统一使用 Given-When-Then 格式
   - 每个用例必须有唯一ID
   - 每个用例必须标注优先级
   - 每个用例必须标注类型（适用端）
   - 每个用例必须标注场景类型（正向场景、边界场景、异常场景、端到端场景）

3. **测试数据要求**：
   - 测试数据必须具体、可执行
   - 不允许使用模糊描述如"某用户"
   - 必须包含边界值数据

4. **预期结果要求（Then）**：
   - Then 只写**用户在页面上可观测到的结果**（提示信息、列表变化、按钮状态等）
   - Then 断言的目标元素必须存在于 When 最后一步所在的页面上（When-Then 联动）
   - 每条 Then 需能映射为浏览器自动化断言：元素可见、文本包含、元素状态变化
   - 禁止写数据库断言（如 `数据库中 xxx 字段已更新`）
   - 禁止写硬编码时间（如 `2秒内`），改为 `出现xxx提示`
   - 禁止写硬编码数量（如 `已成功设置 3 台`），改为 `出现成功数量反馈`
   - 禁止写接口级断言（如 `接口返回数据包含 xxx`）
   - 禁止写主观/不可验证描述（如 `便于快速找到xxx`）
   - 数据前提（设备数量、初始状态等）放在 Given 中，不放在 Then 中
   - 异常场景必须验证用户可见的错误提示

5. **操作步骤要求（When）**：
   - UI 用例的 When 必须包含具体的导航路径（菜单点击顺序），不使用抽象描述
   - 每步点击后标注等待点（如 → 等待表格加载、→ 等待子菜单展开）
   - 导航步骤用 → 连接，先写导航再写业务操作

6. **自动化可行性标注**：
   - 对于非 UI 可验证的用例（后台任务、cron job、数据库直接操作），在属性表 `类型` 列标注为 `通用（不可UI自动化）`
   - 对于 Taro 小程序用例，优先改写为 `H5端` 并使用目标仓启动后的 H5 入口执行
   - 对于无法转 H5 或依赖原生小程序专属能力的用例，在属性表中标注 `本轮是否执行=否`、`环境前提=不可 UI 自动化`，并在 `不执行原因` 中写明原生能力缺口
   - 对于当前账号、样本、权限、mock 能力不足的用例，在属性表中标注 `本轮是否执行=否`，并填写不执行原因

7. **用例数量要求**：
   - 每个功能模块至少3个测试用例
   - 包含：正向场景、边界条件、异常场景

### 输出格式要求

- 使用 Markdown 格式
- 严格按照测试文档模板结构
- 用例描述清晰、步骤可执行
