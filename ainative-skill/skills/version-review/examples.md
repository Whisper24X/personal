# Version Review Examples

## Example 1: User Login Feature

### Version Idea

"添加用户登录功能，支持手机号和邮箱登录"

### Round 1: Business Rules Conflict Check

**Knowledge Base Context:**

- Business rule: "用户认证必须使用OAuth2.0协议"
- Business rule: "密码必须符合复杂度要求：至少8位，包含大小写字母、数字和特殊字符"

**Generated Question:**

```
您的版本想法提到"添加用户登录功能，支持手机号和邮箱登录"。

根据我们的业务规则库，我们有以下要求：
- 用户认证必须使用OAuth2.0协议，不支持直接密码登录
- 密码必须符合复杂度要求：至少8位，包含大小写字母、数字和特殊字符

您的想法是否与这些业务规则冲突？是否需要调整为使用OAuth2.0协议进行认证？
```

**User Answer:**
"是的，我需要调整为使用OAuth2.0。手机号和邮箱可以作为账号标识，但认证流程使用OAuth2.0"

### Round 2: 功能冲突检查

**Knowledge Base Context:**

- 历史需求文档: "用户中心模块已实现手机号注册和登录功能"
- Feature list: "支持微信、QQ第三方登录"

**Generated Question:**

```
基于之前的讨论，您已决定使用OAuth2.0协议。

根据历史需求文档，我们的用户中心模块已经实现了：
- 手机号注册和登录功能
- 微信、QQ第三方登录

您的新功能"手机号和邮箱登录"是否与现有的"手机号登录"功能重复？是否需要：
1. 扩展现有功能，增加邮箱登录方式？
2. 还是这是一个全新的独立功能？
```

**User Answer:**
"这是扩展现有功能，在现有手机号登录基础上增加邮箱登录方式"

### Round 3: Terminology Consistency Check

**Knowledge Base Context:**

- Terminology: "用户账号"定义为"用户的唯一标识，可以是手机号、邮箱或第三方账号ID"
- Terminology: "登录"定义为"通过账号和认证凭证访问系统"

**Generated Question:**

```
在您的版本想法中，使用了"用户登录功能"这个术语。

根据我们的术语词典：
- "用户账号"：用户的唯一标识，可以是手机号、邮箱或第三方账号ID
- "登录"：通过账号和认证凭证访问系统

您提到的"手机号和邮箱登录"中的"手机号"和"邮箱"是指"用户账号"的类型吗？是否需要统一术语为"支持手机号账号和邮箱账号登录"？
```

**User Answer:**
"是的，应该统一为'支持手机号账号和邮箱账号登录'"

### Round 4: 业务数据与系统兼容性检查

**Knowledge Base Context:**

- 系统限制: "用户信息的主标识不可修改"
- 开发规范: "账号字段支持手机号、邮箱和第三方账号ID"

**Generated Question:**

```
您的版本想法涉及添加邮箱账号登录功能。

根据系统限制和开发规范：
- 用户信息的主标识不可修改
- 账号字段已支持手机号、邮箱和第三方账号ID

您的功能是否需要改动业务数据或信息结构？如果需要，具体涉及哪些数据项？是否符合现有的系统限制？
```

**User Answer:**
"不需要改动业务数据，现有的账号字段已经支持邮箱格式，只需要在登录逻辑中增加邮箱格式的验证和查询"

### Round 5: Final Confirmation

**Generated Question:**

```
经过前面4轮的讨论，我们确认了以下关键点：

1. 认证方式：使用OAuth2.0协议（已调整）
2. 功能定位：扩展现有手机号登录功能，增加邮箱登录方式
3. 术语统一：使用"手机号账号"和"邮箱账号"的表述
4. 业务数据：无需修改，利用现有账号字段

基于这些讨论结果，您的版本想法是否需要进一步调整？如果需要，请说明具体的调整方向。
```

**User Answer:**
"不需要进一步调整，可以开始开发"

## Example 2: Payment Feature

### Version Idea

"添加支付功能，支持微信支付和支付宝支付"

### Round 1: Business Rules Conflict Check

**Knowledge Base Context:**

- Business rule: "所有支付必须经过统一支付网关"
- Business rule: "支付金额必须大于0.01元"

**Generated Question:**

```
您的版本想法提到"添加支付功能，支持微信支付和支付宝支付"。

根据我们的业务规则库：
- 所有支付必须经过统一支付网关，不能直接对接第三方支付
- 支付金额必须大于0.01元

您的想法是否符合这些规则？是否需要通过统一支付网关来实现？
```

**User Answer:**
"是的，会通过统一支付网关实现"

### Round 2: 功能冲突检查

**Knowledge Base Context:**

- 历史需求文档: "订单模块已集成统一支付网关，支持微信和支付宝"
- Feature list: "支付功能已实现，支持微信、支付宝、银联"

**Generated Question:**

```
根据历史需求文档，我们的订单模块已经集成了统一支付网关，支持微信和支付宝支付。

您的新功能"添加支付功能，支持微信支付和支付宝支付"是否与现有功能重复？还是这是一个新的支付场景（如退款、充值等）？
```

**User Answer:**
"这是为新的业务场景（会员充值）添加支付功能，复用现有的支付网关"

### Round 3: Terminology Consistency Check

**Knowledge Base Context:**

- Terminology: "支付"定义为"用户向平台转账的行为"
- Terminology: "充值"定义为"用户向账户余额增加资金的行为"

**Generated Question:**

```
您提到的是"会员充值"场景。

根据我们的术语词典：
- "支付"：用户向平台转账的行为
- "充值"：用户向账户余额增加资金的行为

会员充值应该使用"充值"还是"支付"这个术语？是否需要统一？
```

**User Answer:**
"应该使用'充值'，这是用户向账户余额增加资金的行为"

### Round 4: 业务数据与系统兼容性检查

**Knowledge Base Context:**

- 系统限制: "支付记录必须包含：订单号、支付方式、金额、状态、创建时间"
- 开发规范: "账户余额支持负数（用于信用额度）"

**Generated Question:**

```
您的功能涉及会员充值，需要修改账户余额。

根据系统限制和开发规范：
- 支付记录必须包含：订单号、支付方式、金额、状态、创建时间
- 账户余额支持负数（用于信用额度）

您的充值功能是否需要新增业务数据，还是复用现有的支付记录和账户余额？
```

**User Answer:**
"复用现有的支付记录和账户余额，充值订单号使用'RECHARGE-'前缀"

### Round 5: Final Confirmation

**Generated Question:**

```
经过前面4轮的讨论，我们确认了：

1. 支付方式：通过统一支付网关，支持微信和支付宝
2. 功能定位：为会员充值场景添加支付功能，复用现有支付网关
3. 术语统一：使用"充值"而非"支付"来描述会员充值行为
4. 业务数据：复用现有支付记录和账户余额

基于这些讨论，您的版本想法是否需要进一步调整？
```

**User Answer:**
"不需要调整，可以开始开发"
