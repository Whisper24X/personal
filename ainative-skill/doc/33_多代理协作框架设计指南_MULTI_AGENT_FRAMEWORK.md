# 如何设计一个多代理协作框架

## 前言

本文重点是站在工程视角，围绕如何基于现有大模型去设计、实现和落地一个可用且可控的多代理协作框架，不包含模型预训练、微调、RL等模型层面内容。当前多代理技术体系仍在快速演进中，比如Claude Skills、LangChain、AutoGen等框架持续受到开发者关注。本文介绍的内容是截至目前业界主流的设计思路和实践经验，一起期待更强大的多代理协作技术落地吧！

本文目的是构建一个面向多代理协作框架的整体知识与设计框架，因此并没有过多深入具体技术实现细节，比如RAG的chunk和embedding、向量数据库的具体实现等等，相关技术细节可参考其他资料。

如果你已经对整个多代理协作知识体系有了解，或者已经在开发多代理系统，建议直接阅读第6节的实践体会。

如果你对多代理协作框架的落地实践有兴趣，可直接看第5节。

## 什么是多代理协作框架

近几年大型语言模型（LLM）在规模和能力上经历了指数级增长，其核心突破在于获得了强大的"认知"与"推理"能力。然而一个核心瓶颈也随之出现：单个LLM Agent的能力边界——它无法同时扮演多个专业角色、无法处理需要多领域协作的复杂任务。这一局限促使行业从"单Agent为中心"转向"Multi-Agent为中心"。多代理协作框架的本质是为多个AI代理提供协作机制，让它们能够像真实团队一样分工协作，对技术同学也意味着可以将过去需要多个专家协作的复杂流程实现自动化，帮助业务实现又快又稳的迭代。

多代理协作新技术不断涌现，是属于技术人的幸福时刻。

### 1. 软件范式的演进

软件编程范式也正在发生根本性变革：从手写逻辑的软件1.0，到数据驱动的软件2.0，再到由自然语言提示驱动的软件3.0，现在正在向多代理协作的软件4.0演进。开发核心也从"如何实现"转向"如何协作"，我们正从代码执行者转变为协作设计者。

| Software 1.0 | Software 2.0 | Software 3.0 | Software 4.0 |
|-------------|-------------|-------------|-------------|
| **核心范式** | 编写逻辑：定义规则和流程 | 定义目标：提供数据和架构 | 描述意图：提供Prompt和上下文 | 设计协作：定义角色和协作流程 |
| **编程内容** | 编写代码 | 准备数据 & 训练模型 | 编写提示词 & 管理上下文 | 设计角色 & 编排工作流 |
| **执行核心** | CPU | GPU | LLM | Multi-Agent System |
| **构建对象** | 算法与逻辑 | 神经网络的权重 | 系统的行为与目标 | 团队的协作机制 |
| **核心特征** | 确定性、可调试 | 感知与泛化能力 | 极致的灵活性与通用性 | 分工协作与集体智能 |
| **典型场景** | 业务逻辑、系统内核 | 图像识别、语音合成 | 内容生成、复杂任务自动化 | 复杂项目生成、多领域协作 |
| **典型提问** | 我该如何实现这个功能？ | 我需要什么数据来训练模型？ | 我该如何设定目标，让Agent自主完成？ | 我该如何设计角色协作，让多个Agent共同完成？ |

### 2. 从单Agent到Multi-Agent

在当前以大型语言模型为基础的工程实践中，多代理协作框架是一个软件系统，它以多个LLM Agent作为核心执行单元，并通过一系列架构组件来赋予其协作能力。

**Multi-Agent Framework = Multiple LLM Agents + Role System + Message System + Workflow Orchestration + Knowledge Base**

多代理协作框架是从传统的单Agent执行（单一智能体）向多Agent协作（团队智能）的根本性转变，其核心特征是从"单一能力"跃升为"分工协作"，行业普遍认为2025年是Multi-Agent元年。

| 维度 | 单Agent系统 | 多代理协作框架 |
|------|------------|----------------|
| **核心本质** | 单一智能体：一个"大脑"完成所有任务 | 协作系统：多个"大脑"分工协作 |
| **技术架构** | LLM+规划+记忆+工具 (单一软件系统) | Multiple LLM+角色系统+消息系统+工作流编排 (完整协作框架) |
| **角色定位** | 被动的"全能助手"；等待提问，给出答案 | 主动的"专业团队"；拥有分工、协作和流程 |
| **核心能力** | 文本理解与生成，在上下文窗口内进行推理 | 角色分工、消息路由、工作流编排、知识共享 |
| **工作模式** | 单次、静态的交互 | 多步、动态的协作流程 |
| **与环境的交互** | 封闭、被动，仅限于文本对话 | 开放、主动，能够通过消息系统协作 |
| **记忆与状态** | 基本无状态，依赖有限的上下文窗口 | 有状态，拥有角色记忆、消息历史和协作状态 |
| **打个比方** | 一位博学但单打独斗的专家 | 一支拥有多个专家的协作团队 |
| **总结** | 强大的核心技术基石，是驱动Agent的引擎 | 基于LLM构建的完整协作系统，它将多个Agent的能力转化为实际生产力 |

**LLM 是新的操作系统内核 (LLM OS)，而 Multi-Agent Framework 就是在这个新 OS 上运行的协作系统。** -- 基于Andrej Karpathy的观点扩展

### 3. 多代理协作框架研发与传统研发的区别

传统研发是将逻辑外化为代码，而多代理协作框架研发则是将协作机制内化到框架的架构和配置中，并通过设计良好的角色系统、消息系统和工作流来确保多个Agent能够自主协作达成目标。这要求开发者从一个逻辑精确的编码者转变为一个协作机制和智能体的设计者。

| 维度 | 传统软件工程研发 | 多代理协作框架研发 |
|------|----------------|-------------------|
| **核心目标** | 实现特定的功能和逻辑 | 实现一个协作机制和自主行为 |
| **思维模型** | 命令式：定义每一步如何做 | 协作导向式：定义角色如何协作和期望是什么 |
| **主要产出物** | 源代码、可执行程序、API等 | 框架架构、角色定义、工作流配置、评估指标等 |
| **核心开发者角色** | 开发工程师、测试工程师、产品 | 框架架构师、角色设计师、工作流编排师、业务专家 |
| **研发模式** | 计划驱动：需求分析 -> 设计 -> 编码 -> 测试 -> 部署。流程线性且严谨 | 实验驱动/探索式：定义协作目标 -> 构建原型框架 -> 大量评估与测试 -> 角色调优/架构调整 -> 再评估。循环迭代，高度依赖反馈 |
| **协作方式** | 基于接口和文档的协作：团队通过定义清晰的API接口、模块职责和设计文档进行协作 | 基于消息和评估的协作：架构师、角色设计师、业务专家围绕着一个共同的评估集进行协作。大家共同定义"什么是好协作"，并一起分析框架在复杂场景下的失败案例 |
| **调试方法** | Debug设置断点，检查堆栈和变量 | 追踪和可视化多代理的完整协作链、消息路由路径、角色决策过程 |
| **结果评判标准** | 确定性：输入A ⇒ 输出B（可复现）<br>评判标准：功能正确性、性能、稳定性 | 概率性：输入A ⇒ 大概率输出B<br>评判标准：协作可靠性、任务完成率、角色调用准确率、消息路由正确性 |
| **控制流** | 硬编码：由 If-else 语句和函数调用精确控制 | 动态决策：由消息系统和工作流引擎实时路由和编排 |
| **迭代核心** | 需求迭代、代码重构和 Bug Fix | 框架升级、角色调优、工作流调整、评估体系优化等 |

## 多代理协作框架基础知识

为了让多个LLM Agent能够协作解决复杂的现实问题，我们需要为它们配备角色系统（Role System）、行动系统（Action System）、消息系统（Message System）、工作流编排（Workflow Orchestration）、知识库系统（Knowledge Base）以及记忆系统（Memory System），这就是一个完整的多代理协作框架全貌。

**Role System（角色系统）**：定义每个Agent的专业角色、职责和能力边界，让Agent知道自己"是谁"、"能做什么"。

**Action System（行动系统）**：定义Agent可以执行的具体行动，将复杂任务拆解为原子化的行动单元。

**Message System（消息系统）**：实现Agent间的通信机制，支持广播、定向和订阅三种路由模式。

**Workflow Orchestration（工作流编排）**：定义Agent的协作流程，支持顺序执行、并行执行和条件分支。

**Knowledge Base（知识库系统）**：为Agent提供外部知识支持，通过RAG技术增强Agent的上下文理解能力。

**Memory System（记忆系统）**：为Agent提供短期记忆（news）和长期记忆（memory），支持跨会话的知识复用。

比如一个软件开发多代理协作框架：

```
用户需求："创建一个TODO应用"
  ↓
Salesperson（销售）: 分析需求，输出MRD
  ↓
ProductManager（产品经理）: 基于MRD编写PRD
  ↓
Architect（架构师）: 基于PRD设计系统架构
  ↓
ProjectManager（项目经理）: 拆分任务
  ↓
Engineer（工程师）: 编写代码
  ↓
QAEngineer（QA工程师）: 编写测试
  ↓
完成项目
```

下面针对多代理协作框架研发涉及的一些关键技术点进行重点介绍，这些技术点的形式包括系统、机制、协议等等。

### Part1：角色系统（Role System）—— "智能体身份"

角色系统是多代理协作框架的"身份体系"。它不是简单的命名，而是通过结构化的角色定义，将非确定性的LLM输出约束为确定性的专业行为，是构建稳定多代理协作框架的地基。

**Talk is cheap, show me your role definition！**

#### 关键点：角色定义 (Role Definition)

**说明**：为每个Agent设定一个明确的专业领域角色，可以激活模型内部相关的垂直领域知识分布，使其输出内容的专业术语、视角和行为模式与设定角色保持一致，从而提升在特定领域任务中的表现。

**示例**：ProductManager角色定义

```typescript
class ProductManager extends Role {
  constructor(context: Context, name: string = 'ProductManager') {
    const config: IRoleConfig = {
      name,
      profile: 'ProductManager',
      goal: '产品经理，负责基于需求文档编写详细的产品需求文档（PRD），进行产品规划',
      constraints: '深入理解用户需求，进行需求分析和转化，编写用户故事和功能需求',
      description: '我是一名专业的产品经理，擅长需求分析和产品规划，能够将业务需求转化为详细的产品需求文档。',
    };
    super(config, context);
    
    // 设置监听的 action（触发条件）
    this.watch([ACTION_WRITE_REQUIREMENT_SPEC]);
    
    // 设置角色执行的 actions
    this.setActions([
      new WritePRD(),
      new PRDReview(),
      new ImprovePRD(),
    ]);
  }
}
```

#### 关键点：角色监听机制（Watch Mechanism）

**说明**：角色通过`watch()`方法订阅特定类型的消息，当环境中发布匹配的消息时，角色会被触发执行相应的行动。这种机制实现了角色间的解耦通信。

**路由模式**：
- **广播模式**：消息发送给所有角色（`MESSAGE_ROUTE_TO_ALL`）
- **定向模式**：消息发送给指定角色（`sendTo`指定角色名）
- **订阅模式**：角色订阅特定类型的消息（`watch`匹配`causeBy`）

**示例**：消息路由机制

```typescript
// Environment中的消息路由逻辑
publishMessage(message: Message): boolean {
  for (const [roleName, role] of this.roles.entries()) {
    const shouldReceive = 
      message.sendTo.has(MESSAGE_ROUTE_TO_ALL) ||  // 广播
      message.sendTo.has(roleName) ||              // 定向
      role.rc.watch.has(message.causeBy);         // 订阅
    
    if (shouldReceive) {
      role.putMessage(message);
    }
  }
}
```

#### 关键点：角色状态管理

**说明**：角色在执行过程中有不同的状态，需要管理角色的生命周期和执行状态。

**角色状态（RoleStatus）**：
- `IDLE`: 空闲状态，等待消息
- `PENDING`: 有待执行的任务，已选择Action但未执行
- `RUNNING`: 正在执行Action
- `FAILED`: 执行失败

**状态转换流程**：
```
IDLE -> PENDING (think()选择action) 
  -> RUNNING (act()开始执行)
    -> IDLE (执行完成) 或 FAILED (执行失败)
```

#### 关键点：角色LLM配置管理

**说明**：不同角色可能需要使用不同的LLM配置（模型、温度、最大token等），支持角色级别的LLM配置管理。

**配置优先级**：
1. **数据库配置（最高优先级）**：从`role_llm_configs`表加载角色特定的LLM配置
2. **显式配置**：构造函数中传入的`config.llm`
3. **默认配置（最低优先级）**：使用系统默认的LLM配置（`context.llm`）

**工程挑战与应对方法**

| 挑战点 | 现象描述 | 应对方法 |
|--------|---------|---------|
| 角色行为不一致 | 相同角色在不同时间执行相同任务时，输出结果差异很大，难以保证协作的稳定性 | **角色配置标准化**：为每个角色定义标准的goal、constraints和description，确保角色行为的一致性 |
| 消息路由错误 | 消息被路由到错误的角色，或者消息没有被任何角色接收，导致协作流程中断 | **消息路由验证**：在消息发布时验证路由规则，记录路由日志，提供消息路由可视化工具 |
| 角色状态混乱 | 角色状态管理不当，导致角色在错误的状态下执行Action，或者状态转换异常 | **状态机设计**：使用明确的状态机定义角色状态转换规则，在状态转换时进行验证 |

### Part2：行动系统（Action System）—— "如何执行"

行动系统是多代理协作框架的"执行单元"。它将复杂任务拆解为原子化的行动，每个Action是独立的、可复用的任务单元。

#### 关键点：Action的原子化设计

**说明**：每个Action应该是原子化的，即完成一个明确的、不可再分的任务。Action的设计遵循单一职责原则，一个Action只做一件事。

**示例**：WritePRD Action

```typescript
class WritePRD extends BaseAction {
  name = 'WritePRD';
  description = '编写产品需求文档（PRD）';

  async run(input: string, options?: WritePRDOptions): Promise<IActionOutput> {
    // 1. 读取输入（MRD文档或用户需求）
    // 2. 使用RAG检索相关文档
    // 3. 调用LLM生成PRD
    // 4. 保存到workspace
    // 5. 返回结果
  }
}
```

#### 关键点：Action执行流程

**说明**：Action的执行遵循标准的流程：输入准备 -> 执行 -> 输出处理 -> 状态更新。

**执行流程**：
1. **输入准备**：从消息、记忆或workspace中提取输入
2. **执行**：调用LLM或工具执行任务
3. **输出处理**：格式化输出，保存到workspace
4. **状态更新**：更新Action状态（RUNNING -> COMPLETED/FAILED）

#### 关键点：Workspace管理

**说明**：Workspace是Action的"工作空间"，用于存储Action产生的文档和代码。Workspace采用分层结构：`workspace/{applicationId}/{projectId}/v{version}/{documentType}/`

**Workspace结构**：
```
workspace/
├── {applicationId}/
│   ├── {projectId}/
│   │   ├── v1/
│   │   │   ├── MRD/
│   │   │   │   └── MRD.md
│   │   │   ├── PRD/
│   │   │   │   └── PRD.md
│   │   │   ├── DESIGN/
│   │   │   │   └── DESIGN.md
│   │   │   ├── CODE/
│   │   │   │   └── src/
│   │   │   └── TEST/
│   │   │       └── tests/
```

#### 关键点：特殊输入处理

**说明**：某些Action需要特殊的输入处理逻辑，比如WriteTest需要组合PRD和代码，MRDReview需要从memory中查找MRD文档。

**特殊输入处理示例**：

```typescript
// WriteTest自动组合PRD和代码
if (actionName === 'WriteTest') {
  const prdMessage = rc.memory.find(m => m.causeBy === 'WritePRD');
  const codeMessage = rc.memory.find(m => m.causeBy === 'WriteCode');
  input = `PRD文档：\n${prdMessage.content}\n\n代码实现：\n${codeMessage.content}`;
}

// MRDReview从memory查找MRD文档
if (actionName === 'MRDReview') {
  const mrdMessage = rc.news.find(m => m.causeBy === 'WriteMRD') 
    || rc.memory.find(m => m.causeBy === 'WriteMRD');
  input = mrdMessage?.content || '';
}
```

**工程挑战与应对方法**

| 挑战点 | 现象描述 | 应对方法 |
|--------|---------|---------|
| Action执行超时 | 某些Action（如WriteCode）执行时间很长，统一超时可能导致长时间运行的Action被错误中断 | **分层超时策略**：不同Action设置不同的超时时间，WriteCode设置60分钟，其他Action使用默认超时 |
| Action输入错误 | Action接收到的输入格式不正确或缺失关键信息，导致执行失败 | **输入验证**：在Action执行前验证输入格式，提供友好的错误提示，支持从多个来源fallback获取输入 |
| Workspace路径混乱 | Workspace路径格式不一致，导致文件保存位置错误或读取失败 | **路径标准化**：统一Workspace路径格式，提供路径生成工具，支持路径格式转换 |

### Part3：消息系统（Message System）—— "如何通信"

消息系统是多代理协作框架的"通信协议"。它实现了Agent间的解耦通信，支持广播、定向和订阅三种路由模式。

#### 关键点：消息格式设计

**说明**：消息是Agent间通信的载体，需要包含足够的信息来支持路由和处理。

**消息结构**：
```typescript
class Message {
  id: string;                    // 消息唯一标识
  content: string;               // 自然语言内容
  instructContent?: Record<string, any>; // 结构化内容
  role: string;                  // 角色类型
  causeBy: string;               // 触发Action
  sentFrom: string;              // 发送者
  sendTo: Set<string>;           // 接收者集合
  metadata: Record<string, any>; // 元数据
}
```

#### 关键点：消息路由机制

**说明**：消息路由支持三种模式：广播、定向和订阅。

**路由规则**：
1. **广播模式**：`sendTo`包含`MESSAGE_ROUTE_TO_ALL`，消息发送给所有角色
2. **定向模式**：`sendTo`包含特定角色名，消息只发送给指定角色
3. **订阅模式**：角色的`watch`集合包含消息的`causeBy`，消息路由到该角色

**路由逻辑**：
```typescript
private isMessageFor(message: Message, role: Role): boolean {
  // 广播模式
  if (message.sendTo.has(MESSAGE_ROUTE_TO_ALL)) {
    return true;
  }
  
  // 定向模式
  if (message.sendTo.has(role.profile)) {
    return true;
  }
  
  // 订阅模式
  if (role.rc.watch.has(message.causeBy)) {
    return true;
  }
  
  return false;
}
```

#### 关键点：消息历史管理

**说明**：消息历史用于追踪Agent的协作过程，支持消息查询、过滤和回放。

**消息存储**：
- **Environment历史**：Environment维护全局消息历史
- **Role记忆**：每个Role维护自己的消息记忆（news和memory）
- **数据库持久化**：重要消息保存到数据库，支持跨会话查询

**工程挑战与应对方法**

| 挑战点 | 现象描述 | 应对方法 |
|--------|---------|---------|
| 消息丢失 | 消息在路由过程中丢失，导致角色没有收到应该接收的消息 | **消息确认机制**：记录消息路由日志，提供消息追踪工具，支持消息重发 |
| 消息循环 | 消息在角色间循环传递，导致无限循环 | **消息去重**：使用消息ID去重，限制消息传递深度，检测循环并中断 |
| 消息格式不一致 | 不同Action产生的消息格式不一致，导致下游角色无法正确解析 | **消息格式标准化**：定义标准的消息格式规范，提供消息格式验证工具 |

### Part4：工作流编排（Workflow Orchestration）—— "如何协作"

工作流编排是多代理协作框架的"控制中枢"。它定义了Agent的协作流程，支持顺序执行、并行执行和条件分支。

#### 关键点：工作流定义

**说明**：工作流定义了角色的执行顺序和输入输出映射关系。

**工作流配置示例**：
```typescript
const workflowConfig = {
  name: '标准软件开发流程',
  steps: [
    {
      role: 'Salesperson',
      actions: ['WriteMRD'],
      inputMapping: { 'User': 'userIdea' },
      outputMapping: { 'WriteMRD': 'MRD' }
    },
    {
      role: 'ProductManager',
      actions: ['WritePRD'],
      inputMapping: { 'WriteMRD': 'MRD' },
      outputMapping: { 'WritePRD': 'PRD' }
    },
    // ...
  ]
};
```

#### 关键点：多角色串联

**说明**：多个角色通过消息系统串联，前一个角色的输出作为后一个角色的输入。

**串联流程**：
```
User -> Salesperson (WriteMRD) -> ProductManager (WritePRD) 
  -> Architect (WriteDesign) -> ProjectManager (BreakdownTasks)
  -> Engineer (WriteCode) -> QAEngineer (WriteTest)
```

#### 关键点：输入输出映射

**说明**：工作流引擎根据输入输出映射关系，自动将前一步的输出传递给下一步的输入。

**映射规则**：
- 根据`causeBy`匹配消息
- 从Role的memory中查找匹配的消息
- 支持多输入组合（如WriteTest需要PRD和代码）

#### 关键点：交互式确认机制

**说明**：在工作流执行过程中，支持人工确认和干预，提升可控性。

**交互模式**：
- **自动模式**：工作流自动执行，无需人工干预
- **交互模式**：每个关键步骤暂停，等待用户确认（继续/编辑/重新生成/跳过）

**工程挑战与应对方法**

| 挑战点 | 现象描述 | 应对方法 |
|--------|---------|---------|
| 工作流死锁 | 工作流执行过程中，角色等待彼此的消息，导致死锁 | **超时机制**：设置工作流执行超时，检测死锁并中断，提供工作流可视化工具 |
| 输入输出映射错误 | 输入输出映射关系错误，导致角色接收到错误的输入 | **映射验证**：在工作流定义时验证映射关系，提供映射可视化工具，支持动态调整映射 |
| 工作流执行不可控 | 工作流自动执行，用户无法干预，导致错误无法及时纠正 | **交互式确认**：支持在工作流关键节点暂停，提供用户确认接口，支持回滚和重试 |

### Part5：知识库系统（Knowledge Base）—— "如何增强"

知识库系统是多代理协作框架的"外部记忆"。它通过RAG技术为Agent提供外部知识支持，增强Agent的上下文理解能力。

#### 关键点：RAG检索增强

**说明**：RAG（Retrieval-Augmented Generation）结合了信息检索和语言生成，通过检索外部知识库来增强LLM的生成能力。

**RAG流程**：
1. **索引**：将文档切片并向量化，存入向量数据库
2. **检索**：根据查询检索最相关的文档片段
3. **增强**：将检索到的文档片段作为上下文输入给LLM
4. **生成**：LLM基于增强的上下文生成答案

#### 关键点：文档索引与检索

**说明**：知识库支持多种文档类型的索引和检索。

**文档类型**：
- **MRD/PRD/DESIGN文档**：产品文档库
- **代码仓库**：代码知识库
- **API文档**：接口文档库

**检索策略**：
- **语义检索**：使用向量相似度检索
- **关键词检索**：使用关键词匹配
- **混合检索**：结合语义和关键词检索

#### 关键点：上下文构建策略

**说明**：如何将检索到的文档片段构建为有效的上下文。

**上下文构建**：
1. **相关性排序**：按相关性对检索结果排序
2. **去重**：去除重复的文档片段
3. **截断**：根据上下文窗口限制截断
4. **格式化**：格式化为LLM可理解的格式

**工程挑战与应对方法**

| 挑战点 | 现象描述 | 应对方法 |
|--------|---------|---------|
| 检索内容质量差 | 检索到的文档片段不相关或质量低，导致LLM生成错误内容 | **检索优化**：使用重排序模型提升检索质量，支持多轮检索和过滤，提供检索结果评估工具 |
| 上下文窗口溢出 | 检索到的文档片段过多，超过LLM的上下文窗口限制 | **上下文压缩**：使用摘要压缩长文档，限制检索结果数量，动态调整上下文长度 |
| 知识库更新滞后 | 知识库内容过时，导致Agent使用过时的知识 | **知识库更新机制**：支持知识库版本管理，提供知识库更新接口，定期更新知识库内容 |

### Part6：记忆系统（Memory System）—— "如何记忆"

记忆系统是多代理协作框架的"内部记忆"。它为Agent提供短期记忆（news）和长期记忆（memory），支持跨会话的知识复用。

#### 关键点：短期记忆（News）

**说明**：News是Role的短期记忆，存储最近接收到的消息，用于当前任务的上下文。

**News特点**：
- 容量有限，只保留最近的消息
- 任务完成后自动清理
- 用于Action的输入准备

#### 关键点：长期记忆（Memory）

**说明**：Memory是Role的长期记忆，存储重要的历史消息，用于跨任务的知识复用。

**Memory特点**：
- 容量较大，可以存储大量历史消息
- 持久化到数据库
- 用于RAG检索和上下文构建

#### 关键点：上下文窗口管理

**说明**：如何管理LLM的上下文窗口，确保重要信息不被截断。

**管理策略**：
1. **消息重要性评分**：根据消息的重要性评分，优先保留重要消息
2. **消息摘要**：对旧消息进行摘要，保留关键信息
3. **滑动窗口**：使用滑动窗口机制，保留最近的消息
4. **选择性保留**：根据任务需求选择性保留相关消息

**工程挑战与应对方法**

| 挑战点 | 现象描述 | 应对方法 |
|--------|---------|---------|
| 记忆容量限制 | News和Memory容量有限，无法存储所有历史消息 | **记忆压缩**：使用摘要压缩旧消息，根据重要性筛选消息，支持外部存储 |
| 记忆检索效率低 | 从大量记忆中检索相关信息效率低 | **记忆索引**：为记忆建立索引，使用向量检索，支持记忆分类和标签 |
| 记忆一致性 | 不同Role的记忆不一致，导致协作出现问题 | **共享记忆**：支持Role间共享记忆，使用全局记忆库，提供记忆同步机制 |

## 工程实践

### 1. 多代理协作框架研发流程

在多代理协作框架的研发过程中，不再是简单的编写逻辑，而是逐步设计一个协作机制。研发流程的核心主要有以下三个关键点：

**核心关注点的转变：从"功能实现"到"协作设计"**

传统研发关注如何精确实现预设的每一个功能点；而多代理协作框架研发的核心是定义一个协作机制，并赋予多个Agent自主协作以达成任务的能力。

**流程驱动力的转变：从"计划驱动"到"实验驱动"**

多代理协作框架研发并非线性的"需求-开发-测试-发布"瀑布流，而是一个紧密的"评估-迭代"循环。不再追求输入与输出之间绝对的、确定的映射关系，转而追求在复杂环境中协作行为的可靠性与鲁棒性。

**协作方式的转变：从"基于接口"到"基于消息"**

团队围绕一个共同的、可执行的消息协议进行协作。这个协议由框架架构师、角色设计师和业务专家共同定义和维护，它包含了多样化的消息类型和明确的路由规则，是团队统一的目标导向。

### 2. 多代理协作框架设计范式

多代理协作框架研发目前还没有形成像软件设计模式（如单例、工厂、观察者等）那样标准化、广泛共识的"设计模式"体系。

**范式一：最小可用范式**

本质上是「单角色单Action + 简单消息传递」，非常适合"一问一答"这类"轻交互、弱流程"场景。

**核心特征**：
- 单角色触发：每次用户请求触发一个角色处理
- 线性流程：用户 -> 角色 -> Action -> 输出
- 无状态设计：不维护长期任务状态

**优点**：
- 高效率与低延迟：响应快，适合对时间敏感的场景
- 成本效益高：LLM调用次数少，运行成本最低
- 实现和维护简单：代码库简单，易于调试

**缺点**：
- 缺乏多角色协作能力：无法处理需要多角色协作的复杂任务
- 功能局限性：只能处理简单的单步任务

**范式二：工作流式（Workflow）**

工作流式是一种由开发者预先定义角色协作流程的架构模式。框架不依赖运行时动态规划，而是严格按照预设的控制流执行一系列结构化任务。

**核心特征**：
- 预定义执行路径：任务的流转逻辑在开发阶段即已确定
- 结构化任务拆解：通过固定流程将复杂问题结构化为具体的步骤
- 关注控制流：系统的核心价值在于如何编排角色的输入输出流向

**优点**：
- 高可预测性与可靠性：每一步的输入输出明确，行为边界清晰
- 强大的监控与调试能力：支持对每个节点设置SLA、超时中断和失败重试机制
- 性能与资源效率：对于I/O密集型任务，并行工作流可大幅降低总耗时

**缺点**：
- 灵活性受限：缺乏探索性，无法处理开放式问题
- 复杂度与维护成本：设计门槛高，初始建模难度大

**范式三：动态规划式**

动态规划式是一种依赖大模型在运行时进行自主推理和任务编排的系统架构。与工作流式执行既定步骤不同，动态规划式框架被赋予了"大脑"，能够在不确定或未知的环境中自主拆解目标、选择角色、处理反馈并动态调整路径。

**核心特征**：
- 运行时动态决策：执行路径不是开发者预设的，而是由框架根据当前环境状态和任务目标实时生成
- 推理驱动行动：通过思考->行动->反馈的闭环，逐步逼近答案
- 高度自治：框架具备自我修正能力，能够处理执行过程中的报错或意外信息

**优点**：
- 极高的灵活性与适应性：无需预定义死板流程，能适应未知环境
- 具备解释性与可控性：过程透明，让用户能清晰看到框架的思考路径

**缺点**：
- 稳定性与可靠性挑战：可能陷入无效的思考循环
- 对模型能力的强依赖：极度依赖LLM的逻辑推理能力

### 3. 多代理协作框架开发方式

从实际工程开发方式看，大致可以分为三种方式：

| 类型 | 关键内容说明 | 示例 |
|------|------------|------|
| **纯代码型** | 完全通过代码定义框架行为：角色、消息、工作流、评估均以代码形式管理；支持任意复杂逻辑：动态规划、多角色协作、自定义记忆策略；具备完整工程能力：版本控制、CI/CD、监控告警、A/B测试 | LangChain、AutoGen、Mind2Build |
| **配置驱动型** | 通过配置文件（JSON/YAML）或数据库定义框架行为；支持可视化配置界面；代码生成或配置驱动，无需手写复杂逻辑 | Dify、Coze、AI Studio |
| **可视化设计型** | 通过可视化界面（拖拽节点、连线）定义框架工作流；支持预置角色和Action集成；提供基础状态管理、分支判断、重试机制 | Dify Workflow、Coze Workflow |

## 案例分享：Mind2Build框架实践

### 1. 背景

在软件开发领域，从需求到代码的完整流程涉及多个角色的协作：产品经理编写PRD、架构师设计系统、工程师编写代码、QA工程师编写测试。传统的开发流程需要多个专家协作，效率低下，且难以标准化。

**核心挑战**：

**多角色协作的复杂性**

软件开发涉及多个专业角色，每个角色有独特的职责和专业能力。如何让多个AI Agent像真实团队一样协作，是一个巨大的挑战。

**流程标准化的难题**

不同团队、不同项目的开发流程存在差异，如何设计一个既灵活又标准化的流程框架，是一个核心问题。

**知识管理的规模化**

软件开发涉及大量的文档和代码知识，如何有效管理和利用这些知识，提升Agent的能力，是一个持续挑战。

### 2. 整体方案

Mind2Build是一个多代理协作框架，通过模拟软件公司团队协作的方式，实现从用户需求到完整软件项目的自动化生成。

**核心定位**：`Code = SOP(Team)` - 通过标准化操作流程和团队协作实现软件开发自动化。

**9个角色协作体系**：

1. **Salesperson（销售）**：收集需求，输出MRD
2. **ProductManager（产品经理）**：基于MRD编写PRD
3. **Architect（架构师）**：基于PRD设计系统架构
4. **ProjectManager（项目经理）**：拆分任务，管理项目
5. **Engineer（工程师）**：编写代码
6. **QAEngineer（QA工程师）**：编写测试计划、测试用例
7. **AutomationEngineer（自动化工程师）**：执行自动化测试，生成测试报告
8. **TeamLeader（团队领导）**：协调任务
9. **DataAnalyst（数据分析师）**：数据分析

**30个Actions完整覆盖**：

- **文档编写**：WriteMRD、WritePRD、WriteDesign、WriteSubProjectDesign
- **文档审查**：MRDReview、PRDReview、DesignReview、SubProjectDesignReview
- **文档改进**：ImproveMRD、ImprovePRD、ImproveDesign、ImproveTest
- **任务管理**：BreakdownTasks、GenerateTask、ExecuteSubtask
- **代码编写**：WriteCode、RunCode、FixBug、CodeReview
- **测试相关**：TestabilityReview、WriteTestPlan、WriteTest、TestCaseReview、TestReview
- **自动化测试**：AutomationPlanning、AutomationExecution、CoverageQualityCheck、QAConclusion
- **其他**：SearchEnhancedQA、Coordinate、DataAnalysis

**工作流编排机制**：

- 支持预定义工作流和自定义工作流
- 支持多角色串联和输入输出映射
- 支持交互式确认机制（CLI + Web）

**知识库增强**：

- RAG检索增强（Qdrant向量数据库）
- 文档知识库（MRD/PRD/DESIGN）
- 代码知识库（代码仓库关联）
- 章节对话历史（迭代优化）

### 3. 流程设计

**标准软件开发流程**：

```
用户需求
  ↓
Salesperson: WriteMRD（市场研究文档）
  ↓
ProductManager: WritePRD（产品需求文档）
  ↓
Architect: WriteDesign（系统设计文档）
  ↓
ProjectManager: BreakdownTasks（任务拆分）
  ↓
ProjectManager: WriteSubProjectDesign（子项目设计）
  ↓
Engineer: WriteCode（编写代码）
  ↓
QAEngineer: WriteTestPlan → WriteTest → TestCaseReview（测试设计3步流程）
  ↓
AutomationEngineer: AutomationPlanning → AutomationExecution 
  → CoverageQualityCheck → QAConclusion（自动化测试4步流程）
  ↓
完成项目
```

**交互式确认流程**：

- **自动模式**：工作流自动执行，无需人工干预
- **交互模式**：每个关键步骤暂停，等待用户确认
  - **继续（C）**：接受当前输出，继续下一步
  - **编辑（E）**：编辑当前输出内容
  - **重新生成（R）**：重新生成当前输出
  - **查看（V）**：查看完整内容
  - **跳过（S）**：跳过当前步骤
  - **退出（Q）**：保存并退出

**Git仓库管理流程**：

- 项目创建时自动初始化Git仓库
- 版本创建时自动创建Git分支
- 支持版本分支管理和切换

### 4. 知识体系

**文档知识库**：

- **MRD文档库**：存储历史MRD文档，支持RAG检索
- **PRD文档库**：存储历史PRD文档，支持RAG检索
- **DESIGN文档库**：存储历史设计文档，支持RAG检索

**代码知识库**：

- **代码仓库关联**：关联Git代码仓库，支持代码检索
- **代码片段索引**：索引代码片段，支持语义检索

**RAG检索策略**：

- **语义检索**：使用向量相似度检索相关文档
- **关键词检索**：使用关键词匹配检索
- **混合检索**：结合语义和关键词检索

**章节对话历史**：

- 记录PRD/MRD章节的迭代优化过程
- 支持多轮对话和内容调整
- 为后续调整提供上下文

### 5. 技术实现亮点

## 个人实践体会

**从"最小可用"开始，渐进式复杂，遵循"奥卡姆剃刀"**

在多代理协作框架设计中一般会面临一个误区：试图在初期就构建功能完备的复杂系统，但实践证明从最简单可用版本开始才是明智之选。先用基础的角色+消息+单Action组合验证核心业务价值，再根据需求逐步引入工作流编排、知识库等复杂组件。奥卡姆剃刀原则尤为适用：如无必要，勿增实体。很多时候精心设计的单角色系统比多角色协作更稳定高效。通过渐进式方法，我们能快速验证业务假设，在每个阶段充分理解系统瓶颈，真正"压榨"出架构的最大潜力，避免过度工程化带来的维护成本和不确定性。

**混合架构是落地常态，"工作流外壳 + 智能内核 + 知识管理"**

纯粹的自主多代理协作在生产环境中往往难以控制，"混合架构"已成为主流选择，核心是用确定性工作流作为外壳，定义清晰的任务边界；在关键决策节点嵌入AI作为智能内核，负责理解、推理和生成；配套完善的知识管理系统，包括向量数据库、业务规则库和工具集。这种设计既保留AI的灵活性，又通过工作流确保可预测性。

**消息系统是协作的核心**

消息系统是多代理协作框架的核心，它实现了角色间的解耦通信。设计良好的消息系统应该支持多种路由模式（广播、定向、订阅），提供消息历史管理和追踪能力。消息格式的设计直接影响框架的扩展性和可维护性。

**知识库质量决定框架能力上限**

真正有价值的知识包含多个层次：显性的文档规范、隐性的专家经验、平台沉淀的案例库、实际操作中发现的边界情况。这些知识分散在不同人员和系统中，且存在冲突、过时、不完整等问题。更关键是质量和持续性：旧文档可能已不适用，专家经验需结构化整理，知识库需随业务持续更新。建议建立"知识工程"流程：比如业务专家 + 知识工程师协作梳理知识图谱，建立版本管理和更新机制，虽然会投入一定资源，但对于知识依赖强的框架非常有必要，因为它决定了框架的能力上限。

**交互式确认提升可控性**

在多代理协作框架中，完全自动化的执行往往难以控制，错误难以及时发现和纠正。交互式确认机制允许用户在工作流关键节点进行人工确认和干预，大大提升了框架的可控性。设计良好的交互式确认应该支持多种操作（继续/编辑/重新生成/跳过），提供友好的用户界面（CLI + Web），支持状态保存和恢复。

**无评估不迭代，无数据不优化**

多代理协作框架的输出不确定性使"感觉"成为最不可靠的评判标准。因此需要建立科学的评估体系，首先是离线评估：构建高质量测试集（覆盖正常、边界、对抗case），定义明确指标，建立自动化评估流程；其次是在线评估：通过A/B测试、用户反馈、人工抽检收集真实数据。更重要是能够建立线上数据发现问题→标注产生新样本→优化框架或配置→再次上线验证这样的飞轮，不然没有被量化验证的优化都是自我安慰。

**角色设计需要深度理解业务**

多代理协作框架开发是高度跨领域的工作，不能简单分为"产品定需求、工程写代码"。架构师和角色设计师都必须深入理解业务场景。角色设计时，只有理解业务才能判断哪些环节需要智能、哪些需要确定性，在Action设计中，业务理解更是核心：什么是正确的输出格式，哪些边界情况需要特别说明，对业务理解的深度决定了一个框架架构的潜力。

**拉长时间看，在特定范围内多代理协作比单Agent更可靠**

在定义明确、规则清晰的特定领域内，多代理协作框架会逐渐体现出超越单Agent的稳定性。它通过角色分工实现了专业能力的聚焦，通过消息系统实现了协作的标准化，通过工作流编排实现了流程的可控性。随着知识库完善和案例积累，框架能力会持续提升并沉淀在系统中，不会因人员流动而流失。可能需要换一种思维来看：把多代理协作框架作为"虚拟团队"来培养和管理。包括为框架分配明确职责范围，定义"团队说明书"，持续"培训"（知识更新、案例积累），建立与人类同事的协作模式，或许这也是适应AI时代的组织进化方向。

## 总结

多代理协作框架是AI Agent技术发展的重要方向，它将单个Agent的能力扩展为多个Agent的协作能力，实现了从"单一智能"到"集体智能"的跃升。

**多代理协作框架的核心要素**：

1. **角色系统**：定义Agent的专业身份和能力边界
2. **行动系统**：将复杂任务拆解为原子化的行动单元
3. **消息系统**：实现Agent间的解耦通信
4. **工作流编排**：定义Agent的协作流程
5. **知识库系统**：为Agent提供外部知识支持
6. **记忆系统**：为Agent提供内部记忆能力

**设计原则与最佳实践**：

1. **从最小可用开始**：渐进式复杂，避免过度工程化
2. **混合架构**：工作流外壳 + 智能内核 + 知识管理
3. **消息驱动**：通过消息系统实现角色间解耦
4. **知识工程**：建立知识库的持续更新机制
5. **交互式确认**：提升框架的可控性
6. **科学评估**：建立量化的评估体系

**未来发展方向**：

1. **更智能的角色决策**：使用更强的LLM提升角色的自主决策能力
2. **更灵活的工作流编排**：支持动态工作流和自适应编排
3. **更强大的知识库**：支持多模态知识（文本、代码、图像等）
4. **更好的协作机制**：支持角色间的协商和冲突解决
5. **更完善的评估体系**：建立标准化的评估基准和工具

多代理协作框架技术仍在快速演进中，期待更强大的多代理协作技术落地，让AI Agent真正成为可靠的协作者！
