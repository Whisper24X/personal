## 1. 产品概述

### 1.1 产品定位
研学系统是一个多渠道研学活动管理平台，为用户提供研学活动购买、课程预约、合同签署等一站式服务。

### 1.2 支持的销售渠道
- **小程序**：微信小程序渠道
- **抖音**：抖音小店渠道
- **微店**：微店平台渠道
- **视频号小店**：微信视频号小店渠道

### 1.3 商品类型

#### 1.3.1 预约商品（主流商品）
**特点**：
- 用户购买后需要预约具体的课程时间
- 一个商品可以包含多个课程分类
- 每个分类可以预约指定次数
- 根据总预约次数自动拆分子订单
- 完成所有预约后订单才算完成

**使用场景**：
- 单日营活动（如"北京科技馆一日游"）
- 多日营活动（如"夏令营5天4夜"）
- 课程套餐（如"3次编程课+2次科学课"）

**示例**：
```
商品：研学单日营套餐
├── 分类A：科技馆参观（可预约2次）
└── 分类B：博物馆参观（可预约1次）

总预约次数 = 2 + 1 = 3次

用户购买后：
1. 系统自动拆分为3个子订单
2. 每次预约消耗一个子订单
3. 完成3次预约后，订单完成
```

#### 1.3.2 定金商品
**特点**：
- 用户支付即完成，无需预约
- 有库存限制
- 支付成功后订单直接完成
- 拆分子订单

**使用场景**：
- 活动定金
- 报名费
- 占位费

## 2. 核心业务实体

### 2.1 订单（Order）

**订单的基本信息**：
- 订单编号：唯一标识一笔订单
- 商品信息：购买的商品名称、价格
- 渠道信息：来自哪个销售渠道（小程序/抖音/微店等）
- 用户信息：购买用户的手机号
- 金额信息：
  - 订单原价
  - 优惠金额（优惠券抵扣）
  - 实收金额（实际到账金额）
  - 退款金额

**订单的两个关键状态**：

1. **订单状态（Status）** - 描述订单的交易状态
   - 待付款：订单已创建，等待用户支付
   - 支付成功（pending）：用户已支付，等待后续操作（预约或直接完成）
   - 已完成：订单已完成（定金商品支付后直接完成；预约商品需所有预约完成）
   - 已退款：订单已全额退款
   - 部分退款：订单部分退款
   - 退款中：退款处理中
   - 退款失败：退款失败
   - 交易关闭：超时未支付，订单自动关闭

2. **服务状态（ServiceStatus）** - 描述预约商品的使用进度
   - 待预约（pending）：支付成功，等待用户预约课程
   - 已预约（success）：用户已预约课程，等待出行
   - 已出行（completed）：用户已完成所有课程
   - 空值：定金商品不使用此状态

### 2.2 子订单（SubOrder）

#### 2.2.1 为什么需要子订单？

子订单是用来**跟踪每次预约**的最小单位。

**拆分规则**：
- 根据商品的**总预约次数**拆分子订单
- 总预约次数 = 所有分类的预约次数（useTimes）之和
- 每个子订单对应一次预约机会

**示例1：单分类商品**
```
商品：单日营
├── 分类A：科技馆参观（可预约1次）

总预约次数 = 1次
拆分结果：1个子订单
```

**示例2：多分类商品**
```
商品：研学套餐
├── 分类A：科技馆参观（可预约2次）
├── 分类B：博物馆参观（可预约1次）
└── 分类C：自然探索（可预约1次）

总预约次数 = 2 + 1 + 1 = 4次
拆分结果：4个子订单

用户购买后：
- 父订单：总价300元
- 子订单1：75元，待预约
- 子订单2：75元，待预约
- 子订单3：75元，待预约
- 子订单4：75元，待预约

预约流程：
1. 第1次预约科技馆 → 子订单1状态改为"已预约"
2. 第2次预约科技馆 → 子订单2状态改为"已预约"
3. 第3次预约博物馆 → 子订单3状态改为"已预约"
4. 第4次预约自然探索 → 子订单4状态改为"已预约"
   → 父订单服务状态改为"已预约"
```

#### 2.2.2 子订单编号规则

**小程序订单**：
- 格式：`父订单号-1-序号`
- 示例：`abc123-1-1`, `abc123-1-2`, `abc123-1-3`

**抖音订单**：
- 父订单格式：`抖音订单号-序号`（每个券对应一个父订单）
- 子订单格式：`抖音订单号-序号-序号`
- 示例：
  - 父订单1：`dy123-1`（对应第1个券）
    - 子订单：`dy123-1-1`, `dy123-1-2`
  - 父订单2：`dy123-2`（对应第2个券）
    - 子订单：`dy123-2-1`, `dy123-2-2`

#### 2.2.3 金额分配规则

- 平均分配，最后一个子订单补齐差额
- 例如：总价100元，拆分3个子订单 → 33.33元、33.33元、33.34元

### 2.3 课程预约（CourseAppointment）

**预约记录包含的信息**：
- 订单信息：关联的订单编号
- 课程信息：课程名称、课程分类
- 时间信息：
  - 课程日期（如"2026-02-05"）
  - 时间段（如"15:30-17:00"）
- 学生信息：
  - 学生姓名、年龄、性别
  - 学生身份证号
- 家长信息：
  - 家长姓名、手机号
  - 是否陪同

**预约状态**：
- 已预约（success）：预约成功，等待出行
- 已完成（completed）：已完成课程
- 取消预约（cancel）：用户取消了预约

**合同状态**：
- 待签署：合同已生成，等待签署
- 签署中：用户正在签署合同
- 已签署：合同签署完成
- 已撤销：合同被撤销
- 已过期：合同已过期
- 已拒签：用户拒绝签署

### 2.4 商品（Good）

**商品的基本信息**：
- 商品名称
- 商品价格
- 商品库存（仅定金商品使用）
- 商品类型（预约商品 / 定金商品）
- 商品状态（正常 / 已下架）

**预约商品的结构**：

预约商品可以包含多个课程分类，每个分类可以独立预约：

```
示例：研学套餐（总预约次数 = 4次）
├── 分类1：科技馆参观
│   ├── 可预约次数：2次
│   └── 课程列表：[北京科技馆, 中国科技馆, ...]
├── 分类2：博物馆参观
│   ├── 可预约次数：1次
│   └── 课程列表：[故宫博物院, 国家博物馆, ...]
└── 分类3：自然探索
    ├── 可预约次数：1次
    └── 课程列表：[植物园, 动物园, ...]

用户购买后：
1. 系统自动拆分为4个子订单（2+1+1=4）
2. 预约科技馆第1次 → 消耗子订单1
3. 预约科技馆第2次 → 消耗子订单2
4. 预约博物馆 → 消耗子订单3
5. 预约自然探索 → 消耗子订单4
6. 所有4个子订单都完成后，订单状态变为"已完成"
```

## 3. 订单业务流程

### 3.1 小程序订单流程

#### 3.1.1 用户下单

**用户操作路径**：
1. 在小程序浏览商品
2. 选择商品，点击"立即购买"
3. 填写学生信息（姓名、年龄、性别、身份证等）
4. 填写家长信息（姓名、手机号）
5. 选择优惠券（可选）
6. 确认订单，点击"去支付"

**系统处理逻辑**：
1. 验证商品信息（价格、库存等）
2. 验证优惠券（是否有效、是否可用）
3. 计算订单金额（原价 - 优惠金额 = 实付金额）
4. 如果使用优惠券，锁定优惠券（防止重复使用）
5. 如果是定金商品，预扣库存
6. 创建订单，状态为"待付款"
7. 设置支付期限（30分钟内支付，超时自动关闭）
8. 调起微信支付

**特殊处理**：
- 如果创建订单失败，自动释放优惠券和库存
- 如果支付调起失败，订单仍然创建成功，用户可以稍后重新支付

#### 3.1.2 支付成功

**触发时机**：用户完成微信支付

**系统处理逻辑**：

**情况1：定金商品**
1. 更新订单状态为"已完成"
2. 服务状态为空（不使用）
3. 核销优惠券（状态从"锁定中"改为"已使用"）
4. 发送订单支付成功通知
5. **不拆分子订单**

**情况2：预约商品**
1. 更新订单状态为"支付成功（pending）"
2. 更新服务状态为"待预约（pending）"
3. 核销优惠券
4. **拆分子订单**（根据总预约次数）
5. 发送订单支付成功通知

**拆单示例**：
```
商品：研学套餐
- 分类A：可预约2次
- 分类B：可预约1次
总预约次数 = 3次

支付成功后：
- 父订单：abc123，300元，状态"支付成功"，服务状态"待预约"
- 自动创建3个子订单：
  - abc123-1-1：100元，服务状态"待预约"
  - abc123-1-2：100元，服务状态"待预约"
  - abc123-1-3：100元，服务状态"待预约"
```

#### 3.1.3 超时未支付

**触发时机**：创建订单后30分钟内未支付

**系统处理逻辑**：
1. 订单状态改为"交易关闭"
2. 释放优惠券（状态从"锁定中"改为"未使用"）
3. 回补库存（定金商品）

### 3.2 抖音订单流程

#### 3.2.1 抖音订单的特殊性

**与小程序的关键区别**：

1. **用户在抖音完成购买和支付**
2. **抖音使用"券"的概念**：
   - 每购买1件商品，抖音生成1张券（certificateId）
   - 券是唯一标识，用于退款等操作
3. **多件商品 = 多个券 = 多个父订单**：
   - 用户购买3件商品 → 抖音生成3张券
   - 系统创建3个父订单（每个券对应1个父订单）
   - 每个父订单再根据预约次数拆分子订单

**关键理解**：
```
用户在抖音购买：3件单日营商品
抖音生成：3张券（cert-1, cert-2, cert-3）

系统创建订单结构：
├── 父订单1（dy123-1，对应券cert-1）
│   ├── 子订单1-1（dy123-1-1）
│   ├── 子订单1-2（dy123-1-2）
│   └── 子订单1-3（dy123-1-3）
├── 父订单2（dy123-2，对应券cert-2）
│   ├── 子订单2-1（dy123-2-1）
│   ├── 子订单2-2（dy123-2-2）
│   └── 子订单2-3（dy123-2-3）
└── 父订单3（dy123-3，对应券cert-3）
    ├── 子订单3-1（dy123-3-1）
    ├── 子订单3-2（dy123-3-2）
    └── 子订单3-3（dy123-3-3）

说明：
- 用户购买3件商品，每件商品的预约次数是3次
- 所以总共有3个父订单，9个子订单
- 可以预约9次课程
```

#### 3.2.2 抖音订单创建流程

**触发时机**：抖音推送支付成功消息

**系统处理逻辑**：

**第1步：接收抖音推送**
```
抖音推送数据：
- 订单ID：dy123456
- 支付金额：297元
- 购买数量：3件
- 券列表：[cert-1, cert-2, cert-3]
```

**第2步：回查抖音订单详情**
- 确认订单真实性
- 获取商品信息
- 查询每张券的实收金额、优惠金额

**第3步：创建多个父订单**（每个券对应一个父订单）
```
父订单1：
- 订单号：dy123456-1
- 券ID：cert-1
- 订单价格：99元
- 状态：支付成功
- 服务状态：待预约

父订单2：
- 订单号：dy123456-2
- 券ID：cert-2
- 订单价格：99元
- 状态：支付成功
- 服务状态：待预约

父订单3：
- 订单号：dy123456-3
- 券ID：cert-3
- 订单价格：99元
- 状态：支付成功
- 服务状态：待预约
```

**第4步：每个父订单拆分子订单**

假设商品有3个预约次数，每个父订单拆分为3个子订单：
```
父订单1（dy123456-1）→ 拆分子订单：
- dy123456-1-1：33元
- dy123456-1-2：33元
- dy123456-1-3：33元

父订单2（dy123456-2）→ 拆分子订单：
- dy123456-2-1：33元
- dy123456-2-2：33元
- dy123456-2-3：33元

父订单3（dy123456-3）→ 拆分子订单：
- dy123456-3-1：33元
- dy123456-3-2：33元
- dy123456-3-3：33元
```

**金额计算**：
- 实收金额 = 实付金额 + 平台优惠 + 支付优惠
- 优惠金额 = 平台优惠 + 支付优惠

**示例**：
```
用户购买3件商品：
- 实付金额：297元
- 平台优惠：10元
- 支付优惠：5元
- 实收金额：297 + 10 + 5 = 312元

分配到每个父订单：
- 父订单1：实收104元（312/3，最后一个补齐差额）
- 父订单2：实收104元
- 父订单3：实收104元
```

#### 3.2.3 失败重试机制

**问题场景**：
抖音推送订单时，我们的系统可能因为网络、数据库等原因处理失败。

**解决方案**：
1. 失败时记录完整的请求数据到`async_task`表
2. 系统每小时自动重试失败的订单（最多重试3次）
3. 重试3次仍失败，发送飞书告警通知运营人员人工处理

### 3.3 订单状态流转图

```
【创建订单】
    ↓
待付款 (pending_payment) ← 30分钟支付期限
    ↓
    ├─→ [超时] → 交易关闭 (closed)
    └─→ [支付成功]
            ↓
            ├─→ [定金商品] → 已完成 (completed) [拆子订单]
            └─→ [预约商品] → 支付成功 (pending) + 服务状态：待预约
                              ↓
                          【拆分子订单】(根据总预约次数)
                              ↓
                          每个子订单：服务状态"待预约"
                              ↓
                          【用户预约课程】
                              ↓
                          子订单1：服务状态"已预约"
                              ↓
                          【课程结束】
                              ↓
                          子订单1：服务状态"已出行"
                              ↓
                          【所有子订单都已出行】
                              ↓
                          父订单：服务状态"已出行"
                              ↓
                          父订单：状态"已完成"

任何状态 → [申请退款] → 退款中 (refunding) 
                            ↓
                       [全额退款] → 已退款 (refunded)
                            ↓
                       [部分退款] → 部分退款 (partial_refunded)
```

## 4. 课程预约业务流程

### 4.1 预约前提条件

用户可以预约课程的条件：
1. 订单状态为"支付成功（pending）"
2. 服务状态为"待预约（pending）"或"已预约（success）"
3. 有可用的子订单（服务状态为"待预约"）
4. 商品包含该课程分类
5. 该分类的预约次数未用完

### 4.2 创建预约流程

**用户操作路径**：
1. 在"我的订单"中找到已支付的订单
2. 点击"预约课程"
3. 选择课程分类和具体课程
4. 选择课程日期和时间段
5. 确认学生和家长信息
6. 提交预约

**系统处理逻辑**：

**1. 验证预约条件**
- 订单是否已支付
- 是否还有可用的子订单（服务状态为"待预约"）
- 课程是否有库存
- 课程日期是否有效（不能预约今天或过去的日期）
- 该分类的预约次数是否已用完

**2. 创建预约记录**
- 保存预约信息（课程、日期、时间、学生信息等）
- 预约状态设为"已预约（success）"

**3. 更新子订单状态**
```
查找第一个服务状态为"待预约"的子订单
将该子订单的服务状态改为"已预约（success）"
```

**4. 检查订单完成情况**
```
统计所有子订单的服务状态：
- 如果所有子订单都已预约 → 父订单服务状态改为"已预约（success）"
- 如果还有待预约的子订单 → 父订单服务状态保持"待预约（pending）"
```

**5. 生成合同**
- 自动生成电子合同
- 发送合同签署链接给家长

**6. 发送通知**

- 发送运营通知（飞书）

**示例流程**：

```
用户购买商品，拆分为3个子订单：
- 子订单1：待预约
```

### 4.3 预约完成（课程结束）

**触发方式**：系统自动完成（每天0点执行一次）

**完成规则**：

**唯一规则：日期已过**
- 课程日期 < 今天
- 自动将预约状态改为"已完成"

**示例**：
```
今天：2026-02-06（凌晨0点执行定时任务）

案例1：昨天的课程
- 课程日期：2026-02-05
- 结果：自动完成（日期已过）

案例2：前天的课程
- 课程日期：2026-02-04
- 结果：自动完成（日期已过）

案例3：今天的课程
- 课程日期：2026-02-06
- 结果：不完成（日期未过）
- 说明：今天的课程要等到明天0点才会自动完成

案例4：未来的课程
- 课程日期：2026-02-10
- 结果：不完成（日期未过）
```

**注意事项**：
- 今天的课程不会在当天自动完成
- 需要等到第二天凌晨0点才会自动完成
- 例如：2026-02-05的课程，会在2026-02-06凌晨0点自动完成

**系统处理逻辑**：

**1. 更新预约状态**
- 预约状态改为"已完成（completed）"

**2. 更新子订单状态**
```
查找第一个服务状态为"已预约"的子订单
将该子订单的服务状态改为"已出行（completed）"
记录参营时间（如"2026年2月5日 15:30"）
```

**3. 检查订单完成情况**
```
统计所有子订单的服务状态：
- 如果所有子订单都已出行 → 父订单服务状态改为"已出行（completed）"
- 如果还有未出行的子订单 → 父订单服务状态保持"已预约（success）"
```

**示例流程**：
```
2026-02-11 00:00（第1次课程日期2026-02-10已过）
系统自动：
- 预约记录1状态改为"已完成"
- 子订单1服务状态改为"已出行"
- 子订单1参营时间记录为"2026-02-10 9:30"
- 父订单服务状态仍为"已预约"（还有2个子订单未出行）

2026-02-16 00:00（第2次课程日期2026-02-15已过）
系统自动：
- 预约记录2状态改为"已完成"
- 子订单2服务状态改为"已出行"
- 父订单服务状态仍为"已预约"（还有1个子订单未出行）

2026-02-21 00:00（第3次课程日期2026-02-20已过）
系统自动：
- 预约记录3状态改为"已完成"
- 子订单3服务状态改为"已出行"
- 父订单服务状态改为"已出行"（所有子订单都已出行）
- 检查所有预约是否完成 → 所有预约都完成 → 父订单状态改为"已完成"
```

### 4.4 取消预约流程

**用户操作路径**：
1. 在"我的预约"中找到预约记录
2. 点击"取消预约"

**系统处理逻辑**：

**1. 更新预约状态**

**2. 恢复子订单状态**


**示例**：

## 5. 退款业务流程

### 5.1 退款触发方式

**小程序订单退款**：
- 用户在小程序申请退款
- 管理员在后台操作退款

**抖音订单退款**：
- 用户在抖音申请退款
- 抖音平台审核通过后自动退款
- 系统每30分钟同步抖音退款状态

### 5.2 抖音退款同步流程

**触发方式**：定时任务（每30分钟执行一次）

**业务流程**：

**1. 查询退款券列表**
- 从抖音获取所有退款中的券

**2. 过滤已处理的退款**
```
查询数据库：
- 找出这些券对应的订单
- 过滤掉已经退款的订单
- 只处理新的退款
```

**3. 查询退款详情**
- 逐个查询退款券的详细信息
- 获取退款金额、退款时间等

**4. 更新父订单状态**
```
父订单：
- 订单状态改为"已退款"
- 记录退款金额
- 记录退款时间
```

**5. 分配退款金额到子订单**
- 按比例将退款金额分配到各个子订单
- 子订单根据退款金额自动判断状态：
  - 如果 退款金额 >= 订单金额 → 子订单状态改为"已退款"
  - 如果 0 < 退款金额 < 订单金额 → 子订单状态改为"部分退款"

### 5.3 退款金额分配规则

**为什么需要分配？**

一个父订单可能拆分为多个子订单，退款时需要明确每个子订单退了多少钱。

**分配算法**：

**按比例分配**：
```
退款比例 = 子订单价格 / 所有子订单总价格
子订单退款金额 = 父订单退款金额 × 退款比例
```

**示例1：完全按比例**
```
父订单退款金额：300元
子订单1价格：100元
子订单2价格：100元
子订单3价格：100元
总价格：300元

分配结果：
- 子订单1退款：300 × (100/300) = 100元
- 子订单2退款：300 × (100/300) = 100元
- 子订单3退款：300 × (100/300) = 100元
```

**示例2：补齐差额**
```
父订单退款金额：100元
子订单1价格：33元
子订单2价格：33元
子订单3价格：34元
总价格：100元

分配结果：
- 子订单1退款：33元（按比例计算）
- 子订单2退款：33元（按比例计算）
- 子订单3退款：34元（补齐差额，避免精度损失）
```

**特殊情况**：

由于抖音订单的退款金额可能包含平台优惠和支付优惠，所以子订单的退款金额可能大于子订单的价格。

```
示例：
子订单价格：30元
平台优惠：3元
支付优惠：2元
子订单退款金额：35元（30 + 3 + 2）

这是正常的，系统不会限制。
```

### 5.4 退款数据修复

**问题背景**：
早期系统可能存在退款金额分配不正确的情况，导致父订单和子订单的退款金额不一致。

**修复机制**：
- 提供 `FixRefundAmount` 接口（手动调用，非定时任务）
- 找出不一致的订单
- 重新分配退款金额

**检查条件**：
- 订单状态为"已退款"
- 支付时间在2026-01-01之后
- 所有子订单的退款金额之和 ≠ 父订单的退款金额

**使用场景**：
- 当发现退款金额不一致时，管理员手动调用此接口
- 接口会异步执行，避免超时

## 9. 核心业务规则

### 9.1 订单拆分规则

#### 9.1.1 小程序订单拆分

**触发条件**：
- 预约商品支付成功后
- 商品总预约次数 > 0

**拆分依据**：
- 总预约次数 = 所有分类的预约次数（useTimes）之和

**示例1：单分类商品**
```
商品：单日营（100元）
├── 分类A：科技馆参观（可预约1次）

总预约次数 = 1次

支付成功后：
- 父订单：abc123，100元
- 子订单1：abc123-1-1，100元，服务状态"待预约"

用户只能预约1次课程
```

**示例2：多分类商品**
```
商品：研学套餐（300元）
├── 分类A：科技馆参观（可预约2次）
├── 分类B：博物馆参观（可预约1次）
└── 分类C：自然探索（可预约1次）

总预约次数 = 2 + 1 + 1 = 4次

支付成功后：
```

#### 9.1.2 抖音订单拆分

**第一层拆分：按券创建父订单**

**触发条件**：
- 用户购买多件商品（多个券）

**拆分规则**：
- 每个券对应一个父订单

**示例**：
```
用户在抖音购买：3件单日营商品（每件100元）
抖音生成：3张券（cert-1, cert-2, cert-3）

系统创建3个父订单：
- 父订单1：dy123-1，100元，券cert-1
- 父订单2：dy123-2，100元，券cert-2
- 父订单3：dy123-3，100元，券cert-3
```

**第二层拆分：每个父订单按预约次数拆分子订单**

**拆分规则**：
- 与小程序订单相同
- 根据商品的总预约次数拆分

**完整示例**：
```
用户在抖音购买：3件单日营商品
商品预约次数：每件可预约3次（分类A×2 + 分类B×1）

拆分结果：
├── 父订单1（dy123-1，100元，券cert-1）
│   ├── 子订单1-1（dy123-1-1，33元）
│   ├── 子订单1-2（dy123-1-2，33元）
│   └── 子订单1-3（dy123-1-3，34元）
├── 父订单2（dy123-2，100元，券cert-2）
│   ├── 子订单2-1（dy123-2-1，33元）
│   ├── 子订单2-2（dy123-2-2，33元）
│   └── 子订单2-3（dy123-2-3，34元）
└── 父订单3（dy123-3，100元，券cert-3）
    ├── 子订单3-1（dy123-3-1，33元）
    ├── 子订单3-2（dy123-3-2，33元）
    └── 子订单3-3（dy123-3-3，34元）

总共：3个父订单，9个子订单
用户可以预约9次课程
```

**不拆分的情况**：
- 定金商品：不拆分，支付后直接完成
- 预约次数为0：不拆分

### 9.2 预约次数与分类规则

**基本概念**：
- 商品包含多个课程分类
- 每个分类有独立的预约次数限制
- 预约时消耗对应分类的次数

**重要说明**：
虽然商品有分类和预约次数限制，但系统**不会限制用户预约哪个分类**。

**实际逻辑**：
1. 根据总预约次数创建子订单
2. 用户预约任意分类的课程
3. 系统只检查：
   - 是否还有"待预约"的子订单
   - 课程是否有库存

**示例**：
```
商品：研学套餐
├── 分类A：科技馆参观（可预约2次）
├── 分类B：博物馆参观（可预约1次）
└── 分类C：自然探索（可预约1次）

总预约次数 = 4次
拆分为4个子订单

用户可以：
✓ 预约4次科技馆（虽然分类A只标注2次）
✓ 预约4次博物馆
✓ 预约2次科技馆 + 2次博物馆
✓ 任意组合，只要不超过4次

系统检查：
- 是否还有"待预约"的子订单？
- 如果有，允许预约
- 如果没有，提示"预约次数已用完"
```

### 9.3 退款金额分配规则

**原则**：退款金额按比例分配到各子订单

**公式**：
```
子订单退款金额 = 父订单退款金额 × (子订单价格 / 所有子订单总价格)
```

**示例1：均等分配**
```
父订单：总价300元，退款300元
子订单1：100元 → 退款 100元
子订单2：100元 → 退款 100元
子订单3：100元 → 退款 100元
```

**示例2：不均等分配**
```
父订单：总价100元，退款100元
子订单1：30元 → 退款 30元
子订单2：30元 → 退款 30元
子订单3：40元 → 退款 40元（补齐差额）
```

**示例3：包含优惠的退款**
```
父订单：
- 订单价格：100元
- 平台优惠：10元
- 支付优惠：5元
- 实收金额：115元
- 退款金额：115元

子订单分配：
- 子订单1：33元 → 退款 38元（33/100 × 115）
- 子订单2：33元 → 退款 38元
- 子订单3：34元 → 退款 39元

说明：子订单退款金额可以大于子订单价格
```

### 9.4 定金商品规则

**定金商品特点**：
1. 有库存限制
2. 支付后直接完成，不需要预约

**业务流程**：

**1. 下单时**
```
检查库存（库存 >= 购买数量）
预扣库存（使用乐观锁，防止超卖）
创建订单，状态为"待付款"
```

**2. 支付成功**
```
订单状态改为"已完成"
服务状态为空（不使用）
库存正式扣减
```

**3. 超时未支付**
```
订单状态改为"交易关闭"
回补库存
```

**4. 退款**
```
订单状态改为"已退款"
库存+1（恢复）
```

**应用场景**：
- 活动定金
- 占位费
- 报名费

### 9.5 支付期限规则

**规则**：
- 创建订单后30分钟内必须支付
- 超时未支付自动关闭订单

**倒计时显示**：
```
剩余支付时间：29分58秒
剩余支付时间：15分30秒
剩余支付时间：0分10秒
支付已超时，订单已关闭
```

**超时后处理**：
1. 订单状态改为"交易关闭"
2. 释放优惠券（改为"未使用"）
3. 回补库存（定金商品）
4. 用户需要重新下单

### 9.6 预约日期限制规则

**规则**：
- 不能预约今天或过去的日期
- 只能预约未来的日期

**示例**：
```
今天：2026-02-05

可以预约：
- 2026-02-06 ✓
- 2026-02-07 ✓
- 2026-03-01 ✓

不能预约：
- 2026-02-05 ✗（今天）
- 2026-02-04 ✗（过去）
- 2026-01-01 ✗（过去）
```

**原因**：
- 避免用户预约已经开始的课程
- 给系统留出准备时间（生成合同、安排座位等）

### A. 业务术语表

| 术语 | 说明 |
|-----|------|
| 父订单 | 用户下单时创建的订单。抖音多券订单中，每个券对应一个父订单 |
| 子订单 | 根据预约次数拆分出的订单，每个子订单对应一次预约机会 |
| 拆单 | 将父订单拆分为多个子订单的过程 |
| 总预约次数 | 商品所有分类的预约次数之和，决定拆分多少个子订单 |
| 预约商品 | 支付后需要预约课程的商品 |
| 定金商品 | 支付后直接完成的商品，不需要预约 |
| 分类预约次数（useTimes）| 商品分类可以预约的次数 |
| 券（certificateId）| 抖音订单中每件商品对应的凭证ID |
| 服务状态 | 预约商品的使用进度（待预约/已预约/已出行）|
| 核销 | 将优惠券状态从"锁定中"改为"已使用" |
| 实收金额 | 商家实际收到的金额（可能包含平台补贴）|
| 实付金额 | 用户实际支付的金额 |
| 优惠金额 | 平台优惠 + 支付优惠 |

### B. 常见问题FAQ

**Q1: 为什么抖音订单会创建多个父订单？**
A: 因为抖音使用"券"的概念，每购买1件商品生成1张券。系统为了方便管理退款（按券退款），每个券对应创建一个父订单。

**Q2: 子订单的数量如何确定？**
A: 子订单数量 = 商品的总预约次数 = 所有分类的预约次数之和。例如：分类A可预约2次，分类B可预约1次，总共拆分3个子订单。

**Q3: 用户必须按照分类的预约次数来预约吗？**
A: 不是的。虽然商品定义了分类和预约次数（如"科技馆2次，博物馆1次"），但系统不强制执行。用户可以预约任意分类的课程，只要有可用的子订单即可。

**Q4: 订单状态和服务状态有什么区别？**
A: 
- 订单状态：描述交易状态（待付款、已完成、已退款等）
- 服务状态：描述预约进度（待预约、已预约、已出行）
- 定金商品只有订单状态，没有服务状态

**Q5: 为什么退款金额可能大于订单金额？**
A: 因为退款金额包含平台优惠和支付优惠。例如：用户实付90元，平台补贴10元，退款时退100元。

**Q6: 预约记录什么时候自动变为"已完成"？**
A: 系统每天凌晨0点检查一次，当课程日期已过（课程日期 < 今天），自动改为"已完成"。注意：今天的课程不会在当天自动完成，需要等到第二天凌晨0点。

**Q7: 取消预约后还能重新预约吗？**
A: 可以。取消预约会恢复子订单为"待预约"状态，可以重新预约。

**Q8: 定金商品和预约商品的主要区别是什么？**
A:
- 定金商品：支付后直接完成，有库存限制，不需要预约
- 预约商品：支付后需要预约课程，根据预约次数拆分子订单，完成所有预约后才算完成

**Q9: 小程序订单和抖音订单的拆单有什么区别？**
A:
- 小程序：1个父订单 → 多个子订单（根据预约次数）
- 抖音：多个券 → 多个父订单（每个券1个） → 每个父订单拆分多个子订单

**Q10: 订单创建后多久必须支付？**
A: 30分钟内必须支付，超时订单会自动关闭。
