# 规划

## 当前项目现状

这份规划不是从零开始设想，而是基于当前项目已经存在的产品雏形继续往前推。

当前前端已经有以下核心入口：

- Dashboard
- Kanban
- Knowledge Base
- Skills
- MCP
- Automations
- Git
- Projects
- Tasks
- Business Lines

当前后端已经有以下核心模块：

- business-lines
- projects
- workflow-templates
- tasks
- artifacts
- project-context
- automations
- skills
- mcps
- git
- observability
- queue

这说明当前项目并不是一个单点 AI 工具，而已经具备企业内部 AI 工作台的基础轮廓。

### 当前项目最强的几个基础

#### 1. 任务执行和代码工作区已经深度结合

现有任务能力已经不只是创建任务记录，而是包含：

- execute / retry / repeat-node / approve / cancel
- workspace tree / file / preview
- git status / diff / artifacts / commit / push / merge / rebase
- terminal session
- logs / stream

这意味着工作台已经具备“真实执行”的基础，不应该把后续规划做成纯聊天产品。

#### 2. 项目知识库已经是现成能力

当前 Knowledge Base 已经支持：

- 项目文档树
- 文档读写
- 文档预览
- 项目内知识问答

因此后续“知识沉淀”不应理解为从零建设，而应理解为对现有知识库做结构化、检索质量和复利能力增强。

#### 3. Skills 和 MCP 已经是工作台级配置能力

当前项目已经支持：

- 业务线级能力管理
- 项目级本地配置导入
- Skills 管理
- MCP 管理
- 从业务线向项目复制能力

因此后续不需要先做一个抽象的“AI 执行能力市场”，而更适合继续强化业务线到项目的能力分发机制。

#### 4. 工作流和任务已经有产品承接面

当前项目不仅有 `tasks` 模块，还已经有 `workflow-templates`、`automations`、看板、任务详情等视图和模块。

这说明未来规划最合理的方向不是另起一套系统，而是在现有“任务 / 工作流 / 自动化”主线之上继续增强“需求进入后如何变成执行结果”。

## 当前主数据链判断

结合现有模块，当前项目已经隐含出一条比较清晰的主数据链：

`业务线 -> 项目 -> 知识库 / Skills / MCP / Git 上下文 -> 工作流模板 / 自动化 -> 任务 -> 工作区 / 产物 / 日志 -> 交付结果`

后续规划应该尽量沿着这条链补能力，而不是平行新开一批没有承接关系的大模块。

## 产品定位

目标产品定位为企业内部 AI 工作台，首批核心用户是业务研发团队。

核心价值不是做一个聊天入口，也不是先做一个开放式 AI 执行能力市场，而是让业务研发团队在统一工作台中，基于项目上下文、任务协同、工作流执行和 AI 能力，更快推进需求到交付。

一句话主线：

`输入一个模糊需求 -> 自动补全上下文 -> 拆成可执行单元 -> 生成工作流 -> 人机协同执行 -> 沉淀结果复用`

## 术语约定

为避免全文里“平台、工作台、agent、task、workflow、automation”混用，统一按以下口径理解：

- `AI 工作台`：产品本体，指企业内部统一承载需求、项目上下文、协作、执行、沉淀的工作入口。
- `工作流`：对一组执行步骤、依赖关系、串并行策略和确认点的编排结果。
- `任务`：工作流中的执行单元，或者单次执行形成的执行记录。
- `自动化`：预设的规则化触发能力，用于把固定场景快速转成可执行流程。
- `AI 执行能力`：泛指大模型、agent、CLI、脚本执行器等 AI 驱动执行能力。
- 代码模块名如 `tasks`、`workflow-templates`、`automations` 保留现有命名，不强行中文化。

## 基于当前项目的能力分层

### 1. 需求理解层

把“我想做什么”变成“系统理解这件事是什么、影响哪里、应该怎么做”。

这一层建议主要基于现有 `projects`、`project-context`、`knowledge-base`、`git` 能力继续增强。

核心能力：

- 需求入口工作台
- 需求补全
- 项目上下文理解
- 影响面分析
- 风险识别
- 历史方案召回

### 2. 执行编排层

把需求变成真正能跑的任务网络，而不是一串待办。

这一层建议主要基于现有 `workflow-templates`、`automations`、`tasks` 继续增强。

核心能力：

- 智能任务拆分
- 工作流自动生成
- 并行与串行策略
- 依赖关系管理
- 失败重试
- 回滚与重排

### 3. 协作交付层

让业务研发团队能稳定接住 AI 产出，并继续推进真实交付。

这一层建议主要基于现有 `tasks`、`artifacts`、`git`、`kanban` 继续增强。

核心能力：

- 人工确认点
- 多角色协同
- 任务状态透明
- 执行产物归档
- 审批机制
- 交付验收

### 4. 组织复利层

让一次执行沉淀成下次更强的基础设施。

这一层建议主要基于现有 `knowledge-base`、`skills`、`mcps`、`observability`、`business-lines` 继续增强。

核心能力：

- 知识沉淀
- 模板化工作流
- 组织最佳实践复用
- 消耗统计
- 效果评估
- 权限与治理

建议优先顺序：

`需求理解层 -> 执行编排层 -> 协作交付层 -> 组织复利层`

## 基于现有项目的需求演进

### 一、优先增强现有能力

这部分最适合优先做，因为项目里已经有模块和页面承接，投入产出比最高。

#### 1. 需求入口工作台

建议落点：

- 新增统一的需求入口，而不是让需求直接散落在任务创建里
- 绑定项目、业务线、仓库、模块，避免需求和实际执行对象脱节
- 支持结构化填写目标、背景、范围、验收标准、限制条件、期望产物
- 支持语音输入，把会议口述、临时想法快速转成需求草稿
- 自动读取项目知识库、历史任务、Git 变更、已有工作流模板
- 自动生成需求摘要和待确认问题
- 在输入区支持 `@ Skills`、`@ MCP`、`@ 命令`、`@ 知识` 等能力引用，减少需求录入和能力调用割裂
- 基于当前输入内容推荐追问，帮助用户快速补齐缺失上下文，而不是只返回一段静态表单
- 支持从知识库文档、聊天记录、外部链接、会议纪要快速导入需求草稿
- 支持把录入后的需求继续流转到补全、拆分、工作流生成，而不是停留在一个表单页面

这项能力落地后，可以成为“项目 -> 任务 / 工作流”的真正起点。

#### 2. 需求补全助手

建议基于现有 `project-context`、`knowledge-base`、`git` 做增强。

可做内容：

- 自动识别缺失信息，如目标不清、验收标准缺失、依赖系统未说明、上线范围不明确
- 自动列出需要确认的问题，并区分“必须确认后才能执行”和“可在执行中补充”两类
- 识别已有模块、接口、数据结构，输出“可能涉及的代码区域”和“可能复用的现有能力”
- 基于知识库、历史任务、Git 变更生成背景摘要，减少用户重复补充上下文
- 标记高风险改动点和跨层影响面，如数据库变更、接口兼容性、跨服务调用、权限逻辑变动
- 生成研发可执行版需求稿，结构至少包含目标、范围、非目标、验收标准、风险、依赖和建议推进方式
- 支持把补全结果一键转成任务拆分输入，而不是停留在一段说明文本

#### 3. 智能任务拆分 1.0

建议基于现有 `tasks` 和 `workflow-templates` 做，而不是单独再搞一套拆分系统。

拆分层级建议：

1. 需求
2. 子需求
3. 任务

同时支持：

1. 拆分建议
2. 人工确认
3. 依赖关系
4. 并行与串行策略
5. 回滚与重排

进一步可补：

- 给每个任务补充目标、输入、输出、完成定义，而不是只给一个标题
- 提供多模板拆分机制，针对通用前端开发、官网/活动页、Chrome 插件、安卓 APK、小程序等场景给出不同拆分骨架
- 标记哪些任务适合 AI 自动执行，哪些任务更适合人工处理
- 支持把拆分结果保存为可复用模板，供同类需求复用
- 支持人工拖拽调整顺序、合并任务、拆分任务、删除低价值任务
- 支持在拆分后直接生成负责角色建议和预估执行方式

#### 4. 智能创建工作流 1.0

建议直接复用现有 `workflow-templates` 和 `automations`，把“需求拆分结果 -> 工作流草稿”打通。

可做内容：

- 根据任务类型选择节点模板，例如分析类、实现类、测试类、文档类、发布类节点
- 支持基于交付类型选择工作流模板，如通用前端、产品官网、插件开发、移动端壳应用、小程序等，减少从零编排成本
- 自动生成串并行结构，并给出为什么串行、为什么并行的理由说明
- 自动补充依赖关系、前置输入和预期输出，避免节点之间只靠人工理解衔接
- 配置人工确认节点，如方案确认、代码评审、发布确认、异常接管
- 配置失败重试和中断点，支持节点级重试、局部回滚、从指定节点恢复执行
- 为节点预填执行配置，如使用的 AI 执行能力、工作目录、上下文来源、关联知识
- 支持生成工作流草稿后再人工调整，再一键进入执行

#### 5. 执行产物中心

当前项目已经有任务工作区、Git 产物、日志流，建议把这部分统一成更明确的工作台能力。

可做内容：

- PRD、方案稿、代码 patch、测试结果、日志统一展示，并按任务节点或执行阶段归档
- 产物版本管理，记录同一份产物在不同执行轮次中的变化
- 差异对比，支持查看方案差异、代码差异、文档差异和产物摘要变化
- 关键结论摘要，自动提取本次执行的结论、风险、未完成项和下一步建议
- 支持直接展示数据库查询结果、结构化校验结果和关键运行数据，方便在任务上下文里做验证和验收
- 从任务详情直接消费产物，减少用户在多个页面来回跳转
- 建立产物和任务、工作流、项目、知识库之间的双向关联
- 支持把高价值产物一键沉淀到知识库或模板库

#### 6. 项目级消耗统计

建议优先做成 `observability + 项目/任务维度聚合`，而不是只做全局调用统计。

可做内容：

- 按业务线、项目、工作流、任务、用户、AI 执行单元统计，支持横向对比
- 统计 token、成本、时长、成功率、平均重试次数、人工介入次数等核心指标
- 支持按时间维度查看趋势，如日、周、月使用变化
- 支持按任务阶段拆分消耗，定位是分析阶段贵，还是实现和测试阶段贵
- 高成本节点告警，帮助识别最消耗资源的节点或流程
- 低成功率工作流提醒，识别需要优化的工作流模板
- 支持成本预算、配额预警和超额提醒，服务企业内部治理

#### 7. AI 执行环境（Agent Harnesses）

这个方向是对的，但建议明确为“基于当前任务运行时的标准 AI 执行底座”。

可做内容：

- 标准 AI 执行运行环境，统一工作目录、上下文装载方式、日志采集和产物输出路径
- 支持“项目配置仓库 + 项目仓库”模式，把执行环境、工具链、默认能力和流程配置放在配置仓库中管理
- 支持通过 `git subtree` 等方式把项目仓装载到执行环境，降低多项目复用和环境初始化成本
- 常用 CLI / 工具接入，减少每个任务单独拼接执行能力的成本
- 统一执行协议，约束输入、输出、状态、错误、重试和中断语义
- 任务与执行环境绑定，保证任务可以复现执行，不因环境漂移导致结果不可追踪
- 和 Skills / MCP / 项目上下文联动，让执行前自动获得所需能力和上下文
- 支持不同执行模式，如只读分析、可编辑改造、发布前验证等
- 记录环境快照，便于故障排查、执行回放和产物审计

#### 8. 知识库增强，而不是重新做知识系统

当前知识库已经能读写和问答，后续更值得做的是：

- 文档分类和结构化归档，区分需求、设计、复盘、规范、操作手册等类型
- 和任务、工作流、产物双向关联，让用户能从知识找到执行，也能从执行回到知识
- 相似文档和历史方案推荐，减少团队重复写同类文档
- 复盘和设计结论自动入库，把一次执行真正沉淀为组织知识
- 支持重要知识的版本演进、过期提示和人工校正
- 支持把高质量任务产物一键提升为团队级或业务线级知识

### 二、中期差异化能力

这部分决定工作台是否只是“有很多页面”，还是开始真正懂项目、懂交付。

#### 1. 代码库上下文地图

建议落在现有 `project-context` 上扩展，而不是另起一个上下文系统。

可做内容：

- 自动识别模块边界，形成项目结构视图，而不是只展示文件树
- 识别服务或子系统依赖关系，帮助判断需求影响面和改动顺序
- 梳理核心领域对象、主数据模型和关键配置点，帮助 AI 理解业务语义
- 识别接口调用链和上下游依赖，避免改一处漏掉另一处
- 标记高频变更区域，识别最活跃、最容易产生耦合的代码区
- 标记风险热点区域，如历史故障集中区、复杂逻辑区、多人频繁修改区
- 支持给需求补全、任务拆分、工作流生成直接提供上下文输入

#### 2. 历史经验召回

建议打通知识库、历史任务、历史工作流、Git 记录。

可做内容：

- 相似需求推荐，帮助快速找到过去做过的同类事项
- 相似方案推荐，优先展示经过验证的历史设计和结论
- 相似代码改动推荐，关联到历史提交、分支差异、关键文件和改动模式
- 历史踩坑提示，提示过去出现过的设计失误、执行阻塞和返工原因
- 历史失败工作流告警，避免重复使用低质量流程
- 支持引用来源，让用户知道建议来自哪次任务、哪份文档、哪段变更
- 支持把高命中历史经验直接带入当前需求和任务上下文

#### 3. 评测中心

这项能力建议作为独立产品能力建设，不并入单纯的成本统计或组织级效果分析。

可做内容：

- 理想输出评测，针对需求补全、任务拆分、方案生成、文档生成等场景，用标准样本和期望答案评估输出质量
- 工作流评测，对一套工作流模板在不同需求样本下做批量回放，比较成功率、稳定性、耗时、成本和人工介入情况
- 轨迹评测，不只看最终结果，还看执行过程中用了哪些上下文、调用了哪些工具、在哪个节点产生偏差
- 评估器机制，支持规则型评估器、模型型评估器和人工标注评估器组合使用，而不是只靠单一打分方式
- 支持评测数据集、评测结果、评估器版本管理，保证优化前后可以做可追溯对比
- 支持把评测结果直接反馈给工作流模板、Skills、MCP、提示词和执行策略优化，形成闭环

#### 4. 工作流优化建议

建议基于现有工作流和任务执行数据做，而不是只靠 prompt 推断。

可做内容：

- 识别串行瓶颈，找出导致整体耗时最长的节点和等待链路
- 推荐并行化，指出哪些任务可以同时推进且不会引入明显冲突
- 推荐合并节点，减少过碎节点带来的切换成本和协作成本
- 推荐增加评审 / 测试关口，提升高风险流程的稳定性
- 识别低价值步骤，删除只是形式存在但不产生有效结果的节点
- 评估不同编排方案的成本、时长和风险差异，帮助用户选择
- 基于历史执行数据不断优化模板，而不是每次都从零建议

#### 5. 多人多 AI 协作模式

建议基于现有任务详情和工作流节点交互继续增强。

可做内容：

- 一个需求下挂多个 AI 执行单元，支持不同角色并行处理不同子任务
- 角色分工：分析、实现、测试、文档，不同角色使用不同上下文和执行权限
- 人和 AI 的交接点，明确哪些阶段必须人工确认、补充信息或接管处理
- 会话与任务绑定，保证沟通记录、决策记录和执行记录不脱节
- 冲突检测和结果合并，避免多个执行单元修改同一范围时互相覆盖
- 支持查看每个执行单元的职责、状态、产物和阻塞原因
- 支持在流程内调整分工，而不是只能在开始时一次性设定

#### 6. 验收与发布联动

建议从当前 `git` 和 `tasks` 延伸，不要让工作台停留在“生成结果”。

可做内容：

- 自动生成验收清单，并关联需求中的目标、范围和验收标准
- 自动关联测试结果，让验收不只依赖主观判断
- 自动输出发布说明，减少上线前重复整理信息的成本
- 对接 CI/CD、代码仓库、缺陷系统，打通执行结果到发布动作的链路
- 发布前风控提示，如未完成测试、未通过审批、存在高风险改动
- 支持记录“已合并 / 已发布 / 已回滚 / 待修复”等交付状态
- 支持对交付结果做复盘，反推需求质量和工作流质量

#### 7. Skills / MCP 分发与治理增强

当前项目已经有 Skills / MCP 管理能力，后续可继续增强：

- 业务线模板包，让业务线把共用能力打包分发给多个项目
- 项目初始化能力包，让新项目能快速获得默认能力集
- 不同提供方的兼容策略，减少不同执行环境之间的配置差异
- 项目本地修改与上游同步策略，明确哪些可以继承、哪些允许覆盖、哪些需要审批
- 使用频率和效果统计，识别哪些能力真正高频且有效
- 支持能力版本管理、灰度发布和回滚，降低变更风险
- 支持区分“推荐能力”“试验能力”“受限能力”，服务治理和推广

#### 8. 记忆系统

记忆不只是聊天记忆，而是组织和项目的执行记忆。

可做内容：

- 项目记忆，沉淀项目术语、常见模块、边界约定和关键背景
- 团队偏好记忆，记录团队对代码风格、流程偏好、审批方式的习惯
- AI 执行策略记忆，记录在什么场景下应该优先用什么执行方式
- 工作流模板记忆，把效果好的工作流沉淀为可复用模板
- 失败案例记忆，保留失败路径、错误原因和修复方式
- 支持按项目、业务线、团队粒度分别沉淀，不做一锅端的大记忆池
- 支持记忆的查看、修正、删除和版本管理，避免错误知识长期污染

### 三、长期组织化建设

目标是从团队工具升级为组织级 AI 工作基础设施。

#### 1. 知识沉淀

方向：

- 类似 spec 归档机制，把需求、方案、执行结果和复盘串成完整链路
- 沉淀历史设计、决策、执行结果，形成可被检索和复用的组织资产
- 支持知识分层，如项目级、团队级、业务线级、组织级
- 支持把高价值知识沉淀为模板、规范、最佳实践和标准流程
- 形成组织复利，让后续需求不再从零开始理解和执行

#### 2. 工作台治理中心

- 权限分级
- 数据隔离
- 模型使用策略
- 审计日志
- 合规策略
- 敏感信息保护
- 能力白名单和黑名单
- 高风险操作审批
- 项目级和业务线级配额控制

#### 3. 跨项目资源调度

- 多项目并发队列
- 高优任务抢占
- 成本预算控制
- 资源配额
- 峰值调度策略
- 不同任务类型的调度优先级
- 低价值任务延后执行策略
- 高峰时段的资源保护机制

#### 4. 效果评估体系

- 需求到交付周期缩短情况
- 哪类 AI 执行单元最有效
- 哪类工作流最稳定
- 哪些任务最适合自动化
- 自动化 ROI 排名

#### 5. 开放集成能力

- 接入更多 AI 执行 CLI / 模型提供方
- 接 GitLab、GitHub、Jira、飞书、企业微信
- 接内部研发平台
- 提供 API、SDK、Webhook
- 支持数据库、数据服务和查询代理接入，让任务执行和验收过程可以直接消费结构化数据
- 支持事件订阅和回调，方便接入外部流程
- 支持标准化能力接入规范，降低新增集成成本

#### 6. 远程控制

方向包括：

- 手机版
- 聊天机器人

更适合作为后期轻操作入口：

- 移动端审批
- 任务状态订阅
- 异常告警处理
- 快速触发标准工作流

## 需要补强但要结合现有模块做的需求

以下需求值得做，但都应该优先落在当前已有模块上，而不是新起一套系统。

### 1. 需求质量评分

自动判断一个需求是否已经足够进入拆分和执行，适合作为需求入口的前置关口。

### 2. 自动确认点设计

工作台需要自动识别哪些步骤必须人工确认，适合作为工作流生成时的默认策略。

### 3. 失败原因归因

工作流失败后，不只显示报错，还要归因到：

- 输入问题
- 上下文不足
- 工具能力不足
- 模型选择不合适
- 依赖顺序错误

### 4. 任务可执行性预测

在执行前判断哪些任务适合 AI 自动执行，哪些任务更适合直接交给人。

### 5. 结果可信度标记

每个输出给出可信度、证据来源、人工复核建议，降低企业场景中的使用风险。

### 6. 模板进化机制

高质量工作流、任务拆分方案、执行策略应能自动沉淀为组织模板。

### 7. 交付闭环追踪

需求不只追踪到“任务完成”，还要追踪：

- 是否合并代码
- 是否上线
- 是否通过验收
- 是否产生返工

## 当前建议优先级

如果只选一版真正能打的主线，建议优先做以下六项：

1. 需求入口工作台
2. 需求补全助手
3. 智能任务拆分 1.0
4. 智能创建工作流 1.0
5. 执行产物中心
6. 项目级消耗统计

这六项串起来后，可以先形成一个完整闭环：

`需求进入 -> 补全 -> 拆分 -> 工作流 -> 执行 -> 产物沉淀 -> 消耗复盘`

## 暂不优先

以下方向可以保留，但不建议在当前阶段优先投入。

### 1. 过早做开放式 AI 执行能力市场

当前项目已经有 Skills / MCP / 项目级能力管理，先把分发和治理做强，比先做市场更有价值。

### 2. 过早做全功能移动端

移动端更适合审批、告警、查看状态，不适合复杂编排。

### 3. 过早追求完全自治的 AI 执行

当前项目已经有 approve / retry / repeat-node 等机制，说明人工确认本来就是主流程的一部分。

### 4. 先做复杂记忆系统，后补执行链路

如果需求入口、拆分、工作流还不强，记忆系统价值会偏虚。

### 5. 把工作台做成泛聊天产品

当前项目最强的基础在任务、工作流、工作区、Git 和产物，不在聊天本身。

### 6. 过重的低代码编排器

当前更适合自动生成工作流草稿，再允许少量人工调整，而不是让用户从零搭复杂流程图。
