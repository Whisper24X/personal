# 规划

## 当前项目现状

这份规划不是从零开始设想，而是基于当前项目已经存在的产品雏形继续往前推。

当前前端已经有以下核心入口：

- Dashboard
- Kanban
- Knowledge Base
- Skills
- MCP
- Automations
- Git
- Projects
- Tasks
- Business Lines

当前后端已经有以下核心模块：

- business-lines
- projects
- workflow-templates
- tasks
- artifacts
- project-context
- automations
- skills
- mcps
- git
- observability
- queue

这说明当前项目并不是一个单点 AI 工具，而已经具备企业内部 AI 工作台的基础轮廓。

### 当前项目最强的几个基础

#### 1. 任务执行和代码工作区已经深度结合

现有任务能力已经不只是创建任务记录，而是包含：

- execute / retry / repeat-node / approve / cancel
- workspace tree / file / preview
- git status / diff / artifacts / commit / push / merge / rebase
- terminal session
- logs / stream

这意味着工作台已经具备“真实执行”的基础，不应该把后续规划做成纯聊天产品。

#### 2. 项目知识库已经是现成能力

当前 Knowledge Base 已经支持：

- 项目文档树
- 文档读写
- 文档预览
- 项目内知识问答

因此后续“知识沉淀”不应理解为从零建设，而应理解为对现有知识库做结构化、检索质量和复利能力增强。

#### 3. Skills 和 MCP 已经是工作台级配置能力

当前项目已经支持：

- 业务线级能力管理
- 项目级本地配置导入
- Skills 管理
- MCP 管理
- 从业务线向项目复制能力

因此后续不需要先做一个抽象的“Agent 市场”，而更适合继续强化业务线到项目的能力分发机制。

#### 4. Workflow 和 Task 已经有产品承接面

当前项目不仅有 task，还已经有 workflow-templates、automations、kanban、task detail 等视图和模块。

这说明未来规划最合理的方向不是另起一套系统，而是在现有 Task / Workflow / Automation 主线之上继续增强“需求进入后如何变成执行结果”。

## 当前主数据链判断

结合现有模块，当前项目已经隐含出一条比较清晰的主数据链：

`业务线 -> 项目 -> 知识库 / Skills / MCP / Git 上下文 -> Workflow Template / Automation -> Task -> Workspace / Artifact / Log -> 交付结果`

后续规划应该尽量沿着这条链补能力，而不是平行新开一批没有承接关系的大模块。

## 产品定位

目标产品定位为企业内部 AI 工作台，首批核心用户是业务研发团队。

核心价值不是做一个聊天入口，也不是先做一个开放式 agent 市场，而是让业务研发团队在统一工作台中，基于项目上下文、任务协同、工作流执行和 AI 能力，更快推进需求到交付。

一句话主线：

`输入一个模糊需求 -> 自动补全上下文 -> 拆成可执行单元 -> 生成工作流 -> 人机协同执行 -> 沉淀结果复用`

## 基于当前项目的能力分层

### 1. 需求理解层

把“我想做什么”变成“系统理解这件事是什么、影响哪里、应该怎么做”。

这一层建议主要基于现有 `projects`、`project-context`、`knowledge-base`、`git` 能力继续增强。

核心能力：

- 需求 Intake 工作台
- 需求补全
- 项目上下文理解
- 影响面分析
- 风险识别
- 历史方案召回

### 2. 执行编排层

把需求变成真正能跑的任务网络，而不是一串待办。

这一层建议主要基于现有 `workflow-templates`、`automations`、`tasks` 继续增强。

核心能力：

- 智能任务拆分
- 工作流自动生成
- 并行与串行策略
- 依赖关系管理
- 失败重试
- 回滚与重排

### 3. 协作交付层

让业务研发团队能稳定接住 AI 产出，并继续推进真实交付。

这一层建议主要基于现有 `tasks`、`artifacts`、`git`、`kanban` 继续增强。

核心能力：

- 人工确认点
- 多角色协同
- 任务状态透明
- 执行产物归档
- 审批机制
- 交付验收

### 4. 组织复利层

让一次执行沉淀成下次更强的基础设施。

这一层建议主要基于现有 `knowledge-base`、`skills`、`mcps`、`observability`、`business-lines` 继续增强。

核心能力：

- 知识沉淀
- 模板化 workflow
- 组织最佳实践复用
- 消耗统计
- 效果评估
- 权限与治理

建议优先顺序：

`需求理解层 -> 执行编排层 -> 协作交付层 -> 组织复利层`

## 基于现有项目的需求演进

### 一、优先增强现有能力

这部分最适合优先做，因为项目里已经有模块和页面承接，投入产出比最高。

#### 1. 需求 Intake 工作台

建议落点：

- 新增统一的需求入口，而不是让需求直接散落在 task 创建里
- 绑定项目、业务线、仓库、模块
- 自动读取项目知识库、历史任务、Git 变更、已有 workflow template
- 自动生成需求摘要和待确认问题

这项能力落地后，可以成为 `Projects -> Tasks / Workflow` 的真正起点。

#### 2. 需求补全助手

建议基于现有 `project-context`、`knowledge-base`、`git` 做增强。

可做内容：

- 自动识别缺失信息
- 自动列出需要确认的问题
- 识别已有模块、接口、数据结构
- 标记高风险改动点和跨层影响面
- 生成研发可执行版需求稿

#### 3. 智能任务拆分 1.0

建议基于现有 `tasks` 和 `workflow-templates` 做，而不是单独搞一套拆分系统。

拆分层级建议：

1. 需求
2. 子需求
3. 任务

同时支持：

1. 拆分建议
2. 人工确认
3. 依赖关系
4. 并行与串行策略
5. 回滚与重排

#### 4. 智能创建工作流 1.0

建议直接复用现有 `workflow-templates` 和 `automations`，把“需求拆分结果 -> workflow 草稿”打通。

可做内容：

- 根据任务类型选择节点模板
- 自动生成串并行结构
- 配置人工确认节点
- 配置失败重试和中断点
- 一键进入执行

#### 5. 执行产物中心

当前项目已经有 task workspace、git artifact、日志流，建议把这部分统一成更明确的产品能力。

可做内容：

- PRD、方案稿、代码 patch、测试结果、日志统一展示
- 产物版本管理
- 差异对比
- 关键结论摘要
- 从 Task Detail 直接消费产物

#### 6. 项目级消耗统计

建议优先做成 `observability + 项目/任务维度聚合`，而不是只做全局调用统计。

可做内容：

- 按业务线、项目、workflow、任务、用户、AI 执行单元统计
- token、成本、时长、成功率
- 高成本节点告警
- 低成功率 workflow 提醒

#### 7. AI 执行环境（Agent Harnesses）

这个方向是对的，但建议明确为“基于当前 task runtime 的标准 AI 执行底座”。

可做内容：

- 标准 AI / agent 运行环境
- 常用 CLI / 工具接入
- 统一执行协议
- 任务与执行环境绑定
- 和 Skills / MCP / 项目上下文联动

#### 8. 知识库增强，而不是重新做知识系统

当前知识库已经能读写和问答，后续更值得做的是：

- 文档分类和结构化归档
- 和任务、workflow、产物双向关联
- 相似文档和历史方案推荐
- 复盘和设计结论自动入库

### 二、中期差异化能力

这部分决定工作台是否只是“有很多页面”，还是开始真正懂项目、懂交付。

#### 1. 代码库上下文地图

建议落在现有 `project-context` 上扩展，而不是另起一个上下文系统。

可做内容：

- 自动识别模块边界
- 服务或子系统依赖关系
- 核心领域对象
- 接口调用链
- 高频变更区域
- 风险热点区域

#### 2. 历史经验召回

建议打通知识库、历史任务、历史 workflow、Git 记录。

可做内容：

- 相似需求推荐
- 相似方案推荐
- 相似代码改动推荐
- 历史踩坑提示
- 历史失败 workflow 告警

#### 3. 工作流优化建议

建议基于现有 workflow 和 task 执行数据做，而不是只靠 prompt 推断。

可做内容：

- 识别串行瓶颈
- 推荐并行化
- 推荐合并节点
- 推荐增加 review / test gate
- 识别低价值步骤

#### 4. 多人多 AI 协作模式

建议基于现有 Task Detail 和 Workflow 节点交互继续增强。

可做内容：

- 一个需求下挂多个 AI 执行单元
- 角色分工：分析、实现、测试、文档
- 人和 AI 的交接点
- 会话与任务绑定
- 冲突检测和结果合并

#### 5. 验收与发布联动

建议从当前 `git` 和 `tasks` 延伸，不要让工作台停留在“生成结果”。

可做内容：

- 自动生成验收清单
- 自动关联测试结果
- 自动输出发布说明
- 对接 CI/CD、代码仓库、缺陷系统
- 发布前风控提示

#### 6. Skills / MCP 分发与治理增强

当前项目已经有 Skills / MCP 管理能力，后续可继续增强：

- 业务线模板包
- 项目初始化能力包
- 不同 provider 的兼容策略
- 项目本地修改与上游同步策略
- 使用频率和效果统计

#### 7. 记忆系统

记忆不只是聊天记忆，而是组织和项目的执行记忆。

可做内容：

- 项目记忆
- 团队偏好记忆
- AI 执行策略记忆
- workflow 模板记忆
- 失败案例记忆

### 三、长期组织化建设

目标是从团队工具升级为组织级 AI 生产基础设施。

#### 1. 知识沉淀

方向：

- 类似 spec 归档机制
- 沉淀历史设计、决策、执行结果
- 形成组织复利

#### 2. 工作台治理中心

- 权限分级
- 数据隔离
- 模型使用策略
- 审计日志
- 合规策略
- 敏感信息保护

#### 3. 跨项目资源调度

- 多项目并发队列
- 高优任务抢占
- 成本预算控制
- 资源配额
- 峰值调度策略

#### 4. 效果评估体系

- 需求到交付周期缩短情况
- 哪类 AI 执行单元最有效
- 哪类 workflow 最稳定
- 哪些任务最适合自动化
- 自动化 ROI 排名

#### 5. 开放集成能力

- 接入更多 agent CLI / 模型提供方
- 接 GitLab、Jira、飞书、企业微信
- 接内部研发平台
- 提供 API、SDK、Webhook

#### 6. 远程控制

方向包括：

- 手机版
- 聊天 bot

更适合作为后期轻操作入口：

- 移动端审批
- 任务状态订阅
- 异常告警处理
- 快速触发标准 workflow

## 需要补强但要结合现有模块做的需求

以下需求值得做，但都应该优先落在当前已有模块上，而不是新起一套系统。

### 1. 需求质量评分

自动判断一个需求是否已经足够进入拆分和执行，适合作为 Intake 的前置 gate。

### 2. 自动确认点设计

工作台需要自动识别哪些步骤必须人工确认，适合作为 workflow 生成时的默认策略。

### 3. 失败原因归因

workflow 失败后，不只显示报错，还要归因到：

- 输入问题
- 上下文不足
- 工具能力不足
- 模型选择不合适
- 依赖顺序错误

### 4. 任务可执行性预测

在执行前判断哪些任务适合 AI 自动执行，哪些任务更适合直接交给人。

### 5. 结果可信度标记

每个输出给出可信度、证据来源、人工复核建议，降低企业场景中的使用风险。

### 6. 模板进化机制

高质量 workflow、任务拆分方案、执行策略应能自动沉淀为组织模板。

### 7. 交付闭环追踪

需求不只追踪到“任务完成”，还要追踪：

- 是否合并代码
- 是否上线
- 是否通过验收
- 是否产生返工

## 当前建议优先级

如果只选一版真正能打的主线，建议优先做以下六项：

1. 需求 Intake 工作台
2. 需求补全助手
3. 智能任务拆分 1.0
4. 智能创建工作流 1.0
5. 执行产物中心
6. 项目级消耗统计

这六项串起来后，可以先形成一个完整闭环：

`需求进入 -> 补全 -> 拆分 -> workflow -> 执行 -> 产物沉淀 -> 消耗复盘`

## 暂不优先

以下方向可以保留，但不建议在当前阶段优先投入。

### 1. 过早做开放 Agent 市场

当前项目已经有 Skills / MCP / 项目级能力管理，先把分发和治理做强，比先做市场更有价值。

### 2. 过早做全功能移动端

移动端更适合审批、告警、查看状态，不适合复杂编排。

### 3. 过早追求完全自治 Agent

当前项目已经有 approve / retry / repeat-node 等机制，说明人工确认本来就是主流程的一部分。

### 4. 先做复杂记忆系统，后补执行链路

如果 Intake、拆分、workflow 还不强，记忆系统价值会偏虚。

### 5. 把工作台做成泛聊天产品

当前项目最强的基础在 Tasks、Workflow、Workspace、Git、Artifacts，不在聊天本身。

### 6. 过重的低代码编排器

当前更适合自动生成 workflow 草稿，再允许少量人工调整，而不是让用户从零搭复杂流程图。
