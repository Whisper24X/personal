# Competitive Product Research

> 调研时间：2026-03-24  
> 调研对象：AINative 当前能力边界下，面向“AI 应用开发 / AI 执行工作台 / Agentic IDE”的代表性产品  
> 结论口径：优先基于官方公开资料，其次结合当前项目现状进行推断；凡无法从公开资料直接确认的点，明确标注为“待试用验证”

## 1. 调研目标

这份调研要解决的不是“要不要做 AI 产品”这个问题，而是更具体的三个产品判断：

- 在当前 AI 应用开发与 AI 编程赛道里，我们应该切入哪一层。
- 我们下一阶段最值得优先建设的能力是什么。
- 哪些能力虽然热，但不适合当前项目阶段跟进。

目标读者主要是：

- 产品：判断产品定位、差异化和版本优先级。
- 设计：判断核心工作流、页面组织和协作方式。
- 技术：判断我们应该强化哪些底层能力边界。
- 商业：判断我们更像卖“工具席位”、还是卖“企业工作台能力”。

期望输出的决策：

- 是否继续沿“企业内部 AI 工作台”方向深化，而不是转成通用聊天或单点 AI Coding 产品。
- 先做“需求进入 -> 拆分 -> 执行 -> 沉淀”的主链路，还是先做模板商城、页面搭建器、移动端生成等外围能力。
- 明确不优先投入的方向，避免被热点牵着走。

## 2. 调研范围与方法

### 2.1 研究范围

本次重点观察两类产品。

在线产品：

- 扣子编程 / 扣子开发平台 / 扣子罗盘
- 飞书妙搭
- 搭叩
- Manus
- Atoms

桌面应用：

- Cursor
- Windsurf

补充说明：

- 在线产品更适合看“从想法到可运行应用”的闭环能力。
- 桌面应用更适合看“面向真实代码仓库的开发体验”和“Agent 与 IDE 的结合方式”。
- 飞书系产品的公开能力分布在妙搭、Aily、应用引擎、集成平台等多个产品中。本文以“妙搭”为主样本，但在涉及生态能力时会参考飞书系整体能力做辅助判断。

### 2.2 样本选择标准

- 与我们的目标用户重合：业务研发团队、数字化团队、AI 应用搭建者。
- 产品成熟度较高：已有公开文档、官网或持续迭代迹象。
- 覆盖不同范式：低代码/零代码、AI 全栈应用生成、异步 Agent、Agentic IDE。
- 能反映真实竞争压力：不只看“会不会写代码”，更看“能不能交付真实结果”。

### 2.3 调研方法

- 阅读官网、帮助中心、定价页、产品文档。
- 对比公开描述中的功能闭环：输入方式、上下文、执行方式、输出形态、协作、评测、部署。
- 结合当前项目代码和已有规划文档，判断哪些能力与我们现有基础匹配，哪些能力需要重建设。

### 2.4 我们的当前基线

这份调研不是脱离现状做抽象对比。结合当前项目已有页面、模块和规划文档，AINative 已具备以下基础：

- 前端已有 Dashboard、Kanban、Knowledge Base、Skills、MCP、Automations、Git、Projects、Tasks、Business Lines 等入口。
- 后端已有 `projects`、`tasks`、`workflow-templates`、`automations`、`project-context`、`skills`、`mcps`、`git`、`observability` 等模块。
- 已有规划文档已经明确产品更像“企业内部 AI 工作台”，而不是纯聊天入口或单点编码工具。

因此，本次调研的核心不是寻找一个“照搬对象”，而是判断：

- 我们应该吸收竞品的哪一段工作流设计。
- 我们应该避免被哪些产品形态带偏。

## 3. 结论摘要

### 3.1 核心发现

#### 核心发现 1：市场已经从“AI 回答问题”进入“AI 直接产出可运行结果”

头部产品不再停留在聊天问答，而是不断往以下方向推进：

- 直接生成应用原型、页面或全栈应用。
- 直接接入数据库、存储、支付、GitHub 等外部能力。
- 在云端或独立沙箱中异步执行长任务。
- 用 Agent 帮用户完成调研、构建、调优、部署。

这意味着用户评价一个产品，不再只看模型回答质量，而更看：

- 能不能交付结果。
- 能不能连接真实上下文。
- 能不能把结果继续纳入团队协作流程。

#### 核心发现 2：强产品已经在争夺“完整闭环”，但大多数只吃到了闭环的一部分

当前赛道里几类产品各自有明显强项：

- 扣子、飞书妙搭、Atoms：更强在“从需求到应用”的生成与托管。
- Manus、搭叩：更强在异步 Agent、外部连接和长任务执行。
- Cursor、Windsurf：更强在真实代码仓库里的开发效率。

但普遍短板也很明显：

- 在线产品大多缺少企业级项目管理、任务承接、审批确认、交付沉淀。
- 桌面产品大多缺少业务上下文、组织协作、任务编排、知识复利。
- 很多产品强调“生成”，但弱于“治理、透明和复盘”。

#### 核心发现 3：我们的天然切入点不是再做一个 IDE，也不是再做一个聊天壳

结合当前项目现状，我们最有机会的不是复制 Cursor 或 Manus，而是把已有模块真正串成一条主链路：

`需求 -> 项目上下文 -> 任务拆分 -> 工作流生成 -> AI/人工协同执行 -> Git/产物沉淀 -> 评测与复用`

这条链路在现有竞品中并没有被完整做好：

- 在线产品强在“造应用”，但普遍弱在“真实项目交付工作台”。
- IDE 产品强在“改代码”，但普遍弱在“企业内部需求到交付的全过程”。

### 3.2 对我们的直接启发

- 我们应该继续做“企业内部 AI 工作台”，而不是转成通用 AI IDE。
- 我们应该优先补齐“需求补全、任务拆分、工作流草稿、执行产物、评测与观察”。
- 我们可以吸收“异步 Agent”“云端执行”“可视化预览”“数据库/存储托管”“协作者并行开发”等机制，但不应让产品核心退化成单纯页面生成器。

### 3.3 建议优先级

- `P0`：需求入口工作台、AI 补全、任务拆分、工作流草稿、执行产物中心、基础评测/观测。
- `P1`：异步云端 Agent、运行通知、可视化预览、轻量数据应用承接、多人协作开发。
- `P2`：移动端/小程序输出、模板商城、对外分发生态。

## 4. 市场格局概览

### 4.1 赛道分层

当前赛道可以粗分成四层：

#### 第一层：AI 应用生成平台

代表产品：

- 扣子编程
- 飞书妙搭
- Atoms

特点：

- 用户用自然语言描述需求。
- 平台自动生成页面、逻辑、数据结构或完整应用。
- 常见卖点是“更快上线”“更低门槛”“托管更完整”。

#### 第二层：异步 Agent 执行平台

代表产品：

- Manus
- 搭叩

特点：

- 更强调长任务执行、外部工具调用、独立运行环境、并行任务。
- 适合做研究、批量处理、系统搭建、长链路任务推进。

#### 第三层：Agentic IDE

代表产品：

- Cursor
- Windsurf

特点：

- 更强调在真实代码仓库中的编码效率。
- 强项是本地代码理解、代码修改、调试、预览、提交。
- 产品中心依然是“开发者个人或小团队的编码体验”。

#### 第四层：AgentOps / 评测与运维层

代表产品：

- 扣子罗盘

特点：

- 聚焦 trace、调试、评测、观测、调优。
- 不直接解决“从需求到交付”的全部问题，但对稳定运行和持续优化越来越关键。

### 4.2 主要差异化路径

目前主流产品的差异化大致沿以下五条路径展开：

- 生态绑定：绑定飞书、火山、GitHub、数据库、支付、MCP 等生态。
- 工程深度：是否只是会生成页面，还是能生成后端、部署和数据层。
- 执行方式：同步对话式，还是支持异步、并行、云端沙箱。
- 协作治理：是否支持多人协作、权限、审批、日志、观测、评测。
- 使用门槛：偏业务人员、偏独立开发者，还是偏研发团队。

### 4.3 市场空白点与机会点

当前最值得关注的空白不是“再做一个能写代码的 Agent”，而是：

- 把企业真实需求承接进来，而不是只接一句 prompt。
- 把 AI 执行结果放进任务、工作流、Git、知识库、产物体系里。
- 让多人协作、审批确认、失败恢复、观察评测成为工作流的一部分。

这恰好与 AINative 已有能力边界吻合。

## 6. 详细竞品分析

### 6.1 在线产品

#### 6.1.1 扣子编程 / 扣子开发平台 / 扣子罗盘

- 产品定位：AI 驱动的应用开发平台，覆盖智能体、工作流、技能、网页应用、移动应用，并用罗盘承接 AgentOps 能力。
- 目标用户：开发者、AI 应用搭建者、希望快速落地 AI 应用的企业团队。
- 核心使用场景：
  - 通过自然语言快速生成 AI 应用。
  - 通过可视化或代码方式继续调优应用。
  - 对上线后的 Agent 做调试、评测、观测和提示词优化。
- 核心功能：
  - 支持智能体、工作流、技能、移动应用、网页应用等多种形态。
  - 提供 Web 代码编辑器、终端、对话区、预览与部署。
  - 提供托管的模型、数据库、存储、插件等集成能力。
  - 罗盘提供 trace、在线评测、观测、自动化调优能力。
- 差异化卖点：
  - 产品面广，覆盖“开发 -> 部署 -> 运维优化”。
  - AI 编程和低代码范式并存，适配不同门槛用户。
  - 插件和集成生态较丰富。
- 产品体验亮点：
  - 从一句需求到“可预览应用”的路径很短。
  - 在应用开发过程中，代码编辑、终端、对话修改形成闭环。
  - 罗盘把 Agent 评测和运维从“额外系统”前置成产品的一部分。
- 产品体验问题：
  - 产品线较多，认知成本偏高，新用户不容易快速理解各子产品边界。
  - 计费体系以积分和按量结合，理解成本较高。
  - 更偏“把应用做出来”，对企业内部任务承接、审批协作、交付管理支持不突出。
- 商业模式 / 定价：个人版免费+付费套餐，企业版采用包年包月+按量混合计费。
- 我们可借鉴点：
  - 同一平台承接多种交付形态，而不是只做聊天或只做页面。
  - 开发环境、预览、部署、运维调优尽量打通。
  - AgentOps 不应等产品做大后再补，至少要先把 trace、评测、用量与结果观察纳入工作流。
- 不建议照搬点：
  - 不要一开始就铺太宽的消费级创作场景。
  - 不要让计费模型侵入产品理解，影响上手清晰度。

#### 6.1.2 飞书妙搭

- 产品定位：面向企业场景的 AI 原生系统搭建工具，更偏“用对话搭业务系统”。
- 目标用户：企业老板、业务负责人、数字化团队、非专业开发者。
- 核心使用场景：
  - 业务系统原型验证。
  - 轻量应用、活动页、官网、互动页面快速搭建。
  - 企业内部系统的快速开发与迭代。
- 核心功能：
  - 灵感探索模式：快速生成原型和页面。
  - 应用模式：继续补数据库、AI 插件等能力。
  - 开发计划：先生成用户故事、页面结构、开发计划，再执行任务。
  - 邀请协作者：多人实时协作开发，消息进入队列后由 Agent 顺序执行。
  - 飞书消息通知、运营报表、日志与上线后管理能力。
- 差异化卖点：
  - 强企业场景和组织协作属性。
  - 不是单次生成，而是把“开发计划、协作者、通知、运营”一起纳入。
  - 与飞书内部协作、权限和数据体系天然接近。
- 产品体验亮点：
  - 双模式切换合理，既能快速出结果，也能继续进深。
  - “开发计划 + 异步通知”的设计适合业务方等待结果。
  - 多人协作开发的产品设计很贴近真实产研流程。
- 产品体验问题：
  - 从公开资料看，更强在企业轻应用/业务系统，不是为复杂工程研发交付而设计。
  - 深度代码仓库、Git 流程、开发者工作区能力公开信息相对有限。
  - 产品边界与飞书生态绑定很深，跨生态扩展性不是其主诉求。
- 商业模式 / 定价：公开资料更偏企业售卖，具体价格未清晰公开。
- 我们可借鉴点：
  - 把“需求确认 -> 开发计划 -> 异步执行 -> 通知回收”设计成显性流程。
  - 引入多人协作、权限角色和消息队列，而不是默认单人和单线程交互。
  - 上线后的日志、报表、运维数据要有承接面。
- 不建议照搬点：
  - 不要把产品过度收敛成内部表单/页面系统搭建器。
  - 不要依赖单一协同生态做壁垒。

#### 6.1.3 搭叩

- 产品定位：异步 Agent 产品，提供独立运行环境的一站式研发工具。
- 目标用户：需要长任务执行、研发协助、报告生成的创作者和研发人员。
- 核心使用场景：
  - 端到端的软件研发任务处理。
  - 产品调研与分析。
  - 专业报告生成。
- 核心功能：
  - 独立云端沙箱环境。
  - 异步执行任务。
  - 批量并行运行任务。
  - 输出研发结果和专业报告。
- 差异化卖点：
  - 把“异步”和“云端独立环境”作为核心卖点。
  - 不是单次问答，而是让 Agent 在独立环境里持续完成任务。
- 产品体验亮点：
  - 很符合长任务、批处理、多人等待结果的使用方式。
  - 云端沙箱天然利于隔离环境和复现实验。
- 产品体验问题：
  - 公开资料较少，产品透明度与能力边界不够清晰。
  - 对协作治理、权限、评测、项目管理的公开描述不足。
  - 更像执行引擎，尚未看到完整的企业工作台形态。
- 商业模式 / 定价：公开信息不足，待进一步试用验证。
- 我们可借鉴点：
  - 异步任务队列。
  - 批量并行执行。
  - 让任务结果以报告和结构化产物回流，而不是只回一句总结。
- 不建议照搬点：
  - 不要把产品做成完全黑盒的“提交需求 -> 等结果”。
  - 对企业用户来说，透明度、可控性、接管能力必须更强。

#### 6.1.4 Manus

- 产品定位：通用 AI Agent 平台，逐步向外部工具连接、网站构建和长任务执行扩展。
- 目标用户：知识工作者、独立构建者、希望让 Agent 直接做事的用户。
- 核心使用场景：
  - 连接外部系统完成任务。
  - 使用并行 Agent 做大规模研究。
  - 构建网站并与 GitHub 同步。
- 核心功能：
  - Connectors 统一接入第三方数据和 API，支持 MCP。
  - 支持 GitHub 双向同步。
  - 支持数据库类连接器，自然语言查询外部数据库。
  - Wide Research 支持并行多 Agent 研究。
  - 网站构建与托管采用订阅 + 用量计费。
- 差异化卖点：
  - 外部连接能力做得比较系统化。
  - 并行研究与长任务执行的产品叙事清晰。
  - 把“通用 Agent + 实际外部执行”结合起来。
- 产品体验亮点：
  - Connectors 把工具、数据和权限控制统一抽象掉，降低切换成本。
  - GitHub 双向同步很适合“Web 构建器 + 代码仓库”混合使用。
  - 并行研究机制很适合大样本调研类任务。
- 产品体验问题：
  - 产品边界很宽，软件研发、研究执行、网站构建混在一起，主心智容易发散。
  - 更适合通用 Agent 任务，不一定适合复杂企业研发协作。
  - 以连接器和用量为核心时，成本预估与治理需要更强支持。
- 商业模式 / 定价：存在免费档，部分能力和网站托管按使用量计费。
- 我们可借鉴点：
  - Connectors / MCP 的统一能力层。
  - 并行研究与异步任务组织方式。
  - GitHub 双向同步，而不是单向导出。
- 不建议照搬点：
  - 不要把产品主线做得过于宽泛。
  - 不要用“万能 Agent”叙事掩盖工作流和协作结构的缺失。

#### 6.1.5 Atoms

- 产品定位：面向产品创作者的 AI 全栈应用生成平台，强调多角色 Agent 与后端基础设施。
- 目标用户：独立开发者、产品创作者、想快速做出 SaaS 雏形的用户。
- 核心使用场景：
  - 生成带登录、数据库、支付和部署能力的全栈应用。
  - 用多角色 Agent 推进产品构建。
- 核心功能：
  - 产品经理、架构师、工程师等角色式 Agent 叙事。
  - Atoms Cloud 提供认证、数据库、对象存储、Serverless、支付等基础设施。
  - 自动设计数据模型、生成 CRUD API、连接前后端并部署。
- 差异化卖点：
  - 明确把“后端不是附属品”作为产品卖点。
  - 比很多“只会生成前端页面”的产品更偏全栈可运行交付。
- 产品体验亮点：
  - “角色化 Agent”更符合用户理解复杂软件开发过程的方式。
  - 后端、支付、部署被默认纳入，减少用户自己拼装。
- 产品体验问题：
  - 公开信息更偏单体应用生成，对企业协作治理和多项目管理支撑较弱。
  - 更适合从零起步的新应用，不一定适合复杂存量项目交付。
  - 多角色叙事强，但企业级项目透明度和控制面仍需观察。
- 商业模式 / 定价：公开价格信息较少，待进一步验证。
- 我们可借鉴点：
  - 让“后端/数据层/部署”成为一等公民，而不是后补功能。
  - 让多角色 Agent 成为可理解的工作流，而不是一句抽象概念。
- 不建议照搬点：
  - 不要把主场景收缩成“独立开发者快速做 SaaS”。
  - 我们更需要接住企业内部项目与长期协作。

### 6.2 桌面应用

#### 6.2.1 Cursor

- 产品定位：AI Code Editor，核心是围绕真实代码仓库提升开发效率。
- 目标用户：开发者、研发团队。
- 核心使用场景：
  - 在真实仓库内理解代码、修改代码、重构、调试。
  - 通过 cloud/background agents 异步执行一部分任务。
  - 利用 MCP、skills、hooks 扩展工作方式。
- 核心功能：
  - Agent 编码能力。
  - Cloud / Background Agents。
  - MCPs、skills、hooks。
  - Bugbot 等代码审查增强能力。
- 差异化卖点：
  - IDE 深度强，代码上下文理解优秀。
  - 对真实工程研发的贴合度高。
  - 扩展机制成熟，容易进入开发者日常主流程。
- 产品体验亮点：
  - 本地开发环境和 AI 结合紧密。
  - 能把部分任务异步丢给云端 agent。
  - 扩展能力强，便于适配不同团队习惯。
- 产品体验问题：
  - 项目管理、任务承接、业务上下文、交付产物沉淀不是其产品中心。
  - 偏单人或研发小团队工作流，对企业跨角色协作支持有限。
- 商业模式 / 定价：免费 + 个人订阅 + 团队版 seat 模式。
- 我们可借鉴点：
  - 深代码上下文理解。
  - Hooks / Skills / MCP 的组合能力。
  - 异步 cloud agents。
- 不建议照搬点：
  - 不要把产品重心变成“另一个 AI IDE”。

#### 6.2.2 Windsurf

- 产品定位：Agentic IDE，强调 Cascade、预览和部署的连贯体验。
- 目标用户：开发者、研发团队。
- 核心使用场景：
  - 在 IDE 里边对话、边改代码、边预览、边部署。
  - 用 Cascade 处理代码生成与修改。
- 核心功能：
  - Cascade 对话式编程。
  - Previews：本地或浏览器内预览，并可把页面元素和错误回送给 Agent。
  - App Deploy。
  - 团队版支持管理面板、访问控制、知识库等能力。
- 差异化卖点：
  - 把预览、错误回传、部署做得比传统 AI IDE 更显性。
  - 适合前端和 Web 应用快速闭环。
- 产品体验亮点：
  - “页面预览 -> 选元素 -> 回送给 Agent”这条回路很短。
  - 对 Web 类应用体验友好。
- 产品体验问题：
  - 仍然是 IDE 中心，不承接更上游的业务需求与项目协作。
  - 组织级流程、审批、任务编排、资产沉淀不强。
- 商业模式 / 定价：免费 + Pro + Teams + Enterprise。
- 我们可借鉴点：
  - 预览面板与 Agent 联动。
  - 从运行错误直接反哺到修改流程。
  - 部署能力尽量缩短路径。
- 不建议照搬点：
  - 不要以“更强编辑器”替代“更强工作台”。

### 7.2 体验维度对比

#### 信息架构

- 扣子编程：产品线多，能力强，但新用户理解成本偏高。
- 飞书妙搭：围绕企业轻系统构建，心智更聚焦。
- Manus：心智较宽，通用 Agent、网站、连接器混合。
- Cursor / Windsurf：对开发者直观，对业务角色不友好。
- 我们的机会：围绕“项目与任务”组织信息架构，比纯功能导航更自然。

#### 首次引导

- 飞书妙搭、Manus 更强调“先出结果”。
- Cursor、Windsurf 更依赖已有开发者习惯。
- 扣子编程介于两者之间，但需要更强的新手引导。
- 我们应该让首次体验从“真实需求进入”开始，而不是从空白聊天开始。

#### 核心路径长度

- 最短：飞书妙搭、扣子编程、Windsurf（尤其是页面预览改动）。
- 较长：Cursor（依赖开发者自己组织任务）。
- 我们需要压缩的不是“写一句话到出代码”路径，而是“需求到执行结果回流任务”的路径。

#### 输出质量

- IDE 类产品在代码质量和可控性上通常更强。
- 在线生成平台在速度上更强，但复杂工程稳定性和可维护性未必最好。
- 我们应强调“可执行 + 可回收 + 可复盘”的综合质量，而不是只比一轮生成效果。

#### 响应速度

- 同步对话式体验通常更快感知结果。
- 异步 Agent 更适合长任务，但需要通知和状态反馈。
- 我们应该支持同步微调和异步长任务并存。

#### 可控性

- Cursor/Windsurf 最强。
- 搭叩、Manus 这类黑盒异步产品相对较弱。
- 我们应在“自动执行”和“人工接管”之间做强切换能力。

#### 专业用户友好度

- Cursor/Windsurf 对专业开发者最友好。
- 飞书妙搭对业务用户更友好。
- 我们应把“业务友好”和“研发友好”做成双模式，而不是只能服务其中一类人。

## 8. 用户价值与机会判断

### 8.1 用户最在意的核心任务

对我们的目标用户来说，真正高价值的任务不是“让 AI 写一段代码”，而是：

- 把模糊需求快速变成可执行方案。
- 自动补全项目上下文，减少重复解释。
- 把大任务拆成可推进、可确认、可交付的小单元。
- 在执行过程中保留透明度、日志、产物和可接管性。
- 让结果沉淀成团队的长期复利资产。

### 8.2 现有产品做得好的点

- 快速原型与应用生成。
- 数据库/存储/支付/部署等基础设施托管。
- 代码仓库内的 AI 协作效率。
- 异步 Agent 和并行研究。
- 连接外部工具与 MCP。

### 8.3 现有产品普遍做得差的点

- 对真实企业需求的结构化输入承接不足。
- 任务拆分和依赖关系不够透明。
- 审批、确认、失败恢复、人机协同切换不足。
- 执行结果与项目、知识库、产物、任务系统关联不够紧密。
- 评测和观测常常停留在模型/trace 层，没有与业务交付结果直接对齐。

### 8.4 我们切入的最佳突破口

最佳突破口不是拼“谁生成页面更快”，而是建立“企业内部 AI 交付工作台”的完整主链路：

- 上游接住真实需求和项目上下文。
- 中间完成拆分、编排、执行和接管。
- 下游沉淀 Git、产物、知识和评测结果。

只要这条链路成立，我们就不会被迫和 Cursor、Manus、扣子编程在它们最强的单点上正面竞争。

## 9. 对我们的产品建议

### 9.1 应该做

#### P0：建议立刻验证的能力

- 统一需求入口工作台：让需求先变成结构化输入，再进入 AI 补全和执行。
- 需求补全助手：自动发现缺失信息、风险点、影响面、依赖关系。
- 智能任务拆分：输出任务目标、输入、输出、完成定义、依赖关系、AI/人工建议。
- 工作流草稿生成：把任务拆分结果转成可编辑工作流。
- 执行产物中心：聚合 PRD、方案、日志、代码差异、测试结果、部署结果。
- 基础评测/观测：至少先接住 trace、结果评估、失败原因和成本观察。

#### P1：建议优先建设的工作流

- 异步云端 Agent 工作流：长任务可以排队、执行、通知、接管。
- 预览与反馈闭环：任务执行结果能直接被预览和评论。
- Git / 任务 / 产物联动：每个任务的变更、日志和产物可追踪。
- 协作者机制：支持多角色协同推进同一个项目或需求。

#### P1：建议建立的差异化壁垒

- 项目上下文系统：知识库、历史任务、Git、Skills、MCP 一起被组织化利用。
- 企业内协作与治理：审批点、确认点、权限、用量、评测、审计。
- 需求到交付的全链路透明性：不是只给结果，而是给过程、状态和接管面。

### 9.2 不应该做

- 不要优先做纯聊天入口。聊天可以是入口之一，但不能成为产品主体。
- 不要优先做消费级模板市场。当前项目更适合先服务企业内部复用，而不是对外内容生态。
- 不要优先做重型可视化页面搭建器。当前更应该把工作流和交付链路先做通。
- 不要优先做“完全黑盒自动执行”。缺少透明度的自动化在企业环境里很难长期成立。
- 不要和 Cursor 正面拼“谁是更好的 IDE”。这不是我们的最强战场。

### 9.3 产品路线建议

#### 短期：1-2 个版本先做什么

- 把“需求 -> 任务 -> 工作流 -> 执行 -> 产物”主链路打通。
- 补足需求补全、任务拆分、工作流草稿和执行产物中心。
- 建立最小可用的 trace / 评测 / 用量观察能力。

#### 中期：形成什么核心能力

- 形成稳定的异步 Agent 执行与接管能力。
- 形成项目上下文系统，让知识库、Git、Skills、MCP 真正服务执行。
- 形成企业级协作和治理能力，让多人能共同推进 AI 交付。

#### 长期：如何建立护城河

- 把工作台做成企业内部需求推进和 AI 执行的默认入口。
- 让每次执行都能沉淀成模板、知识、评测样本和最佳实践。
- 在业务线 -> 项目 -> 工作流 -> 任务 -> 产物 -> 评测的纵向链路上形成数据复利。
