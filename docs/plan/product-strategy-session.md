## 一句话定义

AINATIVE 应该定位为一个面向团队与业务线的 `Agent Harness Workbench`：把多种 AI CLI、项目上下文、工作流模板、知识沉淀、权限审批和可观测性整合成统一工作台，而不是先做成一个“大而全的 AI 助手”。

## Strategy Context

### 当前已具备的产品资产

从仓库现状看，AINATIVE 已经不是 0 到 1 的概念验证，而是具备了平台底座：

- 多租户与组织边界：`business-lines`、`projects`、`access`
- 任务执行闭环：创建、执行、回复、重试、审批、取消、重复执行
- 工作流资产：`workflow-templates`
- Agent 工具适配：`codex`、`claude`、`cursor`、`gemini`、`opencode`
- 本地项目上下文读取：`project-context`
- 本地技能与 MCP 管理：`skills`、`mcps`
- Git / worktree / terminal / task detail 可视化能力
- 平台级指标：队列、成功率、任务时长、运行告警

这意味着 AINATIVE 最强的机会，不是“再做一个聊天入口”，而是把这些能力收束成企业可复用的 AI 工作台。

### 当前草案的主要问题

`plan.md` 里方向很多，但有三个典型混杂：

- 平台能力、终端形态、未来想象放在同一层级
- B 端刚需和 C 端增色功能混在一起
- 没有区分“近期必须做”与“以后可以做”

结果是容易把路线拉散，团队会同时追多个漂亮但不闭环的方向。

### 市场与时机判断

现在的时机成立，原因有三点：

- 各类 AI CLI 已经足够实用，但企业缺少统一治理层
- 团队开始从“个人提效”进入“组织级 AI 协作”
- 企业真正愿意付费的不是模型入口，而是可控、可复用、可追踪、可沉淀

## Positioning

### 产品定位

AINATIVE = 面向研发团队的 AI 执行与治理工作台。

它解决的不是“让单个人更会问 AI”，而是：

- 让一个业务线内多个项目可以复用 AI 工作方式
- 让任务从需求到执行到审批到沉淀形成闭环
- 让管理者看到 AI 产出、风险、消耗和复利

### 定位声明

对于希望把 AI 从个人工具升级为团队生产力基础设施的研发组织，
AINATIVE 提供一个统一的 Agent Harness Workbench，
将多模型 CLI、项目上下文、技能、MCP、工作流模板、审批和观测整合到同一工作台，
帮助团队安全地执行、复用和优化 AI 工作流；
不同于单点聊天工具或个人本地编排器，
AINATIVE 的核心价值是组织级治理、跨项目复用和知识复利。

### 与 AgentCrew 的关系

AgentCrew 更像“本地原生编排工作台”，强在：

- 本地体验
- DAG / wave 调度
- 双模式执行
- auto-planner
- 运行时洞察

AINATIVE 不应直接复制它的产品定义，而应：

- 借它的执行模型
- 借它的 planner / orchestration 思路
- 借它的 mode recommendation 思路
- 但坚持 AINATIVE 的核心是“团队工作台”，不是“个人 macOS 工作台”

一句话说：

- AgentCrew 更像执行器和交互范式参考
- AINATIVE 更像团队级工作台与资产沉淀层

## Target Customer

### 主要客户画像

1. 研发团队负责人 / 工程经理
- 关心 AI 使用是否可控、是否有产出、是否能标准化

2. Tech Lead / Staff Engineer
- 关心复杂需求如何拆分、执行如何稳定、上下文是否足够

3. 工具平台 / 效能平台负责人
- 关心多工具接入、权限治理、组织复用、成本统计

### 次级用户

- 普通开发者
- 测试 / QA
- 交付 / 运维角色

### 暂不作为核心目标用户

- 泛 C 端个人效率用户
- 强社交协作场景的外部伙伴
- 非研发主导的泛办公助手用户

## Proto Personas

### Persona A：工程经理

- 负责多个项目和业务线的交付节奏
- 痛点是 AI 使用分散、不可见、无法复盘
- 需要看到任务进度、风险、审批点、消耗和复用率

### Persona B：Tech Lead

- 负责把模糊需求落到可执行研发任务
- 痛点是上下文断裂、需求拆分靠人工、跨仓库改动风险高
- 需要更强的上下文补全、智能拆分、执行回路和局部重试

### Persona C：平台管理员

- 负责工具接入、账号策略、技能资产和组织规范
- 痛点是每个团队都在重复配置 CLI / MCP / prompt / workflow
- 需要统一目录、模板分发、权限边界和审计视图

当业务线接入新的 AI 工具或最佳实践时，我希望能一次配置、多项目复用，并保留权限和审计边界，这样工作台才能真正形成组织复利。

## Problem Framing

### 核心问题陈述

企业内的 AI 研发活动正在增长，但仍停留在“个人 CLI + 临时 prompt + 手工复制经验”的阶段，导致：

- 需求进入 AI 前缺少上下文补全
- 复杂任务缺少稳定拆分与依赖编排
- 多模型、多 CLI 使用缺少统一治理
- 审批、风险控制、运行追踪仍然割裂
- 经验无法沉淀为跨项目复用资产
- 管理层无法回答“AI 到底创造了什么价值、花了多少成本”

### Why Now

- 模型能力已经足以承担执行节点，而不是只做问答
- 团队开始接受 workflow / agent / MCP / skill 这些概念
- 如果此时不做工作台层，组织会先形成大量不可维护的“个人自动化孤岛”

### How Might We

我们能否把 AINATIVE 从“任务执行系统”升级为“组织级 AI 执行与治理工作台”，让需求补全、任务拆分、执行编排、审批、知识沉淀与消耗统计形成一个连续闭环？

## Opportunities

### Opportunity 1：把现有能力收束成真正的 Agent Harness Workbench

目标：
让业务线、项目、技能、MCP、工作流模板、Agent CLI 不再是分散模块，而成为统一资产层。

价值：
- 形成工作台心智
- 建立组织级复用
- 为后续智能化提供统一承载层

### Opportunity 2：把“任务执行”升级为“需求到执行的中间层”

目标：
从“创建一个任务”升级为“输入一个需求，系统先补全上下文，再拆分，再生成执行计划”。

价值：
- 真正提升上游效率
- 形成差异化
- 更接近研发生产过程，而不是简单任务管理

### Opportunity 3：把知识沉淀做成复利系统

目标：
把需求、方案、执行记录、工作流、技能、MCP、产物关联起来，形成项目级和业务线级知识网络。

价值：
- 越用越好
- 复盘可追溯
- 降低人员流动损失

### Opportunity 4：把观测从“运行健康”升级为“经营视角”

目标：
不仅看队列和成功率，还看业务线 / 项目 / 工具 / 用户维度的 AI 消耗与收益。

价值：
- 帮管理层做预算和策略
- 让工作台从工具变成经营系统

### Opportunity 5：以轻量终端形态补足闭环，而不是抢主战场

目标：
提供移动审批和桌面执行伴侣，但不把主产品重心切到移动端或原生桌面。

价值：
- 增强可达性
- 支持高频审批和通知
- 不偏离工作台核心

## Solution Hypotheses

### Epic 1：Unified Agent Harness

假设：
如果把业务线、项目、技能、MCP、工作流模板、Agent CLI 统一成标准化资产目录和配置入口，团队会更快复制最佳实践，并减少重复配置。

信号：
- 新项目接入时间下降
- 模板复用率上升
- 新工具接入时间下降

### Epic 2：Context-Aware Requirement Completion

假设：
如果系统在需求创建前自动读取项目上下文、文档、Git 信息和历史任务，并生成可研发状态的需求稿，需求澄清成本会显著下降。

信号：
- 需求从创建到执行的平均等待时间下降
- 用户对“任务描述质量”的主观评分上升
- 返工率下降

### Epic 3：Hierarchical Task Decomposition

假设：
如果系统能把大需求拆成“需求 -> 子需求 -> 任务 -> 节点”的层级结构，并支持依赖、并行、重排和回滚，复杂任务的执行成功率和协作效率会提高。

信号：
- 大任务平均完成率上升
- 中途人工重排比例下降
- 重试成功率上升

### Epic 4：Memory & Knowledge Compound Interest

假设：
如果系统能把 spec、执行记录、讨论、工件和模板归档关联，团队会更频繁复用过去经验，工作台留存会更强。

信号：
- 历史资产引用率上升
- 知识库访问与关联点击上升
- 同类需求启动速度提升

### Epic 5：AI Spend & Outcome Analytics

假设：
如果系统能按业务线 / 项目 / 工具 / 用户统计消耗与产出，管理层会更愿意推动工作台在组织内扩散。

信号：
- 管理者周活跃提升
- 业务线扩容意愿上升
- 预算决策更快

### Epic 6：Approval & Companion Surfaces

假设：
如果高频审批、告警和进度同步可以通过移动端或轻量桌面端完成，任务周转会更快，但这只能作为增强，不应成为主产品定义。

信号：
- in_review 停留时长下降
- 审批响应时间下降

## Prioritization

### 采用框架

使用 `战略价值 x 落地可行性 x 差异化 x 数据闭环能力` 的加权优先级，而不是单纯按“看起来酷不酷”排序。

### 优先级结论

P0：
- Unified Agent Harness
- Context-Aware Requirement Completion
- Hierarchical Task Decomposition

P1：
- Memory & Knowledge Compound Interest
- AI Spend & Outcome Analytics

P2：
- Approval & Companion Surfaces

P3：
- 角色人格化
- 社交动态流
- 个人效率仪表盘
- 外部公开分享
- AR / VR

### 排序理由

P0 之所以优先，是因为它们直接决定 AINATIVE 是否能成为工作台级产品，而不是“功能集合”。

P1 很重要，但前提是先有稳定执行与资产结构，否则统计和记忆只会变成散乱数据堆积。

P2 可以做，但属于提效增强，不是当前破局点。

P3 暂时不建议进入主路线，因为它们对核心价值贡献弱，且会显著稀释资源。

## Roadmap / Sequencing

### Phase 0：重新定义主线（未来 2-4 周）

目标：
完成工作台叙事收束，建立第一批试点项目。

交付：
- 明确产品北极星与对内对外定位
- 收敛信息架构：工作台资产层、执行层、沉淀层、观测层
- 选 2-3 个试点项目，覆盖不同复杂度
- 定义埋点与度量口径

### Phase 1：打透工作台最小闭环（0-3 个月）

目标：
让 AINATIVE 完成“需求进入 -> 上下文补全 -> 执行 -> 审批 -> 记录”的闭环。

重点建设：
- 项目 / 业务线级 Agent Harness 工作台目录
- 需求补全助手 v1
- 层级任务拆分 v1
- 任务依赖、并行、重排能力增强
- 审批节点体验优化
- 结果与工件归档

验收标准：
- 试点团队能稳定用它处理真实复杂需求
- 至少 30% 的任务使用模板或复用资产启动

### Phase 2：做出组织复利（3-6 个月）

目标：
把单次执行能力升级为跨项目复用能力。

重点建设：
- spec / 决策 / 执行记录统一沉淀
- 资产检索与关联推荐
- 工作流模板与技能分发机制
- MCP 导入、复制、治理体验增强
- 跨项目最佳实践复用

验收标准：
- 新项目接入时间明显下降
- 至少 2 个业务线开始复制同一套能力

### Phase 3：建立经营视图（6-9 个月）

目标：
让管理层能够用数据管理 AI 工作台。

重点建设：
- AI 消耗统计
- 成功率 / 时长 / 回滚 / 审批瓶颈分析
- 按业务线 / 项目 / 工具 / 用户看板
- 成本与产出关联视图

验收标准：
- 周报 / 月报可以工作台自动产出
- 管理者能用工作台数据做预算与治理决策

### Phase 4：补全伴侣形态（9-12 个月）

目标：
增强可达性，不改变工作台重心。

重点建设：
- 移动审批与通知
- 桌面轻伴侣
- 主动式提醒与异常预警

验收标准：
- 审批响应时间下降
- 高优先级任务中断减少

## What To Borrow From AgentCrew

建议直接借鉴：

- 双模式执行思路：固定 Pipeline + 动态 Agent
- DAG / Wave 调度模型
- Auto-planner 的任务拆分框架
- 执行监控与模式洞察
- 高风险操作的人在回路

建议改造成工作台能力：

- Planner 不只生成 step，还要落到业务线 / 项目模板体系
- Mode recommendation 不只给个人提示，还要形成组织级策略建议
- 本地编排能力要接入权限、审批、资产沉淀、可观测性

不建议直接照搬：

- macOS 原生工作台作为主产品形态
- 以个人工作目录为中心的产品结构
- 偏个人效率和本地自动化的叙事

---

## What Not To Do Now

短期不建议作为主线：

- 先做“角色化 AI 助手人格”
- 先做“超级移动端”
- 先做“社交化协作 / 动态流”
- 先做“个人效率仪表盘”
- 先做“模板市场社区化”
- 先做“公开分享链接”

原因：

- 这些功能会让产品看起来更丰富，但不会先解决工作台主矛盾
- 很多属于增长层或体验层，不是工作台成立条件
- 过早投入会稀释对 P0 能力的建设

- 每个业务线月活项目数
- 每个项目 AI 驱动交付占比
- 单位有效任务成本

## Discovery And Validation Plan

当前最大的缺口不是产品想象力，而是客户验证。

建议在未来 2 周完成以下动作：

1. 访谈 5 位内部用户
- 2 位工程经理
- 2 位 Tech Lead
- 1 位平台负责人

2. 验证 4 个问题
- 他们最痛的是需求补全、拆分、执行、还是治理
- 他们是否真的需要业务线级资产复用
- 他们如何评估 AI 价值
- 他们愿不愿意为了审计和复用放弃部分个人灵活性

3. 试点 2 个核心能力
- 需求补全 v1
- 层级任务拆分 v1

4. 用真实数据判断是否进入下一阶段
- 如果用户只认可执行层，不认可工作台层，要重新审视定位
- 如果用户强烈认可治理与复用，说明主路线成立

## 未来 12 个月的产品主张

## 结论

AINATIVE 的正确升级方向，不是功能继续发散，而是产品主线收束：

从“一个能跑 AI 任务的系统”
升级为
“一个让组织获得 AI 执行复利的 Agent Harness Workbench”。

这条线一旦立住，后面的记忆系统、消耗统计、移动审批、主动服务才会自然成立；如果主线没立住，后面的大多数功能都会变成分散的增量模块。
