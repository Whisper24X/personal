# OpenCode Configuration Design

This document describes the **actual** OpenCode configuration design used in this project.

Scope:

- business-line OpenCode configurations
- backend argument compilation in `AgentRunnerService`
- frontend defaults and interactions in the OpenCode configuration modal

Out of scope:

- Codex / Claude / Cursor / Gemini configuration design
- workflow prompt template design
- OpenCode TUI usage

## 1. Goals

The OpenCode refactor follows the same rules as the other CLI adapters:

1. frontend fields must equal backend-effective fields
2. the project continues to run `opencode run` headlessly
3. free-form passthrough fields are removed

Because of that, the OpenCode business-line config is now limited to stable fields that map directly to `opencode --help` / `opencode run --help`.

## 2. Current Configuration Model

The persisted OpenCode `configJson` now uses this shape:

```ts
type OpenCodeConfig = {
  model?: string | null
  agent?: string | null
  prompt?: string | null
  fork?: boolean | null
  env?: Record<string, string> | null
}
```

These fields fall into three groups.

### 2.1 Direct CLI flags

- `model`
- `agent`
- `prompt`
- `fork`

### 2.2 Environment variables

- `env`

This is used to inject extra environment variables into the OpenCode child process.

### 2.3 Runtime continuation

OpenCode continuation is no longer described by static business-line config.

That means:

- when a task node already has `agentCliSessionId`, the platform appends `--continue --session <id>`
- `fork=true` only matters when a runtime session already exists
- business-line config no longer owns `session`

## 3. Defaults

The backend keeps the command base fixed as:

```text
opencode run --format json
```

Why this base is fixed:

- `run` is the supported headless subcommand
- `--format json` is required by the platform event parser

No extra privilege field is exposed because OpenCode does not provide a Codex-style or Claude-style explicit high-permission switch in the same configuration surface.

## 4. CLI Compilation

### 4.1 Field-to-flag mapping

| Config field | CLI flag |
| --- | --- |
| `model` | `--model <value>` |
| `agent` | `--agent <value>` |
| `prompt` | `--prompt <value>` |
| `fork=true` | `--fork`, but only when continuing a runtime session |

### 4.2 Prompt behavior

`prompt` is treated as a static OpenCode CLI prompt setting.

It does **not** replace the task/node prompt generated by the platform. The runner still writes the task prompt to stdin, and `prompt` acts as an extra OpenCode-side prompt parameter.

### 4.3 Continuation behavior

When a task node already has `agentCliSessionId`, the backend appends:

```text
--continue --session <id>
```

If `fork=true` at the same time, the backend additionally appends:

```text
--fork
```

### 4.4 Example

Configuration:

```json
{
  "model": "openai/gpt-5",
  "agent": "builder",
  "prompt": "Use repository conventions first.",
  "fork": true,
  "env": {
    "OPENAI_API_KEY": "xxx"
  }
}
```

Without a runtime session, it compiles to:

```text
opencode run \
  --format json \
  --model openai/gpt-5 \
  --agent builder \
  --prompt "Use repository conventions first."
```

With `agentCliSessionId=opencode-session-1`, it compiles to:

```text
opencode run \
  --format json \
  --model openai/gpt-5 \
  --agent builder \
  --prompt "Use repository conventions first." \
  --continue \
  --session opencode-session-1 \
  --fork
```

And `OPENAI_API_KEY=xxx` is injected into the child process environment.

## 5. Removed Legacy Fields

These fields are intentionally no longer part of OpenCode business-line config:

- `append_prompt`
- `variant`
- `continue`
- `session`
- `auto_approve`
- `auto_compact`
- `base_command_override`
- `additional_params`

Reasons:

### 5.1 They are not stable one-to-one startup fields

- `continue`
- `session`

Continuation is runtime state and should be driven by node session data, not business-line defaults.

### 5.2 They create UI-only capabilities without backend guarantees

- `append_prompt`
- `auto_approve`
- `auto_compact`

Those fields do not belong to the current project execution model, so keeping them would create misleading configuration surfaces.

### 5.3 They break platform control boundaries

- `base_command_override`
- `additional_params`

Those fields bypass structured configuration and make future upgrades harder to control safely.

### 5.4 They are intentionally not exposed in this project

- `variant`

Even though `opencode run --help` exposes `--variant`, the current project does not expose it as a business-line default yet. The existing design keeps the model surface smaller until there is a concrete product need for provider-specific reasoning controls.

## 6. Frontend Behavior

The OpenCode config modal enforces these rules:

- only CLI-aligned structured fields are shown
- `prompt` is shown as an advanced multiline field
- `fork` is shown as a boolean switch with a continuation-only hint
- removed legacy fields are no longer visible

## 7. Implementation

The current implementation lives in:

- `backend/src/tasks/agent-runner.service.ts`
- `backend/src/tasks/agent-runner.service.spec.ts`
- `frontend/src/components/business/settings/modals/AgentToolConfigModal.vue`
- `frontend/src/components/business/settings/__tests__/AgentToolConfigModal.spec.ts`

## 8. Extension Rules

If OpenCode configuration is extended later, use this order:

1. confirm a real flag in `opencode --help` or `opencode run --help`
2. prefer one-to-one CLI fields over platform-only abstractions
3. only introduce higher-level session or prompt layers if the project later adds a separate OpenCode protocol layer
