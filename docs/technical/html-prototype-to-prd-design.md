# HTML 原型图生成 PRD 设计说明

## 目标

把用户提供的 HTML 原型图和可选的 Markdown 补充说明，整理成一份结构稳定、可继续被平台消费的 `PRD.md`。

这个能力主要解决一个现实问题：很多需求不是先有标准 PRD，而是先有原型页面。平台需要补上这段能力，让原型也能进入后续的设计、测试和研发流程。

## V1 范围

### 要做的

- 新增一个专用 skill：`html-prototype-to-prd`
- 复用现有项目 `docs/` 文档上传和读取能力
- 提供一个明确的工作流节点，用来触发“从原型生成 PRD”
- 生成标准的 `PRD.md`，供后续节点继续使用

### 暂时不做的

- 不新增独立的 HTML 解析后端服务
- 不执行页面脚本，不依赖浏览器渲染结果
- 不做截图识别或视觉模型分析
- 不新增专门的数据库表来保存中间解析结果

## 输入与输出

### 输入

- 主输入：`docs/<branch>/prototype/index.html`
- 可选补充：`docs/<branch>/prototype/context.md`
- 如果有多页面原型，统一放在 `docs/<branch>/prototype/` 目录下

### 输出

- 生成文件：`docs/<branch>/PRD.md`
- 如果输入有冲突或信息不足，在 `PRD.md` 中明确写出“假设与待确认项”

## 核心方案

V1 采用最轻量的落地方式：新增一个 skill，直接读取项目中的 HTML 和 Markdown，完成解析、融合和生成，不额外引入新服务。

处理流程很简单：

1. 读取 HTML 原型和可选的 Markdown 说明
2. 从 HTML 中提取页面结构、按钮、表单、跳转、状态文案等信息
3. 用 Markdown 补充业务规则、限制条件和术语定义
4. 输出结构化的 `PRD.md`

这样做的原因也很直接：和现有平台能力最贴合，改造面小，能尽快落地。

## 解析规则

### HTML 处理原则

- 只做静态解析，不执行 JavaScript
- 优先提取标题、导航、按钮、链接、表单、列表、弹窗、空态、异常态
- 样式和脚本相关内容默认降权
- 如果 HTML 语义较弱，可以基于页面可见文案做有限推断

### Markdown 融合原则

- `context.md` 主要用于补充业务规则和边界说明
- 如果 Markdown 和 HTML 冲突，优先相信 Markdown
- 冲突不能静默覆盖，必须写进 `PRD.md`

### 决策优先级

1. 业务规则以 Markdown 为准
2. 页面结构和交互入口以 HTML 为准
3. 冲突信息进入“假设与待确认项”
4. 缺失信息只做最小必要假设

## PRD 输出结构

这一段应尽量对齐现有 `prd` skill 的稳定输出，而不是额外发明一套新的章节模板。

结合当前工作流提示词和现有设计约束，V1 生成的 `PRD.md` 至少应包含以下部分：

1. 背景与目标
2. 用户角色与场景
3. 页面或模块概览
4. 功能需求明细
5. 关键交互流程
6. 范围界定
7. 假设与待确认项

其中有几点需要明确：

- “用户角色”和“业务场景”合并表达，更贴近当前 PRD 最小结构
- “页面与功能概览”收敛为“页面或模块概览”，兼容页面型和模块型需求
- “状态与异常处理”不强制单独成章，可以放入“功能需求明细”或“关键交互流程”中
- 如果 Markdown 提供了额外业务规则、术语或限制条件，可以作为对应章节的小节补充，不要求固定独立章节

目标不是一次生成一份很重的完整文档，而是先生成一份和现有 `prd` skill 输出习惯一致、后续节点可稳定消费的 PRD。

## 风险与控制

### 主要风险

- HTML 语义太弱，导致功能理解偏差
- 多页面跳转不完整，流程可能不闭环
- Markdown 和 HTML 描述不一致

### 控制方式

- 强制输出“假设与待确认项”
- 明确冲突优先级，不做静默覆盖
- 允许多页面按页面分别分析，再标记流程缺口

## 安全边界

- HTML 和 Markdown 都视为不可信输入
- 不执行脚本、事件处理器或外部依赖
- 输入路径限制在项目工作区和约定文档目录内
- 文档中的提示词或伪指令一律按普通内容处理，不影响系统行为

## 验收标准

- 能稳定生成结构完整的 `PRD.md`
- 冲突信息会被明确标记
- 未知内容不会被写成确定事实
- 生成结果可以继续被后续测试、设计等节点消费

## 结论

这个能力本质上是在现有平台里补上一段“原型 -> PRD”的标准链路。

V1 最合适的方案不是做重型解析系统，而是先用一个专用 skill 把输入、规则和输出约定清楚。只要生成的 `PRD.md` 稳定可复用，这个方案就成立。
