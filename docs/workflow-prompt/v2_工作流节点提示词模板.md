# v2 工作流节点提示词模板

这份文档面向**当前版本**的工作流模板能力，不再沿用 `v1_CLI执行真实提示词.md` 里那种“后端写死一句话 skill 触发词”的方式。

当前版本的实际执行模型是：

```text
最终发给 Agent 的 prompt =
节点级 prompt(node.input.prompt / nodeInput)
+
续写消息(runtime.pendingUserMessage，仅在继续对话时出现)
```

也就是说：

- 任务级 prompt 适合放“原始需求、业务背景、统一约束”，供节点 prompt 通过变量显式引用
- 节点级 prompt 适合放“这个节点此刻要做什么”，实际执行时只会发送节点级 prompt
- 节点级 prompt 可以引用工作流变量

另外，这一版模板按你的要求统一采用**技能驱动**方式设计：

- 所有节点都可以使用技能处理
- 节点 prompt 应明确告诉 Agent 优先使用哪个技能
- 如果一个节点本身就是多阶段执行，则允许在一个节点内按顺序调用多个技能

## 1. 当前版本可直接使用的变量

支持以下变量：

```text
{{taskId}}
{{taskTitle}}
{{taskPrompt}}
{{gitBranch}}
{{gitBaseBranch}}
{{gitWorktree}}
{{gitWorktreePath}}
{{projectId}}
{{projectName}}
{{projectGitUrl}}
{{projectDefaultBranch}}
```

建议：

- `{{taskPrompt}}` 放原始需求正文
- `{{taskTitle}}` 放任务标题
- `{{projectName}}`、`{{gitBranch}}`、`{{gitWorktreePath}}` 放执行上下文

文档产出目录建议统一按分支隔离：

```text
docs/{{gitBranch}}/
```

这样同一项目下不同任务分支的 MRD / PRD / TEST / DESIGN / 原型 / 部署记录不会互相覆盖。

## 2. 建议的任务级 Prompt 写法

创建任务时，`task.prompt` 建议写成这类内容，而不是把所有节点说明都塞进去：

```text
目标：
<一句话描述这次要交付什么>

业务背景：
<为什么做这件事，给谁用，解决什么问题>

范围要求：
- <范围 1>
- <范围 2>

交付要求：
- 需要产出 MRD / PRD / 原型 / 测试 / 设计 / 代码 / 部署结果

约束：
- 遵循当前仓库既有技术栈与代码风格
- 优先复用现有实现，不要凭空发明不存在的基础设施
- 若需求存在冲突或信息不足，先在文档中标注假设与待确认项
```

下列模板是**节点级 Prompt**，可以直接填到工作流模板节点的 `input.prompt`。

技能映射建议如下：

```text
Brainstorm -> brainstorm
WriteMRD -> mrd
WritePRD -> prd
GeneratePrototype -> prototype
WriteTest -> test
WriteDesign -> design
ProjectManager -> project-manager
WriteCode -> code-task-apply / code-evaluate-completion / code-task-check
ImproveCode -> improve-review / improve-analyze / improve-execute / improve-verify
DocumentChanges -> code-doc
Deploy -> deploy-prepare / deploy-execute / deploy-verify
TESTPathGuide（自动化就绪） -> path-guide
TESTPlaywright（浏览器自动化） -> playwright-skill
```

## 3. 工作流节点 Prompt 模板

### 3.1 Brainstorm

```text
使用 `brainstorm` 技能，根据以下需求生成需求澄清文档：
{{taskPrompt}}

项目信息：
- 项目：{{projectName}}
- 任务：{{taskTitle}}
- 分支：{{gitBranch}}
- 工作目录：{{gitWorktreePath}}

输出文件保存到 `docs/{{gitBranch}}/brainstorm.md`。
```

推荐配置：

- `requiresApproval: true`
- `loopEnabled: false`
- `maxLoops: 1`

### 3.2 WriteMRD

```text
使用 `mrd` 技能，优先基于 `docs/{{gitBranch}}/brainstorm.md`，并结合以下需求生成 MRD：
{{taskPrompt}}

项目信息：
- 项目：{{projectName}}
- 任务：{{taskTitle}}
- 分支：{{gitBranch}}
- 工作目录：{{gitWorktreePath}}
```

推荐配置：

- `loopEnabled: false`

### 3.12 TESTPlaywright（浏览器自动化，playwright-skill）

```text
使用 `playwright-skill` 技能，基于 `docs/{{gitBranch}}/TEST.md` 生成 Playwright 自动化脚本并逐条执行。严格遵循技能 SKILL.md 中的全量对账、覆盖率表、状态取值等契约。

**固定顺序（禁止颠倒）：**
① **地址预检**：读取 `$SKILL_DIR/references/LOGIN_ACCOUNT.md` 中的「项目地址」，用 `curl -s -o /dev/null -w "%{http_code}" --connect-timeout 5 <项目地址>` 验证可达。若不可达，**停止**并向用户确认正确地址、修正后再继续。
② **生成脚本**：按 SKILL.md 流程，为 TEST.md 中每个「类型 | 管理后台」用例生成 `docs/{{gitBranch}}/artifacts/playwright/by-id/playwright-test-<TC-ID>.js`，然后用 `validate-tc-by-id-dir.js ... --type 管理后台` 校验，再更新 `docs/{{gitBranch}}/AUTOMATED_TEST.md`。
③ **执行前再检**：再次 `curl` 验证地址可达，不可达则停止。
④ **逐条执行**：`run-by-id-sequential.js docs/{{gitBranch}}/TEST.md docs/{{gitBranch}}/artifacts/playwright/by-id --type 管理后台 --headed --continue-on-fail`。**禁止**在未生成脚本前执行。

**脚本自包含（硬性）：**
- 每个 `playwright-test-<TC-ID>.js` 必须**完全自包含**：自行 `applyLoginEnvIfUnset()`、启动浏览器、登录、导航、执行测试、关闭浏览器。**禁止**依赖 `shared-harness.js` 等外部公共模块（`references/login-env.js` 除外）。
- 原因：`run.js` 将脚本写到 skill 目录下的临时文件再 `require`，`__dirname` 指向 skill 目录而非 by-id 目录，对 by-id 下其他文件的相对路径会失败。多个脚本有相同逻辑时直接重复。

**Element Plus 侧栏菜单定位：**
- 一级菜单：`page.locator('.el-sub-menu__title').filter({ hasText: '菜单文本' })`（勿用 `getByRole('menuitem')`）。
- 子菜单项：`page.locator('.el-menu-item').filter({ hasText: '菜单文本' })`。
- 菜单不存在时**优雅降级**：15s 内未出现则列出可见菜单项，输出 `[skipped]` 并 exit 0，不超时崩溃。

输入：
- 测试文档：`docs/{{gitBranch}}/TEST.md`

输出目录 `docs/{{gitBranch}}/`：
- `AUTOMATED_TEST.md`（覆盖率总表 + 执行命令）
- `artifacts/playwright/by-id/`（脚本留档，仅管理后台）

项目信息：
- 项目：{{projectName}}
- 任务：{{taskTitle}}
- 分支：{{gitBranch}}
- 工作目录：{{gitWorktreePath}}

凭据从环境变量或 `references/LOGIN_ACCOUNT.md` 读取，**禁止**硬编码账号密码与固定域名。
```

推荐配置：

- `requiresApproval: false`
- `loopEnabled: true`
- `maxLoops: 4`

## 5. 使用建议

为了让当前版本工作流更稳定，建议注意这几点：

- 任务级 prompt 只放“全局上下文”，不要把各节点说明全都塞进任务级
- 需求不够稳定或信息不完整时，把 `Brainstorm` 放在第一个环节
- 节点级 prompt 只放该节点职责，并明确对应技能，避免一个节点同时承担分析、设计、编码、部署所有职责
- `WriteCode`、`ImproveCode`、`Deploy`、`TESTPlaywright` 才比较适合开循环
- `Brainstorm`、`WriteDesign`、`WriteCode`、`Deploy` 更适合开启人工审批
- 上游文档路径尽量固定，这样下游节点才能稳定引用

## 6. 与 v1 的关系

`v1_CLI执行真实提示词.md` 记录的是旧版默认工作流里“后端实际发给 CLI 的固定提示词”。

这份文档给的是**当前版本工作流模板可直接填写的节点 Prompt 模板**。两者的核心差异是：

- v1：后端 action 写死 prompt
- v2：由节点 prompt 主导执行，任务 prompt 通过 `{{taskPrompt}}` 等变量在节点中按需引用

如果你要在当前版本里复刻旧版流程，优先使用本文件中的节点模板，而不是直接照搬 v1 里那几句短 prompt。
