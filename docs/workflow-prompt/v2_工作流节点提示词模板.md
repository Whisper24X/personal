# v2 工作流节点提示词模板

这份文档面向**当前版本**的工作流模板能力，不再沿用 `v1_CLI执行真实提示词.md` 里那种“后端写死一句话 skill 触发词”的方式。

当前版本的实际执行模型是：

```text
最终发给 Agent 的 prompt =
节点级 prompt(node.input.prompt / nodeInput)
+
续写消息(runtime.pendingUserMessage，仅在继续对话时出现)
```

也就是说：

- 任务级 prompt 适合放“原始需求、业务背景、统一约束”，供节点 prompt 通过变量显式引用
- 节点级 prompt 适合放“这个节点此刻要做什么”，实际执行时只会发送节点级 prompt
- 节点级 prompt 可以引用工作流变量

另外，这一版模板按你的要求统一采用**技能驱动**方式设计：

- 所有节点都可以使用技能处理
- 节点 prompt 应明确告诉 Agent 优先使用哪个技能
- 如果一个节点本身就是多阶段执行，则允许在一个节点内按顺序调用多个技能

## 1. 当前版本可直接使用的变量

支持以下变量：

```text
{{taskId}}
{{taskTitle}}
{{taskPrompt}}
{{gitBranch}}
{{gitBaseBranch}}
{{gitWorktree}}
{{gitWorktreePath}}
{{projectId}}
{{projectName}}
{{projectGitUrl}}
{{projectDefaultBranch}}
```

建议：

- `{{taskPrompt}}` 放原始需求正文
- `{{taskTitle}}` 放任务标题
- `{{projectName}}`、`{{gitBranch}}`、`{{gitWorktreePath}}` 放执行上下文

文档产出目录建议统一按分支隔离：

```text
docs/{{gitBranch}}/
```

这样同一项目下不同任务分支的 MRD / PRD / TEST / DESIGN / 原型 / 部署记录不会互相覆盖。

## 2. 建议的任务级 Prompt 写法

创建任务时，`task.prompt` 建议写成这类内容，而不是把所有节点说明都塞进去：

```text
目标：
<一句话描述这次要交付什么>

业务背景：
<为什么做这件事，给谁用，解决什么问题>

范围要求：
- <范围 1>
- <范围 2>

交付要求：
- 需要产出 MRD / PRD / 原型 / 测试 / 设计 / 代码 / 部署结果

约束：
- 遵循当前仓库既有技术栈与代码风格
- 优先复用现有实现，不要凭空发明不存在的基础设施
- 若需求存在冲突或信息不足，先在文档中标注假设与待确认项
```

下面 9 个模板是**节点级 Prompt**，可以直接填到工作流模板节点的 `input.prompt`。

技能映射建议如下：

```text
Brainstorm -> brainstorm
WriteMRD -> mrd
WritePRD -> prd
GeneratePrototype -> prototype
WriteTest -> test
WriteDesign -> design
任务拆解 -> project-manager
WriteCode -> code-task-apply / code-evaluate-completion / code-task-check
ImproveCode -> improve-review / improve-analyze / improve-execute / improve-verify
Deploy -> deploy-prepare / deploy-execute / deploy-verify
```

## 3. 工作流节点 Prompt 模板

### 3.1 Brainstorm

```text
使用 `brainstorm` 技能，根据以下需求生成需求澄清文档：
{{taskPrompt}}

项目信息：
- 项目：{{projectName}}
- 任务：{{taskTitle}}
- 分支：{{gitBranch}}
- 工作目录：{{gitWorktreePath}}

输出文件保存到 `docs/{{gitBranch}}/brainstorm.md`。
```

推荐配置：

- `requiresApproval: true`
- `loopEnabled: false`
- `maxLoops: 1`

### 3.2 WriteMRD

```text
使用 `mrd` 技能，优先基于 `docs/{{gitBranch}}/brainstorm.md`，并结合以下需求生成 MRD：
{{taskPrompt}}

项目信息：
- 项目：{{projectName}}
- 任务：{{taskTitle}}
- 分支：{{gitBranch}}
- 工作目录：{{gitWorktreePath}}

输出文件保存到 `docs/{{gitBranch}}/MRD.md`。

如果信息不足，只允许做最小必要假设；所有假设必须单独列在“假设与待确认项”中，不得混入正式结论。
```

推荐配置：

- `requiresApproval: false`
- `loopEnabled: false`
- `maxLoops: 1`

### 3.3 WritePRD

```text
使用 `prd` 技能，基于 `docs/{{gitBranch}}/brainstorm.md`、`docs/{{gitBranch}}/MRD.md` 和以下需求生成 PRD：
{{taskPrompt}}

项目信息：
- 项目：{{projectName}}
- 任务：{{taskTitle}}
- 分支：{{gitBranch}}
- 工作目录：{{gitWorktreePath}}

输出文件保存到 `docs/{{gitBranch}}/PRD.md`。

如果 MRD 不存在或信息不足，只允许做最小必要假设并结合需求补全；所有假设必须单独列在“假设与待确认项”中，不得混入正式结论。
```

推荐配置：

- `requiresApproval: false`
- `loopEnabled: false`
- `maxLoops: 1`

### 3.4 GeneratePrototype

```text
使用 `prototype` 技能，基于 `docs/{{gitBranch}}/PRD.md` 生成高保真原型。

项目信息：
- 项目：{{projectName}}
- 任务：{{taskTitle}}
- 分支：{{gitBranch}}
- 工作目录：{{gitWorktreePath}}

输出文件保存到 `docs/{{gitBranch}}/prototype/index.html`。

原型需覆盖核心页面、关键交互、状态变化、异常态和空态，并尽量贴近真实产品效果。
如果 PRD 信息不足，只允许做最小必要假设；所有假设必须单独列在“假设与待确认项”中，不得混入正式结论。
```

推荐配置：

- `requiresApproval: false`
- `loopEnabled: false`
- `maxLoops: 1`

### 3.5 WriteTest

```text

项目信息：
- 项目：{{projectName}}
- 任务：{{taskTitle}}
- 分支：{{gitBranch}}
- 工作目录：{{gitWorktreePath}}

输出文件保存到 `docs/{{gitBranch}}/TEST.md`。

测试文档需覆盖测试范围、测试策略、前置条件、测试数据、功能测试、异常测试、边界测试和回归建议。
如果需求或原型信息不足，只允许做最小必要假设；所有假设必须单独列在“假设与待确认项”中，不得混入正式结论。
```

- `requiresApproval: false`
- `loopEnabled: false`

### 3.6 WriteDesign

```text
使用 `design` 技能，基于 `docs/{{gitBranch}}/PRD.md`、`docs/{{gitBranch}}/TEST.md` 和当前仓库实现生成系统设计文档。

- 默认分支：{{projectDefaultBranch}}
- 当前分支：{{gitBranch}}
- 工作目录：{{gitWorktreePath}}
```

```text
- 需求文档：`docs/{{gitBranch}}/PRD.md`

- 任务：{{taskTitle}}
- 默认分支：{{projectDefaultBranch}}
- 当前分支：{{gitBranch}}
- 工作目录：{{gitWorktreePath}}
```

## 4. 推荐的节点串联顺序

如果你希望尽量贴近旧版默认工作流，可以按这个顺序配置：

1. `Brainstorm`
2. `WriteMRD`
3. `WritePRD`
4. `GeneratePrototype`
5. `WriteTest`
6. `WriteDesign`
7. `任务拆解（ProjectManager）`
8. `WriteCode`
9. `ImproveCode`
10. `Deploy`

## 5. 使用建议

为了让当前版本工作流更稳定，建议注意这几点：

- 任务级 prompt 只放“全局上下文”，不要把 9 个节点说明全都塞进去
- 需求不够稳定或信息不完整时，把 `Brainstorm` 放在第一个环节
- 节点级 prompt 只放该节点职责，并明确对应技能，避免一个节点同时承担分析、设计、编码、部署所有职责
- `WriteCode`、`ImproveCode`、`Deploy` 才比较适合开循环
- `Brainstorm`、`WriteDesign`、`WriteCode`、`Deploy` 更适合开启人工审批
- 上游文档路径尽量固定，这样下游节点才能稳定引用

## 6. 与 v1 的关系

`v1_CLI执行真实提示词.md` 记录的是旧版默认工作流里“后端实际发给 CLI 的固定提示词”。

这份文档给的是**当前版本工作流模板可直接填写的节点 Prompt 模板**。两者的核心差异是：

- v1：后端 action 写死 prompt
- v2：由节点 prompt 主导执行，任务 prompt 通过 `{{taskPrompt}}` 等变量在节点中按需引用

如果你要在当前版本里复刻旧版流程，优先使用本文件中的节点模板，而不是直接照搬 v1 里那几句短 prompt。
