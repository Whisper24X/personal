# Weekly Workflow To Skills

## 适用范围

这个 skill 用于把零散的每日工作记录，整理成可复用的方法资产。

目标分为 3 个阶段：

1. 按天还原真实工作流
2. 识别一周内重复出现的流程
3. 只提炼最值得沉淀的 skills

不要把输入简单改写成周报。优先保留顺序、决策点、卡点、解法、重复动作。

## 使用方式

当用户明确要求使用 `weekly-workflow-to-skills`，按下面流程执行。

如果用户没有提供每日记录，先索要原始材料，再继续。

## 输入要求

优先接收按天组织的原始记录。记录可以粗糙，但至少要包含下列信息中的一部分：

- 当天目标
- 实际做了哪些事
- 顺序如何
- 遇到了什么卡点
- 如何排查和解决
- 产出了什么
- 哪些动作是重复出现的

如果输入不足以还原流程，先向用户追问缺失项，不要直接虚构。

## 三阶段工作流

### 阶段 1：按天提取真实工作流

先逐天整理，不要跨天混写。

每一天都尽量提取：

- 任务起点：这项工作为什么开始
- 输入材料：文档、需求、链接、代码、会议、上下文
- 关键步骤：实际执行顺序
- 决策点：为什么这样做而不是那样做
- 卡点与解决：问题、排查动作、最终解法
- 结果输出：产出、结论、遗留问题
- 可沉淀片段：哪些步骤像稳定流程

如果原文只有结果，没有过程，要明确标注“过程信息缺失”。

### 阶段 2：归纳周度共性流程

完成逐日整理后，再做周度归纳。

把一周中的动作分为 3 类：

- 稳定流程：重复出现且步骤相对固定
- 半稳定流程：重复出现，但判断或步骤仍依赖上下文
- 一次性动作：偶发，不值得立刻沉淀成 skill

归纳时重点回答：

- 哪些工作场景反复出现
- 每次都有哪些共同步骤
- 哪些步骤是机械重复的
- 哪些地方依然强依赖人工判断
- 哪些风险或卡点最常见

### 阶段 3：蒸馏 skill 候选

只提炼 1-3 个最值得沉淀的 skill，不要贪多。

优先选择同时满足以下条件的流程：

- 一周中重复出现至少 2 次，或明显会继续出现
- 输入边界相对清楚
- 输出结果可以定义
- 至少有一部分步骤可以标准化

以下内容暂时不要做成 skill，除非用户明确要求：

- 纯一次性临时任务
- 完全依赖隐性经验、无法描述输入输出的动作
- 需要大量主观创造且几乎没有可复用步骤的过程

## Skill 候选输出格式

对每个候选 skill，使用这个结构：

```markdown
## Skill Candidate: `skill-name`

### 用途
这个 skill 解决什么重复问题。

### 触发场景
当用户提到哪些任务、目标、上下文时应考虑调用。

### 输入
- 必要材料
- 可选补充材料

### 标准流程
1. 第一步
2. 第二步
3. 第三步

### 输出
- 期望产物
- 输出格式

### 边界
- 什么情况不适用
- 哪些步骤仍需人工判断
```

## 信息不足时的追问模板

当输入不完整时，优先追问能补齐流程的最少信息。可直接复用下面的问题：

```markdown
为了把这些记录蒸馏成稳定的 skill，我还缺少几类关键信息：

1. 这一天的任务起点是什么？
2. 你实际按什么顺序推进？
3. 中间做过哪些关键判断？
4. 卡点出现在哪里，最后怎么解决？
5. 这套做法是第一次出现，还是本周重复出现过？
```

## 质量要求

输出时遵守这些规则：

- 不要把过程洗成空泛总结
- 不要把所有事情都硬提炼成 skill
- 明确区分事实、推断、信息缺失
- 优先保留“为什么这么做”
- 技能名称尽量具体，避免 `helper`、`workflow-skill` 这种空名字
- 如果用户想继续落地成真正的 `SKILL.md`，可基于候选 skill 再进一步生成正式 skill 文件

## 示例触发语句

下面这些表达都适合显式使用本 skill：

- “使用 `weekly-workflow-to-skills`，帮我整理这周每天的工作流并提炼 skills”
- “按 `weekly-workflow-to-skills` 处理这批每日记录”
- “把我这周的工作过程蒸馏成 1-3 个可复用 skills”
