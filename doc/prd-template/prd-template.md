# PRD 模板（AI 根据 MRD 生成，Review 后进入技术分析）

> 目标：AI 基于 MRD 自动生成一份“可直接评审”的 PRD；人工只需要 Review/改少量 `TBD`，即可进入下一步技术分析与方案设计。
>
> 原则：偏业务口径（What/Why），但必须“可落地、可验收、可观测、可发布回滚”。
>
> 填写/生成规范：
> - 标记：`[MUST]` 必填、`[SHOULD]` 建议填、`[OPTIONAL]` 可选
> - 允许 `TBD`：只能出现在「15. 开放问题」并带 Owner + 截止时间；正文不应出现 `TBD`
> - 不写实现细节：不写具体技术选型/库/表结构/代码；可写业务规则、约束、错误与降级、对外依赖
> - 多端一致性：涉及多端时明确“必须一致/允许差异”，并写差异点
> - 示例块：本文包含可折叠的 `<details>` 示例；AI 生成最终 PRD 时必须删除所有示例块（避免混入示例内容）

## 目录

- 0. 生成说明（给 AI）
- 1. 文档信息
- 2. MRD 摘要与需求来源
- 3. 目标与成功标准（KPI）
- 4. 需求范围与优先级
- 5. 用户、角色与场景
- 6. 端到端流程（关键路径）
- 7. 功能需求（可验收条目）
- 8. 业务对象与规则（为技术分析做准备）
- 9. 数据与埋点（可观测）
- 10. 非功能性需求（业务口径）
- 11. 依赖与影响范围
- 12. 风险与对策
- 13. 发布、灰度与运营准备
- 14. 验收标准（用例与 Go/No-Go）
- 15. 开放问题（从 MRD 补齐缺口）
- 16. 附录（链接与记录）

## 0. 生成说明（给 AI）

### 0.1 输入（MRD）

- [MUST] MRD 链接/编号：
- [MUST] MRD 核心内容（若无链接请粘贴摘要）：（AI 生成时从 MRD 提取，不要原样长篇复制）
- [SHOULD] 相关附件：竞品/用户调研/运营策略/法务合规意见（链接即可）

### 0.2 输出要求（PRD）

- [MUST] 输出应“可评审”：每个 P0 功能点必须有清晰的主流程、规则、异常边界、验收标准、埋点要求
- [MUST] 输出应“可进入技术分析”：明确业务对象、关键字段口径、权限边界、外部依赖、灰度与回滚条件
- [MUST] 输出应“可观测”：至少包含 KPI 定义与事件表（不要求具体上报 SDK/实现）
- [MUST] 输出应“可发布回滚”：包含灰度策略、停止灰度阈值、回滚与止血策略

### 0.3 生成策略（AI 自检）

- 是否把 MRD 的目标用户/痛点/价值假设转成了可验证的指标与验收？
- 是否明确了 In/Out Scope 并给出优先级（P0/P1/P2）？
- 是否为每个 P0 功能点写了：输入、规则、异常、提示文案、验收、埋点？
- 是否把 MRD 中不明确/有争议的点集中到「15. 开放问题」并标 Owner？

### 0.4 Review Gate（人工审核清单，完成后进入技术分析）

- [MUST] 范围与优先级：In/Out Scope 明确；P0/P1/P2 明确且无冲突
- [MUST] KPI 可计算：每个 KPI 有口径、窗口、归因范围、Owner
- [MUST] P0 可验收：每个 P0 功能点都有 AC、异常边界、埋点要求
- [MUST] 灰度可执行：分批/窗口/观察指标/停止阈值/回滚止血完整且有负责人
- [MUST] `TBD` 清零：正文无 `TBD`；所有不确定点只出现在「15. 开放问题」且有 Owner + 截止时间

签字（可选）：PM ____  设计 ____  研发 ____  QA ____  数据 ____
