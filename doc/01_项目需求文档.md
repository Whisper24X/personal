# 即思即成（Mind2Build）项目需求文档

**Slogan**: 让所思，即所得

## 1. 项目概述

### 1.1 项目简介
即思即成（Mind2Build）是一个多代理（Multi-Agent）协作框架，旨在通过让 AI 扮演软件公司中的不同角色来协作完成复杂任务。其核心理念是 **"Code = SOP(Team)"**，即通过标准化操作流程（SOP）和团队协作来实现软件开发的自动化。

### 1.2 项目愿景
- 让 AI 代理能够像真实的软件公司团队一样协作工作
- 从一行需求输入，自动生成完整的软件项目（包括需求文档、设计文档、代码、测试等）
- 提供自然语言编程能力，降低软件开发门槛
- 让所思即所得，将想法快速转化为可实现的产品

### 1.3 目标用户
- 软件开发人员：希望提高开发效率，自动化重复性工作
- 产品经理：需要快速原型开发和需求验证
- 初学者：学习软件开发流程和最佳实践
- 研究人员：研究多代理协作和 AI 编程

## 2. 核心功能需求

### 2.1 多角色代理系统
**功能描述**：系统需要支持多种角色的 AI 代理，每个代理有独特的职责和能力。

**架构设计**：
Role类采用模块化设计，将职责分离到不同的组件中：
- **RoleActionExecutor（行动执行器）**: 处理action执行逻辑，包括输入准备、执行和状态管理
  - 支持workspace options的actions列表（WriteMRD, WritePRD, WriteDesign等）
  - 特殊输入处理（WriteTest自动组合PRD和代码，MRDReview/PRDReview从memory查找文档等）
  - 序列继续处理（BY_ORDER模式）：自动处理action序列的执行和状态清理
  - 状态管理：action执行时设置为RUNNING，完成后设置为COMPLETED，失败时设置为FAILED
- **RoleThinker（思考决策器）**: 处理角色决策逻辑，决定下一步要执行的action
  - 支持BY_ORDER（按顺序执行）、REACT（LLM动态决策）、PLAN_AND_ACT（先计划后执行）三种模式
  - 状态管理：state=-1表示初始/终止状态，state>=0表示正在执行序列中的某个action
- **RoleLLMConfig（LLM配置管理器）**: 管理角色的LLM配置，支持从数据库加载角色特定配置
  - 配置优先级：数据库配置（角色特定）> 显式配置（构造函数传入）> 默认配置（系统默认）
  - 异步加载数据库配置，自动更新actions的LLM实例
- **RoleWorkspaceExtractor（工作区选项提取器）**: 从消息和上下文中提取workspace选项
  - 提取策略：从rc.news和rc.memory中查找，解析workspaceDir路径，fallback到context

**角色清单**：
0. **销售（Salesperson）**
   - 收集客户需求和痛点
   - 进行市场调研和业务分析
   - 产出市场研究文档（MRD）
   - 监听：User 消息
   - Actions：WriteMRD

1. **产品经理（Product Manager）**
   - 基于市场研究文档（MRD）编写产品需求文档（PRD）
   - 进行市场研究和竞品分析（SearchEnhancedQA）
   - 定义产品功能和用户故事
   - 监听：WriteMRD action
   - Actions：WritePRD, SearchEnhancedQA

2. **架构师（Architect）**
   - 设计系统架构
   - 定义数据结构和接口
   - 生成系统设计文档
   - 监听：WritePRD action
   - Actions：WriteDesign

3. **项目经理（Project Manager）**
   - 任务分解和规划（BreakdownTasks）
   - 子项目设计（WriteSubProjectDesign）
   - 监听：WritePRD 和 WriteDesign actions
   - Actions：BreakdownTasks, WriteSubProjectDesign, SubProjectDesignReview

4. **工程师（Engineer）**
   - 编写代码实现（WriteCode）
   - 执行子任务（ExecuteSubtask）
   - 代码执行和Bug修复
   - 支持自动代码生成模式
   - 监听：WritePRD, WriteDesign, BreakdownTasks actions
   - Actions：WriteCode, ExecuteSubtask, RunCode, FixBug

5. **QA 工程师（QA Engineer）**
   - 执行完整的 9 步 QA 工作流
   - 需求可测性审查、测试计划、测试用例生成
   - 自动化测试规划与执行
   - 覆盖率检查与 QA 结论
   - 监听：WritePRD 和 WriteCode actions
   - Actions：TestabilityReview, WriteTestPlan, WriteTest, TestCaseReview, AutomationPlanning, AutomationExecution, CoverageQualityCheck, QAConclusion

6. **团队领导（Team Leader）**
   - 协调各角色工作
   - 制定开发计划
   - 决策管理
   - 监听：所有广播消息（不watch特定action）
   - Actions：Coordinate

7. **数据分析师（Data Analyst）**
   - 数据分析需求处理
   - 生成分析代码
   - 数据可视化
   - 监听：无特定监听（独立任务）
   - Actions：DataAnalysis

### 2.2 标准操作流程（SOP）
**功能描述**：定义清晰的工作流程，确保各角色按照标准化流程协作。

**典型工作流**：
```
用户需求 → 销售（需求说明） → 产品经理（PRD） → 架构师（设计） → 项目经理（任务分解） 
→ 工程师（编码） → 代码审查 → QA测试 → 输出完整项目
```

**流程特点**：
- 每个角色只在接收到前置角色的输出后才开始工作
- 支持迭代和反馈循环
- 支持增量开发模式

### 2.3 消息系统
**功能描述**：实现角色间的通信和协作机制。

**核心要求**：
- 支持角色间的消息发布和订阅
- 支持消息路由（定向发送、广播）
- 支持消息历史记录
- 支持结构化消息（包含内容和元数据）

### 2.4 记忆系统
**功能描述**：为角色提供上下文记忆能力。

**类型**：
- **短期记忆**：当前对话的历史消息（`rc.news`）
- **长期记忆**：持久化的知识和经验（`rc.memory`）
- **工作记忆**：当前任务相关的临时信息（`rc.workingMemory`）

**记忆系统功能**：
- **消息存储**: Memory类存储所有消息，支持按角色、按action类型过滤
- **重要记忆**: 自动提取来自监听actions的消息（`rc.importantMemory`）
- **消息查找**: 支持从memory中查找特定action的消息（如WritePRD、WriteDesign等）
- **消息历史**: 支持获取最近k条消息或全部消息历史

### 2.5 行动系统（Action System）
**功能描述**：每个角色通过执行特定的 Action 来完成任务。

**Action执行机制**：
- **RoleActionExecutor**负责处理action的执行逻辑
- 支持workspace options的actions会自动从消息中提取workspace选项（applicationId, projectId, version等）
- 特殊输入处理：
  - `WriteTest`: 自动从memory中获取PRD文档，组合PRD和代码作为输入
  - `MRDReview/PRDReview`: 从news或memory中查找对应的文档内容
  - `ImprovePRD/ImproveMRD/ImproveDesign`: 从news或memory中查找审查报告
  - `BreakdownTasks`: 从memory中获取WritePRD和WriteDesign的消息
  - `WriteTestPlan/TestabilityReview`: 自动从memory中获取PRD和代码
- 序列继续处理（BY_ORDER模式）：action执行完成后，如果还有更多actions，清除todo但保留news供下一个action使用
- 状态管理：action执行前设置为RUNNING，成功完成设置为COMPLETED，失败设置为FAILED（不清理news，允许重试）

**核心 Action**（共 31 个）：

**文档编写 Actions**：
- `WriteMRD`：编写市场研究文档（MRD）
- `WritePRD`：编写产品需求文档
- `WriteDesign`：编写系统设计
- `WriteSubProjectDesign`：子项目设计
- `WriteCode`：编写代码
- `WriteTest`：编写测试用例
- `WriteTestPlan`：编写测试计划

**文档审查 Actions**：
- `MRDReview`：MRD文档审查
- `PRDReview`：PRD文档审查
- `DesignReview`：设计文档审查
- `SubProjectDesignReview`：子项目设计审查
- `CodeReview`：代码审查

**文档改进 Actions**：
- `ImprovePRD`：根据审查报告改进 PRD 文档
- `ImproveMRD`：根据审查报告改进 MRD 文档
- `ImproveDesign`：根据审查报告改进设计文档
- `ImproveTest`：根据审查报告改进测试用例

**任务管理 Actions**：
- `BreakdownTasks`：任务拆分
- `ExecuteSubtask`：执行子任务

**代码执行与修复 Actions**：
- `RunCode`：代码执行
- `FixBug`：Bug修复

**QA 工作流 Actions**：
- `TestabilityReview`：需求可测性审查
- `TestCaseReview`：测试用例评审与补充
- `AutomationPlanning`：自动化测试规划
- `AutomationExecution`：自动化测试执行
- `CoverageQualityCheck`：测试覆盖率与质量检查
- `QAConclusion`：QA结论输出

**其他 Actions**：
- `SearchEnhancedQA`：增强搜索和问答
- `DataAnalysis`：数据分析
- `Coordinate`：协调任务

### 2.6 智能工具集成
**功能描述**：为角色提供可用的工具能力。

**工具类型**：
- **浏览器（Browser）**：网页访问和搜索
- **编辑器（Editor）**：文件读写和编辑
- **终端（Terminal）**：命令执行
- **搜索增强（SearchEnhancedQA）**：智能搜索和问答
- **代码解释器**：代码执行和分析

### 2.7 项目管理
**功能描述**：管理生成的项目文件和结构。

**能力要求**：
- 自动创建项目目录结构
- 支持 Git 版本控制
- 文件依赖关系管理
- 支持增量迭代
- 项目序列化和恢复

**Workspace管理**：
- **Workspace选项提取**: RoleWorkspaceExtractor自动从消息和上下文中提取workspace选项
  - 支持的路径格式：`workspace/{applicationId}/{projectId}/v{version}/{documentType}/`
  - 支持旧格式和遗留格式的兼容
  - Fallback机制：如果消息中找不到，从context中获取applicationId和projectId
- **文档类型映射**: 自动根据action名称映射到对应的文档类型（MRD, PRD, DESIGN, TASKS, CODE, TEST）
- **版本管理**: 支持多版本并存，通过version参数区分不同版本的项目文件

### 2.8 成本管理
**功能描述**：控制 AI 调用的成本和资源消耗。

**要求**：
- 设置预算上限
- 追踪 Token 使用量
- 成本超限时停止运行
- 提供成本报告

### 2.9 多 LLM 支持
**功能描述**：支持多种大语言模型提供商。

**LLM配置管理**：
- **角色特定LLM配置**: 支持为每个角色配置独立的LLM（通过数据库`role_llm_configs`表）
- **配置优先级**: 
  1. 数据库配置（角色特定，最高优先级）
  2. 显式配置（构造函数传入的config.llm）
  3. 默认配置（系统默认的context.llm，最低优先级）
- **异步加载**: LLM配置从数据库异步加载，不阻塞角色初始化
- **自动更新**: 当actions设置后，自动使用角色特定的LLM更新所有actions的LLM实例

**支持的 LLM**：
- ✅ OpenAI（GPT-4, GPT-3.5）- 已实现（通过 OpenAICompatibleLLM）
- ✅ 智谱AI (ZhipuAI) - 已实现（通过 OpenAICompatibleLLM）
- ✅ 火山引擎 Ark (豆包) - 已实现（通过 OpenAICompatibleLLM）
- ✅ DeepSeek - 已实现（通过 OpenAICompatibleLLM）
- ✅ Cursor Agent - 已实现（独立 CursorLLM 实现）
- ⚙️ Anthropic（Claude）- 可配置支持（通过 OpenAICompatibleLLM）
- ⚙️ Google Gemini - 可配置支持（通过 OpenAICompatibleLLM）
- ⚙️ 百度千帆 - 可配置支持（通过 OpenAICompatibleLLM）
- ⚙️ 阿里通义 - 可配置支持（通过 OpenAICompatibleLLM）
- ⚙️ Ollama（本地模型）- 可配置支持（通过 OpenAICompatibleLLM）

### 2.10 数据解释器（Data Interpreter）
**功能描述**：专门用于数据分析任务的特殊角色。

**能力**：
- 理解数据分析需求
- 编写数据处理代码
- 执行代码并生成结果
- 创建数据可视化
- 支持 Jupyter Notebook

## 4. 典型使用场景

### 4.1 场景1：从零开始创建项目
```bash
mind2build "Create a 2048 game"
```
**预期输出**：
- 完整的项目目录结构
- 需求文档（PRD）
- 系统设计文档
- 完整的源代码
- 项目文档

### 4.2 场景2：数据分析任务
```python
from mind2build.roles.di.data_interpreter import DataInterpreter

di = DataInterpreter()
await di.run("Run data analysis on sklearn Iris dataset, include a plot")
```
**预期输出**：
- 数据加载和预处理代码
- 分析结果
- 可视化图表

### 4.3 场景3：增量开发
```bash
mind2build "Add user login feature" --inc --project-path ./existing_project
```
**预期输出**：
- 更新的需求文档
- 新的设计文档
- 新增的代码文件
- 保留原有项目结构

### 4.4 场景4：代码审查
**自动触发**：在代码生成后自动进行审查
**预期输出**：
- 代码质量评估
- 改进建议
- 优化后的代码

## 5. 系统约束

### 5.1 技术约束
- 后端：Node.js（推荐 v18+）
- 前端：Vue 3 + Vite
- 数据库：PostgreSQL（推荐 v14+）
- 需要有效的 LLM API Key

### 5.2 业务约束
- LLM 调用有成本
- 响应时间依赖于 LLM 服务
- 生成的代码质量取决于 LLM 能力

### 5.3 环境约束
- 需要网络连接（访问 LLM API）
- 文件系统写入权限
- 足够的存储空间
