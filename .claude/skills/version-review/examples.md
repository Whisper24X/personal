# 版本评审示例

## 示例 1：用户登录能力增强

### 版本想法

`添加用户登录功能，支持手机号和邮箱登录`

### 第 1 轮：业务规则冲突检查

**问题：**

```markdown
> 📚 来源：业务规则 - 账号认证规范

根据现有业务规则，用户认证必须使用统一认证流程，不支持绕开认证规范自行新增登录方式。

你的版本想法提到“支持手机号和邮箱登录”。
按照当前规则，需要先确认这两种方式是否仍然走统一认证流程。

这是否与你的想法冲突？是否需要调整为“手机号和邮箱作为账号标识，但认证流程保持统一”？
```

**回答：**

`需要调整，手机号和邮箱只是账号标识，认证流程保持统一。`

### 第 2 轮：功能冲突检查

**问题：**

```markdown
> 📚 来源：历史需求文档 - 用户中心一期

历史需求文档中已经定义了“手机号登录”能力。

基于上一轮确认的结果，你当前想做的是在统一认证流程下增加邮箱作为账号标识。
这意味着本次需求更像是“扩展现有登录能力”，而不是新增独立登录模块。

这次需求是否确认作为现有登录能力的扩展，而不是单独新增一套登录流程？
```

**回答：**

`确认，作为现有登录能力的扩展。`

### 第 3 轮：术语一致性检查

**问题：**

```markdown
> 📚 来源：术语词典 - 账号与登录定义

术语词典中，“账号”用于表示手机号、邮箱等用户身份标识；
“登录”用于表示用户通过认证进入系统。

基于前两轮结论，你的需求实际是在扩展“账号类型”，不是改变“登录”定义。

是否确认统一表述为“支持手机号账号和邮箱账号登录”？
```

**回答：**

`确认，统一使用“手机号账号和邮箱账号登录”。`

### 第 4 轮：业务数据与系统兼容性检查

**问题：**

```markdown
> 📚 来源：系统限制 - 用户信息约束
> 📚 来源：开发规范 - 账号信息维护规则

现有规则要求用户主身份信息保持稳定，账号信息需要在现有资料结构内维护。

基于前面的讨论，这次需求是在现有登录能力中增加邮箱账号支持。
如果不新增新的资料结构，只在现有账号信息中补充邮箱识别方式，整体更符合当前规则。

是否确认本次需求不新增新的业务资料结构，只在现有账号信息范围内扩展邮箱识别能力？
```

**回答：**

`确认，不新增新的业务资料结构。`

### 第 5 轮：最终确认

**问题：**

```markdown
> 📚 来源：第 1 轮评审结论
> 📚 来源：第 2 轮评审结论
> 📚 来源：第 3 轮评审结论
> 📚 来源：第 4 轮评审结论

基于前四轮的评审，我们已经确认：

1. 手机号和邮箱只是账号标识，认证流程保持统一
2. 这次需求是对现有登录能力的扩展
3. 统一使用“手机号账号和邮箱账号登录”的表述
4. 不新增新的业务资料结构

基于这些结论，版本想法是否还需要进一步调整？
```

**回答：**

`不需要，可以按以上结论进入后续需求整理。`
