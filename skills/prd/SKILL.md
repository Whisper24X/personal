# MRD 转 PRD

将 MRD 转换为符合团队规范的 AI-first PRD 文档。

## 输出规范（强制）

> **重要**：以下规范必须严格遵守，不可违反。

| 项目           | 规范                                                                        |
| -------------- | --------------------------------------------------------------------------- |
| **输出文件名** | `PRD.md`（必须使用此文件名，不可使用其他名称如"产品需求文档.md"）           |
| **文件数量**   | 只生成 1 个文件，禁止创建额外的说明文件或拆分文件                           |
| **文档结构**   | 必须严格按照 [prd-template.md](references/prd-template.md) 的 16 个章节结构 |

## 核心原则

1. **PRD 关注 What / Why / Experience / Rules**，不写代码与技术选型
2. **减少自由发挥空间**：每个需求点必须明确、可验收
3. **P0 功能必须完整**：用户目标、系统行为、体验约束、验收标准缺一不可
4. **不确定项只能出现在「15. 开放问题」**

## 转换流程

### Step 1: 读取模板

首先读取 [prd-template.md](references/prd-template.md) 获取完整的 PRD 结构和填写规范。

### Step 2: 分析 MRD

从 MRD 中提取：

- 目标用户与核心问题
- 市场机会与业务目标
- 关键假设与验证方式
- 功能范围与优先级

### Step 2.5: 检索知识库内容

在生成PRD前，必须检索以下知识库内容：

1. **历史PRD**（docs-archive/prd/）：
   - 检索类似功能的PRD文档
   - 复用现有的流程命名、状态定义、数据模型
   - 确保新功能与现有功能的一致性

2. **业务规则**（docs/business-knowledge/）：
   - 检索相关的业务规则和约束
   - 确保功能设计符合业务规则
   - 规则需可编码、可测试

3. **技术约束**（docs/dev-spec/）：
   - 检索技术架构约束和性能要求
   - 确保功能设计在技术边界内
   - 性能指标需在技术边界内

4. **现有功能**（代码实现 + docs-archive/prd/）：
   - 检查是否存在类似功能
   - 明确新功能与现有功能的关系（扩展/替代/并行）
   - 如发现功能冲突，必须在第2.3章"约束与假设"中说明

5. **术语定义**（docs/business-knowledge/）：
   - 检索相关术语的标准定义
   - 必须使用知识库中的标准术语，不得自创同义词
   - 数据口径需明确定义

**检索方式**：

- 使用CLI工具在指定目录中搜索相关内容
- 对于每个章节，参考对应的知识类型（见PRD章节知识映射）：
  - 第0章（生成说明）：历史MRD
  - 第1章（文档信息）：历史PRD
  - 第2章（MRD摘要与需求背景）：历史MRD、业务规则
  - 第3章（目标与成功标准）：历史PRD、业务规则
  - 第4章（用户体验与交互设计要求）：历史PRD、开发规范
  - 第5章（需求范围与优先级）：历史PRD、功能清单、业务规则
  - 第6章（用户、角色与使用场景）：历史PRD、术语定义
  - 第7章（端到端关键流程）：历史PRD、业务规则、技术约束
  - 第8章（功能需求）：历史PRD、功能清单、开发规范
  - 第9章（数据与埋点）：开发规范、历史PRD
  - 第10章（非功能性需求）：技术约束、开发规范
  - 第11章（依赖与影响范围）：技术约束、历史PRD
  - 第12章（风险与应对）：历史PRD、业务规则
  - 第13章（发布、灰度与回滚）：开发规范、技术约束
  - 第14章（验收与 Go / No-Go）：历史PRD、技术约束、业务规则
  - 第15章（开放问题）：历史PRD
  - 第16章（附录）：历史MRD、历史PRD

**知识库使用要求**：

- 在文档中引用知识库内容时，使用格式：> 📚 来源：[知识类型] - 文档名称
- 如发现功能冲突，必须在第2.3章"约束与假设"中说明：
  - 冲突点描述（逻辑/功能/数据/交互）
  - 影响范围（模块、端、用户）
  - 涉及的已有功能或代码位置
  - 建议的解决方案（调整需求/复用能力/修改实现）
- 必须复用历史PRD中的术语和定义，保持一致性
- 必须复用历史PRD中的流程命名和状态定义
- 必须遵守业务规则和技术约束，确保可实现性

### Step 3: 按模板生成 PRD

依据模板的 16 个章节结构填充内容，确保：

- 每个 P0 功能包含完整的 A-E 规格（用户视角、系统行为、体验约束、验收标准、数据归因）
- 第 4 章体验规格完整（UX 指标、MUST 原则、UI 约束）
- 不确定项仅出现在第 15 章

### Step 4: 验收检查

- [ ] 所有 P0 功能都有完整规格
- [ ] 每个 KPI 都有对应埋点事件
- [ ] 验收标准具体、可测试
- [ ] 无技术实现细节

## 常见问题处理

| 情况             | 处理方式                         |
| ---------------- | -------------------------------- |
| MRD 缺少用户画像 | 在第 15 章标记为开放问题         |
| MRD 无明确 KPI   | 根据业务目标推导，标注需确认     |
| 功能边界模糊     | 主动明确 In Scope / Out of Scope |
| 体验要求不清晰   | 填充默认 MUST 原则，标注需评审   |

## 禁止事项

以下行为是禁止的，违反将导致输出无效：

1. ❌ 使用非 `PRD.md` 的文件名（如"产品需求文档.md"、"需求规格.md"等）
2. ❌ 创建多个文件（如一个说明文件+一个 PRD 文件）
3. ❌ 省略模板中的任何章节（16 个章节必须完整）
4. ❌ 在非第 15 章出现不确定项或待确认内容
5. ❌ 包含技术实现细节（代码、技术选型等）
