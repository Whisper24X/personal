# OpenSpec Validator

自动审查和修正 OpenSpec 规范文件与 PRD/Design 文档的一致性。

## 快速开始

### 触发方式

当你需要：

- 审查 openspec 变更的完整性
- 验证规范是否与 PRD/Design 一致
- 检查规范文件之间的一致性
- 修正规范中的冲突和错误

只需说：

```
"审查 openspec 规范，确保与 PRD 和 design 一致"
"检查 openspec 是否有遗漏或错误"
"验证 add-deposit-good-type 变更的规范完整性"
```

### 工作原理

```
1. 读取基准文档
   ├── PRD (需求规格)
   ├── design.md (技术设计)
   └── proposal.md (变更说明)

2. 审查所有 spec 文件
   ├── 检查冲突
   ├── 检查缺失
   └── 检查错误

3. 自动修正
   ├── 修正冲突（以 PRD/Design 为准）
   ├── 补充缺失（新增内容）
   └── 修正错误（逻辑错误、不一致）

4. 生成报告
   ├── 修正摘要
   ├── 详细清单
   └── 待确认事项
```

## 核心功能

### ✅ 冲突检查与修正

- 业务规则冲突：PRD 与 spec 描述不一致
- 技术方案冲突：design.md 与 spec 实现不一致
- 数据模型冲突：字段定义、枚举值不一致

### ✅ 缺失检查与补充

- 需求覆盖缺失：PRD 中的需求未在 spec 中体现
- 技术规范缺失：接口定义、数据模型、校验规则不完整
- 场景覆盖缺失：用户操作场景、异常场景未完整描述

### ✅ 错误检查与修正

- 内部逻辑错误：前后矛盾、条件不完整
- 跨 spec 不一致：概念定义、数据类型、引用关系不一致

### ✅ 完整性验证

- 需求追溯：每个 PRD 需求都有对应的 spec
- 技术追溯：每个 design 决策都在 spec 中体现
- 端到端验证：完整的用户旅程都有规范覆盖

## 修正原则

### 文档优先级

```
PRD > design.md > proposal.md > 现有 spec
```

当文档之间有冲突时，采用优先级高的文档。

### 修改策略

1. **冲突**：以基准文档为准，直接修正
2. **缺失**：补充内容，保持现有结构
3. **错误**：修正逻辑，确保一致性
4. **不确定**：标记为"待确认"，不主观添加

### 保留原则

- 保留 spec 中不冲突的实现细节
- 保留 spec 的原有格式和结构
- 保留 spec 中合理的补充说明

## 审查报告

每次审查生成包含以下内容的报告：

```markdown

   - 补充缺失：X 处

   - 待人工确认：X 项

2. 详细清单
   - 每个问题的描述
   - 基准文档引用
   - 修正内容
   - 影响评估

3. 完整性验证
   - 需求覆盖情况
   - 技术决策体现
   - 端到端场景验证

4. 下一步行动
   - 待确认事项
   - 建议改进
```

## 常见问题

### Q: 什么时候使用这个技能？

A:

- AI 生成 openspec 后，需要审查质量
- PRD 或 design 更新后，需要同步更新 spec
- 发现 spec 之间不一致，需要统一
- 准备提交变更前，需要最终验证

### Q: 技能会自动修改文件吗？

A:
是的，技能会：

1. 自动修正明确的冲突（以基准文档为准）
2. 自动补充缺失的内容
3. 自动修正逻辑错误

但对于不确定的问题，会标记为"待人工确认"。

### Q: 如果 PRD 和 design.md 冲突怎么办？

A:
PRD 优先级更高。PRD 定义"做什么"，design.md 定义"怎么做"。
如果发现真正的冲突，会标记为"待人工确认"。

### Q: 技能会创建新的 spec 文件吗？

A:
通常不会。技能优先在现有 spec 中补充内容。
只有当缺失的内容明显属于新的独立模块时，才会建议创建新 spec。

### Q: 如何处理 Open Questions？

A:
技能会识别 design.md 中的 Open Questions，并在相关 spec 中：

1. 添加"⚠️ 待确认"标记
2. 提供保守的临时方案
3. 在审查报告中列为"待人工确认"

### Q: 审查报告保存在哪里？

A:
审查报告会在对话中展示，你可以选择：

1. 保存为变更目录下的 `REVIEW_REPORT.md`
2. 添加到 tasks.md 的审查记录中
3. 仅在对话中查看，不保存文件

## 最佳实践

### ✅ Do

- 在 AI 生成 openspec 后立即运行审查
- 定期运行审查，确保 spec 与最新 PRD/design 同步
- 结合 CHECKLIST.md 手工复核关键部分
- 将审查报告作为 Code Review 的一部分

### ❌ Don't

- 不要跳过完整性验证步骤
- 不要忽略"待人工确认"的问题
- 不要在没有 PRD/design 的情况下运行审查
- 不要完全依赖自动审查，关键部分需人工复核
