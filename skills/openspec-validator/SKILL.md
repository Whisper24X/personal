# OpenSpec Validator

基于 PRD 和 design 文档审查 openspec 下所有规范文件，检查冲突、缺失和错误，并自动修正确保完整覆盖需求。

## 工作流程

### 第 1 步：定位 openspec 变更目录

识别用户当前工作的变更目录：

```
workspace/{project-id}/{app-id}/versions/{version-id}/ainative-workspace/openspec/changes/{change-name}/
```

典型结构：

```
changes/{change-name}/
├── proposal.md          # 变更说明
├── design.md            # 技术设计
├── specs/               # 具体规范
│   ├── {spec-1}/spec.md
│   └── {spec-2}/spec.md
└── tasks.md             # 任务清单
```

### 第 2 步：收集基准文档

读取以下基准文档（按优先级）：

1. **PRD 文档**（最高优先级）
   - 查找路径：`docs/prd/`
   - 内容：业务需求、用户场景、功能规格

2. **design.md**（技术基准）
   - 位置：变更目录下的 `docs/design.md`
   - 内容：技术决策、架构设计、实现方案

### 第 3 步：遍历审查所有 openspec 下所有文件

对 `openspec/` 下的每个文件：

#### 3.1 冲突检查

查找与 PRD/design 冲突的内容：

**检查项**：

- [ ] 需求描述是否与 PRD 一致
- [ ] 技术方案是否与 design.md 决策一致
- [ ] API 定义是否与设计文档匹配
- [ ] 数据模型是否与设计文档匹配
- [ ] 业务规则是否与 PRD 一致

**冲突处理原则**：

1. PRD/design 为准，修改涉及到的文件
2. 保留文件中额外的实现细节（不冲突的部分）
3. 记录修改原因

#### 3.2 缺失检查

查找 PRD/design 中有但文件中缺失的内容：

**检查项**：

- [ ] PRD 中的所有需求是否都有对应的规范
- [ ] design 中的技术决策是否都被反映在规范中
- [ ] 关键业务场景是否完整覆盖
- [ ] 数据字段定义是否完整
- [ ] 接口定义是否完整
- [ ] 错误处理规范是否完整

**缺失处理**：

1. 在对应的文件中新增缺失内容
2. 如果不确定归属哪个文件，新增到最相关的 文件 中
3. 如果需要新的文件，创建新的规范文件，但要符合openspec的规范

#### 3.3 错误检查

查找规范中的逻辑错误或不一致：

**检查项**：

- [ ] 内部逻辑是否一致（前后文不矛盾）
- [ ] 跨 文件 引用是否正确
- [ ] 枚举值定义是否一致
- [ ] 字段类型定义是否准确
- [ ] 必填/可选字段标识是否明确

**错误处理**：

1. 修正明显的逻辑错误
2. 对于不确定的问题，标记为 Open Question

### 第 4 步：生成审查报告

创建审查清单，跟踪进度：

```markdown
## OpenSpec 审查报告

### 审查范围

- 变更：{change-name}
- 基准文档：PRD, design.md, proposal.md
- 审查文件：{列出所有 spec 文件}

### 审查结果

#### ✅ 已修正的冲突

1. [spec-name] {具体冲突描述} → 已修正为：{修正内容}
2. ...

#### ✅ 已补充的缺失

1. [spec-name] {缺失内容描述} → 已新增：{新增内容}
2. ...

#### ✅ 已修正的错误

1. [spec-name] {错误描述} → 已修正为：{修正内容}
2. ...

#### ⚠️ 需要人工确认

1. [spec-name] {问题描述} → 建议：{处理建议}
2. ...

### 验证清单

- [ ] 所有 PRD 需求已覆盖
- [ ] 所有 design 决策已反映
- [ ] 跨 spec 引用一致
- [ ] 数据模型定义完整
- [ ] API 定义完整
- [ ] 错误场景已覆盖
```

### 第 5 步：验证完整性

最终验证确保规范完整覆盖需求：

#### 需求覆盖验证

逐条检查 PRD 中的需求：

- 每个需求场景都有对应的规范描述
- 每个用户故事都有对应的接口定义
- 每个业务规则都有对应的校验逻辑

#### 技术覆盖验证

逐条检查 design.md 中的决策：

- 每个技术决策都被规范化
- 每个数据模型变更都有定义
- 每个接口变更都有规范

#### 一致性验证

检查跨文件一致性：

- 同一概念在不同 spec 中定义一致
- 数据类型定义一致
- 枚举值定义一致
- 字段命名一致

## 修改原则

### 1. 以文档优先级为准

```
PRD > design.md > proposal.md > 现有 spec
```

当文档之间有冲突时，采用优先级高的文档。

### 2. 保留实现细节

如果 文件 中包含不冲突的实现细节（PRD/design 未提及），保留这些细节。

### 3. 明确标注修改

修改 文件 时，保持清晰的版本控制意识：

- 重大修改要确保逻辑完整
- 新增内容要符合现有结构
- 删除内容要确认无依赖

### 4. 补充而非替换

优先补充缺失内容，而非完全重写现有内容。

## 常见场景

### 场景 1：新增需求未在 spec 中体现

**问题**：PRD 中新增了「定金商品无需预约」需求，但 `order-management/spec.md` 未提及。

**处理**：

1. 在 `order-management/spec.md` 的 ADDED/MODIFIED Requirements 中新增对应场景
2. 确保场景描述完整（WHEN/AND/THEN 结构）
3. 补充相关的校验规则

### 场景 2：design 决策与 spec 实现不一致

**问题**：design.md 决定「定金商品跳过预约字段校验」，但 spec 中仍要求校验。

**处理**：

1. 修改 spec 中的校验逻辑描述
2. 添加条件判断：「当商品类型为 deposit 时，跳过 courseId、appointmentTime 等字段校验」
3. 保留其他商品类型的校验逻辑

### 场景 3：跨 spec 概念定义不一致

**问题**：`good-management/spec.md` 中商品类型枚举为 `single/multi/deposit`，但 `order-management/spec.md` 中只提及 `single/multi`。

**处理**：

1. 更新 `order-management/spec.md`，添加 `deposit` 类型的处理逻辑
2. 确保枚举值在所有 spec 中一致
3. 补充 `deposit` 类型的订单创建场景

### 场景 4：缺少关键业务规则

**问题**：design.md 提到「定金商品可能不支持优惠券」，但所有 spec 中都未提及。

**处理**：

1. 在 design.md 的 Open Questions 中确认这是待定问题
2. 在 spec 中标注：「优惠券支持待确认」
3. 不主动添加不确定的业务规则

## 输出格式

完成审查后，输出以下内容：

```markdown
## OpenSpec 审查完成

### 审查摘要

- 修正冲突：{数量} 处
- 补充缺失：{数量} 处
- 修正错误：{数量} 处
- 待人工确认：{数量} 处

### 详细报告

[按上述模板生成完整报告]

### 下一步行动

- [ ] 审查修改内容
- [ ] 确认待定问题
- [ ] 更新 tasks.md（如有必要）
- [ ] 提交变更
```

## 注意事项

1. **保持规范格式一致性**：遵循项目现有的 spec 格式和结构
2. **不要过度推断**：如果 PRD/design 未明确，标记为待确认，不要自行添加业务逻辑
3. **优先级管理**：先处理冲突，再补充缺失，最后修正错误
4. **完整性优先**：确保所有 PRD 需求都有对应的规范，即使实现细节待定
5. **版本意识**：修改时考虑向后兼容性和影响范围
