# PRD 评审与难度评估

基于 PRD 内容进行全面评审，识别问题并提供改进建议，同时评估需求难度等级。

## 使用场景

当用户或工作流需要以下操作时使用此 skill：

- 评审 PRD（产品需求文档）质量
- 检查 PRD 完整性与逻辑一致性
- 识别 PRD 中的缺失章节或模糊描述
- 评估 PRD 可读性与可维护性
- 提供结构化改进建议
- 评估需求难度等级（L1/L2/L3/L4）并提供复杂度分析

## 输出规范（强制）

> **重要**：所有评审输出必须严格遵守以下格式。

| 项目           | 规范                                                                                                                 |
| -------------- | -------------------------------------------------------------------------------------------------------------------- |
| **输出格式**   | PRD 评审：使用四部分结构（Summary、Strengths、Issues、Recommendations）；需求难度评级：使用六维度评估表格 + 综合评级 |
| **输出语言**   | 中文（除非用户明确要求英文）                                                                                         |
| **问题分级**   | PRD 评审使用 P0/P1/P2/P3；难度评级使用 L1/L2/L3/L4                                                                   |
| **建议可操作** | 每条建议必须具体、可执行，不得模糊（如"需要改进"）                                                                   |

## 评审输出结构（必须严格遵循）

```markdown
## Summary（摘要）

[简要总结文档目的、类型、覆盖范围与核心内容]

## Strengths（优点）

- [优点1：具体描述文档的优势，如结构清晰、覆盖全面等]
- [优点2：...]

## Issues（问题）

- **[P0/P1/P2] 问题标题**：具体描述问题，指出位置（章节/行号），说明影响
- **[P1] 缺失章节**：缺少"非功能需求"章节，未明确性能、安全性要求
- **[P2] 逻辑不一致**：第3节描述与第5节矛盾，需统一

## Recommendations（建议）

- **建议1**：补充"非功能需求"章节，包含性能指标、安全要求、可用性目标
- **建议2**：统一第3节与第5节的描述，明确[具体内容]应采用[方案A/方案B]

## 准确率评估

| 评估维度 | 准确率 | 说明                                                   |
| -------- | ------ | ------------------------------------------------------ |
| 字段识别 | 85%    | PRD 定义的数据字段完整性与准确性（字段名、类型、约束） |
| 业务规则 | 90%    | 业务逻辑、规则、限制条件的清晰度与正确性               |
| 流程识别 | 80%    | 业务流程、状态转换、时序关系的完整性与准确性           |
| 角色权限 | 95%    | 用户角色、权限矩阵、访问控制的明确性与正确性           |

## 评估结论

- **是否达到推广标准**：是/否 + 理由（基于准确率与问题严重性）
- **是否可规模化使用**：是/否 + 理由（基于架构可扩展性、技术选型、依赖关系）
- **风险点**：列出关键风险（技术风险、业务风险、交付风险）
- **优化建议**：3-5条高优先级的改进建议

## 需求难度评级：L3

### 评估维度

| 维度             | 等级 | 说明       |
| ---------------- | ---- | ---------- |
| 功能点数         | L3   | [具体说明] |
| 技术复杂度       | L3   | [具体说明] |
| 数据复杂度       | L2   | [具体说明] |
| 测试验证复杂度   | L3   | [具体说明] |
| 依赖与协作复杂度 | L3   | [具体说明] |
| 交付风险         | L2   | [具体说明] |

### 综合评级理由

[说明为什么是这个难度等级，预估工期]

- [风险点1]
- [风险点2]
```

## 评审检查点

### 1. 文档目的与范围

- [ ] 文档目的清晰
- [ ] 目标受众明确
- [ ] 范围边界清晰

### 2. 结构完整性

- [ ] 章节结构完整（根据文档类型）
- [ ] 无缺失关键章节
- [ ] 章节顺序合理

### 3. 内容质量

- [ ] 描述清晰无歧义
- [ ] 无逻辑矛盾
- [ ] 术语使用一致
- [ ] 无模糊表述（如"某用户"、"正常显示"、"合理范围"）

### 4. 可执行性

- [ ] 步骤具体可操作
- [ ] 验收标准明确
- [ ] 数据依赖完整

### 5. 可维护性

- [ ] 格式统一
- [ ] 易于更新
- [ ] 引用关系清晰

### 6. 准确率评估检查点

- [ ] 字段识别：数据实体、字段定义、类型约束
- [ ] 业务规则：业务逻辑、规则引擎、限制条件
- [ ] 流程识别：业务流程图、状态机、时序关系
- [ ] 角色权限：角色定义、权限矩阵、访问控制

## 评审流程

### Step 1: 读取 PRD 文档

使用 Read 工具读取 PRD 文档，理解整体结构与核心内容。

### Step 2: 按检查点逐项评估

依据 PRD 评审检查点，逐项检查文档：

- 记录优点（Strengths）
- 识别问题（Issues），标注严重性
- 检测逻辑不一致、缺失章节、模糊描述

### Step 3: 生成结构化输出

按照输出格式规范生成评审报告：

1. **Summary**：总结 PRD 目的与覆盖范围
2. **Strengths**：列出 PRD 优点（至少2条）
3. **Issues**：列出问题，按严重性排序（P0 → P3）
4. **Recommendations**：提供可操作建议，每条建议对应一个问题

### Step 4: 验收检查

- [ ] 输出格式符合规范（四部分结构）
- [ ] 每个问题都有对应建议
- [ ] 建议具体可执行
- [ ] 无模糊评价（如"整体不错"、"需要优化"）

## 问题严重性分级

| 级别 | 定义     | 说明                                 | 示例                       |
| ---- | -------- | ------------------------------------ | -------------------------- |
| P0   | 阻断问题 | 缺失核心章节、严重逻辑矛盾、无法执行 | 缺少功能需求章节、流程矛盾 |
| P1   | 重要问题 | 内容不完整、描述不清晰、影响理解     | 验收标准模糊、术语不一致   |
| P2   | 一般问题 | 格式不统一、细节缺失、可读性问题     | 表格格式混乱、缺少示例     |
| P3   | 优化建议 | 可优化项、最佳实践建议、非必需补充   | 添加图表、优化排版         |

## PRD 特殊检查点

评审 PRD 时，除通用检查点外，还需关注以下要点：

- **功能需求完整性**：功能清单完整，无遗漏关键功能点
- **用户场景明确性**：用户场景描述清晰，包含典型流程与边界情况
- **验收标准可量化**：验收标准具体、可测量、可验证
- **优先级定义清晰**：P0/P1/P2/P3 分级明确，符合业务目标
- **非功能需求**：性能、安全、可用性等非功能需求明确
- **依赖关系清晰**：外部依赖、前置条件、约束条件明确
- **数据模型完整**：涉及的数据实体、字段、关系定义清晰
- **字段定义准确性**：数据实体、字段、类型、约束定义清晰准确
- **业务规则完整性**：业务逻辑、规则、限制条件清晰无遗漏
- **流程定义清晰性**：业务流程、状态转换、时序关系完整准确
- **角色权限明确性**：角色定义、权限矩阵、访问控制规则清晰

## 需求难度评级

### 评级定义

对需求（特别是 PRD）进行难度评级，评级范围为 **L1 / L2 / L3 / L4**，基于六个核心维度综合评估。

| 难度等级 | 定义     | 预估工期   | 适用场景                               |
| -------- | -------- | ---------- | -------------------------------------- |
| L1       | 简单需求 | 1-3 人天   | 单一功能点、无复杂依赖、技术成熟       |
| L2       | 中等需求 | 4-10 人天  | 多功能点、中等技术复杂度、少量依赖     |
| L3       | 复杂需求 | 11-20 人天 | 大量功能点、高技术复杂度、多方协作     |
| L4       | 高度复杂 | 20+ 人天   | 大型系统、创新技术、多团队协作、高风险 |

### 评估维度

#### 1. 功能点数

统计需求涉及的功能点数量与范围。

| 等级 | 功能点数 | 说明                          | 示例                     |
| ---- | -------- | ----------------------------- | ------------------------ |
| L1   | 1-3 个   | 单一模块，少量功能点          | 简单表单提交、数据展示   |
| L2   | 4-8 个   | 单模块或跨2个模块，中等功能点 | 用户注册登录、基础 CRUD  |
| L3   | 9-15 个  | 跨多模块，大量功能点          | 订单管理系统、工作流引擎 |
| L4   | 16+ 个   | 跨系统/平台，海量功能点       | 电商平台、ERP 系统       |

#### 2. 技术复杂度指标

评估技术实现难度与技术栈复杂性。

| 等级 | 技术复杂度                  | 说明                                         |
| ---- | --------------------------- | -------------------------------------------- |
| L1   | 低：CRUD + 简单业务逻辑     | 标准技术栈，成熟框架，无技术难点             |
| L2   | 中：中等算法 + 中间件集成   | 常见算法（排序、搜索）、Redis/MQ 集成        |
| L3   | 高：复杂算法 + 分布式架构   | 复杂算法（推荐、调度）、微服务、分布式事务   |
| L4   | 极高：创新技术 + 高性能优化 | AI/ML 模型、实时计算、高并发架构、自研中间件 |

#### 3. 数据复杂度指标

评估数据模型、数据量与数据处理复杂性。

| 等级 | 数据复杂度                | 说明                                          |
| ---- | ------------------------- | --------------------------------------------- |
| L1   | 低：1-3 张表，简单关系    | 单表或少量关联表，无复杂查询                  |
| L2   | 中：4-10 张表，中等关系   | 多表关联、常规聚合查询、少量数据迁移          |
| L3   | 高：10+ 张表，复杂关系    | 多层级关联、复杂查询优化、大数据量迁移        |
| L4   | 极高：海量数据 + 复杂建模 | 百万级/千万级数据、实时数据处理、多数据源整合 |

#### 4. 测试验证复杂度

评估测试用例数量、测试场景复杂性与验收难度。

| 等级 | 测试复杂度                  | 说明                                         |
| ---- | --------------------------- | -------------------------------------------- |
| L1   | 低：10-20 个用例，简单场景  | 基础功能测试，无复杂边界条件                 |
| L2   | 中：20-50 个用例，中等场景  | 多场景测试、常规边界条件、少量集成测试       |
| L3   | 高：50-100 个用例，复杂场景 | 大量场景组合、复杂边界条件、全面集成测试     |
| L4   | 极高：100+ 用例，极端场景   | 海量场景覆盖、压力测试、安全测试、兼容性测试 |

#### 5. 依赖与协作复杂度

评估外部依赖、团队协作与跨部门沟通复杂性。

| 等级 | 协作复杂度                  | 说明                                        |
| ---- | --------------------------- | ------------------------------------------- |
| L1   | 低：单人/单团队，无外部依赖 | 独立开发，无需协调外部资源                  |
| L2   | 中：2-3 人协作，少量依赖    | 小团队协作、依赖1-2个外部接口/服务          |
| L3   | 高：跨团队协作，多依赖      | 多团队协作、依赖多个外部系统、需跨部门协调  |
| L4   | 极高：跨公司/多方协作       | 多团队/多公司协作、复杂依赖链、大量外部对接 |

#### 6. 交付风险指标

评估需求变更风险、技术风险、进度风险与质量风险。

| 等级 | 风险等级                    | 说明                                             |
| ---- | --------------------------- | ------------------------------------------------ |
| L1   | 低风险：需求明确，技术成熟  | 需求稳定、技术验证完毕、无阻塞风险               |
| L2   | 中风险：需求基本明确        | 需求可能微调、技术有小风险、进度可控             |
| L3   | 高风险：需求不完全明确      | 需求可能变更、技术有难点、进度紧张               |
| L4   | 极高风险：需求模糊/创新业务 | 需求探索阶段、技术未验证、依赖不可控、进度高风险 |

### 评级流程

#### Step 1: 读取需求文档

使用 Read 工具读取 PRD 或需求文档，提取关键信息。

#### Step 2: 逐维度评分

按六个维度逐项评估，记录每个维度的等级（L1/L2/L3/L4）与理由。

#### Step 3: 综合评级

- 计算六个维度的平均等级（向上取整）
- 若有任一维度为 L4，最终等级至少为 L3
- 若有3个及以上维度为 L3，最终等级为 L3
- 特殊情况可根据实际调整（如技术风险极高但功能简单，可评为 L3）

#### Step 4: 输出评级报告

生成结构化难度评级报告：

```markdown
## 需求难度评级：L3

### 评估维度

| 维度             | 等级 | 说明                                           |
| ---------------- | ---- | ---------------------------------------------- |
| 功能点数         | L3   | 涉及 12 个功能点，覆盖订单、支付、库存三大模块 |
| 技术复杂度       | L3   | 需要分布式事务、复杂库存扣减算法               |
| 数据复杂度       | L2   | 8 张表，中等关联关系，无大数据量处理           |
| 测试验证复杂度   | L3   | 60+ 测试用例，需覆盖多种订单状态流转场景       |
| 依赖与协作复杂度 | L3   | 依赖支付网关、物流系统、需跨3个团队协作        |
| 交付风险         | L2   | 需求基本明确，技术方案已验证，进度可控         |

### 综合评级理由

- 功能点数量多（L3），涉及核心业务流程
- 技术实现复杂（L3），需分布式事务与复杂算法
- 协作复杂度高（L3），需多团队协调与外部对接
- 数据与风险相对可控（L2）
- 综合评估：**难度等级 L3**，预估工期 15-18 人天

### 关键风险点

- 分布式事务一致性保障
- 支付网关对接稳定性
- 多团队协作进度同步
```

### 注意事项

1. **客观评估**：基于实际情况评估，避免主观臆断
2. **记录依据**：每个维度评级必须说明具体理由
3. **识别风险**：重点标注高风险项（L3/L4 维度）
4. **预留缓冲**：工期预估建议预留 20-30% 缓冲
5. **持续更新**：需求变更时及时更新难度评级

## 准确率评估

### 准确率评分标准

#### 字段识别（Field Identification）

- **100%**：所有数据实体、字段、类型、约束、索引、关联关系完整准确
- **90-99%**：主要字段完整，少量字段类型或约束描述不够明确
- **80-89%**：主要字段完整，部分字段缺失或类型不准确
- **70-79%**：关键字段缺失或类型错误，需补充
- **<70%**：字段定义严重不足，无法指导数据库设计

#### 业务规则（Business Rules）

- **100%**：所有业务逻辑、规则、限制条件清晰完整准确
- **90-99%**：主要业务规则完整，少量边界条件或异常处理不够明确
- **80-89%**：主要规则完整，部分规则描述不清或缺失
- **70-79%**：关键规则缺失或描述不准确
- **<70%**：业务规则严重不足，无法指导实现

#### 流程识别（Process Identification）

- **100%**：所有业务流程、状态转换、时序关系完整准确，流程图清晰
- **90-99%**：主要流程完整，少量状态转换或异常分支不够明确
- **80-89%**：主要流程完整，部分流程缺失或时序关系不清
- **70-79%**：关键流程缺失或流程描述不准确
- **<70%**：流程定义严重不足，无法指导实现

#### 角色权限（Role & Permissions）

- **100%**：所有角色定义、权限矩阵、访问控制规则完整准确
- **90-99%**：主要角色和权限完整，少量权限规则不够明确
- **80-89%**：主要角色完整，部分权限定义缺失
- **70-79%**：关键角色或权限缺失
- **<70%**：角色权限定义严重不足

## 评估结论

### 推广标准判断规则

达到推广标准需同时满足：

1. **无 P0 问题**（阻断问题必须全部解决）
2. **P1 问题 ≤ 3 个**（重要问题可控）
3. **所有准确率维度 ≥ 80%**
4. **需求难度评级为 L1-L3**（L4 需额外评估）

不达标情况：

- 存在 P0 问题：必须修复后再评估
- P1 问题 > 5 个：需求质量不足，需优化
- 任一准确率 < 70%：需求定义严重不足

### 规模化能力判断规则

可规模化使用需满足：

1. **架构可扩展**（支持水平扩展、微服务拆分等）
2. **技术选型成熟**（非实验性技术，有成熟社区支持）
3. **依赖关系清晰**（外部依赖可控、可替换）
4. **数据模型规范**（支持分库分表、读写分离等）
5. **监控与运维完善**（日志、告警、性能监控齐全）

不可规模化情况：

- 单体架构无法拆分
- 依赖实验性技术或不可控第三方
- 数据库设计不支持扩展

## 评审示例

```markdown
## Summary

本文档为"用户管理系统"的 PRD，覆盖用户注册、登录、权限管理三大模块。文档目标受众为产品、开发、测试团队。整体结构完整，包含功能需求、用户场景、验收标准等核心章节。

## Strengths

- 功能需求章节结构清晰，按模块分类，易于理解
- 用户场景描述详细，包含多种典型场景与边界情况
- 优先级定义明确，P0/P1/P2 分级清晰

## Issues

- **[P0] 缺失核心章节**：缺少"非功能需求"章节，未明确性能、安全、可用性指标
- **[P1] 验收标准模糊**：第3.2节"登录成功"的验收标准仅描述"跳转首页"，未定义响应时间与错误处理
- **[P2] 术语不一致**：文档中"用户角色"与"角色类型"混用，建议统一使用"用户角色"
- **[P2] 缺少示例**：权限矩阵仅有表格，建议补充实际场景示例

## Recommendations

- **补充非功能需求章节**：新增章节，明确性能指标（如登录响应时间 < 2s）、安全要求（如密码加密算法）、可用性目标（如系统可用性 99.9%）
- **细化验收标准**：将"登录成功"验收标准修改为"登录响应时间 < 2s，跳转首页，显示用户信息，记录登录日志；失败时显示错误提示（错误码 + 提示文案）"
- **统一术语**：全文搜索并替换"角色类型"为"用户角色"，确保术语一致性
- **补充权限矩阵示例**：在权限矩阵表格后增加2-3个实际场景示例，如"管理员可删除普通用户但不可删除其他管理员"
```

## 禁止事项

以下行为是禁止的，违反将导致输出无效：

1. ❌ 不使用四部分结构（Summary、Strengths、Issues、Recommendations）
2. ❌ 问题描述模糊（如"这里不太好"、"需要改进"）
3. ❌ 建议不可操作（如"优化一下"、"完善内容"）
4. ❌ 不标注问题位置（缺少章节号或具体位置）
5. ❌ 优点流于形式（如"整体不错"、"写得很好"）
6. ❌ 不读取 PRD 就直接生成评审（必须先读取待评审的 PRD）

## 常见问题处理

| 情况           | 处理方式                                                      |
| -------------- | ------------------------------------------------------------- |
| PRD 结构非标准 | 基于实际结构评审，在 Issues 中指出结构问题                    |
| 缺少功能需求   | 在 Issues 中列出缺失功能点，在 Recommendations 中说明补充方式 |
| 验收标准不明确 | 在 Issues 中指出模糊标准，在 Recommendations 中提供可量化建议 |
| PRD 质量极差   | 如实指出所有问题，提供系统性改进建议                          |
| PRD 质量很好   | 在 Strengths 中详细说明优点，Issues 可为空或仅列优化建议      |
