# 生成 MRD

将产品想法或需求描述转化为结构化的市场需求文档（MRD）。

## 输出规范（强制）

> **重要**：以下规范必须严格遵守，不可违反。

| 项目           | 规范                                                                       |
| -------------- | -------------------------------------------------------------------------- |
| **输出文件名** | `MRD.md`（必须使用此文件名，不可使用其他名称如"市场需求文档.md"）          |
| **文件数量**   | 只生成 1 个文件，禁止创建额外的说明文件或拆分文件                          |
| **文档结构**   | 必须严格按照 [mrd-template.md](references/mrd-template.md) 的 7 个章节结构 |

## 核心原则

1. **聚焦 Why 和 What**：MRD 关注问题定义、用户价值、业务目标，不涉及具体实现
2. **可量化**：成功标准必须有基线和目标值
3. **边界清晰**：明确做什么、不做什么
4. **边界交叉识别**：如果当前需求和用户提出的需求有边界上的交叉，必须明确描述出来
5. **状态和边界变化描述**：如果有状态或边界上的变化，必须详细描述变化后的规则和状态
6. **风险前置**：识别不确定点和风险

## 生成流程

### Step 0: 检查是否存在 Version Review 5 轮问答

- 如果存在用户已完成的 **5 轮问题与答案**，必须先参考 `version-review` 的产出文档（Q&A 记录与总结）
- MRD 的信息来源优先级为：**5 轮问答结果文档 > 用户当前输入 > 其他已知上下文**

### Step 1: 读取模板

首先读取 [mrd-template.md](references/mrd-template.md) 获取完整结构。

### Step 2: 收集信息

从用户输入中提取：

- 要解决的核心问题
- 目标用户是谁
- 典型使用场景
- 期望达成的目标
- 已知的约束条件
- **如存在 5 轮问答结果文档，必须优先从该文档中提取以上信息**
- **边界交叉情况**：当前需求与用户提出需求之间的边界交叉点（如有）
- **状态和边界变化**：识别是否存在状态或边界上的变化，如有则收集变化前后的对比信息

### Step 2.5: 检索知识库内容

在生成MRD前，必须检索以下知识库内容：

1. **业务规则**（docs/business-knowledge/）：
   - 检索与当前需求相关的业务规则
   - 确保新需求符合现有业务规则
   - 如果发现冲突，必须在第6章"不确定点和风险"中说明

2. **历史MRD**（docs-archive/mrd/）：
   - 检索类似需求的历史分析
   - 避免重复定义已分析的需求
   - 参考历史MRD中的问题定义、用户画像、成功标准

3. **术语定义**（docs/business-knowledge/）：
   - 检索相关术语的标准定义
   - 确保使用统一的术语表达
   - 必须使用知识库中的标准术语，不得自创同义词

4. **竞品分析**（docs-archive/mrd/）：
   - 检索相关的竞品分析内容
   - 参考竞品功能设计，标注参考来源

**检索方式**：

- 使用CLI工具在指定目录中搜索相关内容
- 对于每个章节，参考对应的知识类型（见章节知识映射）：
  - 第1章（背景与问题定义）：历史MRD、竞品分析、业务规则
  - 第2章（目标用户和场景）：历史PRD、历史MRD、术语定义
  - 第3章（目标与成功标准）：业务规则、历史MRD
  - 第4章（核心需求范围）：历史PRD、业务规则、功能清单、术语定义
  - 第5章（关键约束）：技术约束、业务规则、开发规范
  - 第6章（不确定点和风险）：历史MRD、技术约束
  - 第7章（备注）：竞品分析、技术约束、历史MRD

**知识库使用要求**：

- 在文档中引用知识库内容时，使用格式：> 📚 来源：[知识类型] - 文档名称
- 如发现冲突，必须在第6章"不确定点和风险"中说明：
  - 冲突点描述
  - 影响范围
  - 建议的解决方案
- 必须使用知识库中的术语定义，保持术语一致性
- 必须检查与现有功能的功能冲突，明确新功能与现有功能的关系

### Step 3: 按模板生成 MRD

依据模板的 7 个章节填充内容：

| 章节              | 核心要点                                                                                     |
| ----------------- | -------------------------------------------------------------------------------------------- |
| 1. 背景与问题定义 | 核心痛点、不解决的后果                                                                       |
| 2. 目标用户和场景 | 用户画像、2-3 个典型场景                                                                     |
| 3. 目标与成功标准 | 业务目标、可量化指标                                                                         |
| 4. 核心需求范围   | P0/P1 功能、明确不做的范围、**边界交叉情况**（如有）、**状态和边界变化**（如有，需详细描述） |
| 5. 关键约束       | 时间、技术、成本、合规约束                                                                   |
| 6. 不确定点和风险 | 待确认问题、已识别风险                                                                       |
| 7. 备注           | 竞品参考、技术参考、工程评估信息                                                             |

> **补充规则**：若存在 5 轮问答结果文档，MRD 必须基于该文档中的问答与结论生成，确保与 `version-review` 的结论一致。

### Step 4: 检查清单

- [ ] 核心问题定义清晰（2-3 个要点）
- [ ] 至少 2 个典型场景
- [ ] 成功标准有基线和目标值
- [ ] P0/P1 功能区分明确
- [ ] 明确列出不做的范围
- [ ] **边界交叉情况已识别和描述**（如有）
- [ ] **状态和边界变化已详细描述**（如有，包括变化前后的规则和状态对比）
- [ ] 风险和不确定点已识别

## 信息不足时的处理

| 缺失信息         | 处理方式                                          |
| ---------------- | ------------------------------------------------- |
| 用户规模不明     | 标注「待确认」，放入第 6 章                       |
| 成功指标无基线   | 建议指标类型，标注需补充基线数据                  |
| 约束不清晰       | 放入「待确认约束」                                |
| 竞品信息缺失     | 可省略或标注「待补充」                            |
| 状态变化规则不明 | 标注「待确认」，放入第 6 章，并说明需要补充的信息 |
| 边界变化细节不足 | 标注「待确认」，放入第 6 章，并说明需要补充的信息 |

## 状态和边界变化描述要求

当识别到状态或边界上的变化时，必须在第 4 章「核心需求范围」中详细描述：

1. **变化前状态**：描述变化前的规则、边界定义、状态机制
2. **变化后状态**：描述变化后的规则、边界定义、状态机制
3. **变化原因**：说明为什么需要这个变化
4. **影响范围**：说明这个变化会影响哪些功能、用户或业务流程
5. **迁移考虑**：如有需要，说明从旧状态迁移到新状态的注意事项（可选）

## 禁止事项

以下行为是禁止的，违反将导致输出无效：

1. ❌ 使用非 `MRD.md` 的文件名（如"市场需求文档.md"、"需求文档.md"等）
2. ❌ 创建多个文件（如一个说明文件+一个 MRD 文件）
3. ❌ 省略模板中的任何章节（即使信息不足也要标注"待确认"）
4. ❌ 输出不完整的占位符内容
