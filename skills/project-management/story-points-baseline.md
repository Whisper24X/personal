## 1. 故事点范围

### 1.1 可用故事点

故事点评估采用斐波那契数列的简化版本：

- **0个故事点**：纯运营/配置/极小改动（纯开发时间 < 0.5天）
- **1个故事点**：极简单任务（纯开发时间 0.5-1天）
- **2个故事点**：简单任务（纯开发时间 1-2天）
- **3个故事点**：标准任务（基准点，纯开发时间 2-3天）
- **5个故事点**：复杂任务（纯开发时间 3-5天）
- **8个故事点**：非常复杂的任务（纯开发时间 ≥5天，建议拆分）

### 1.2 范围说明

- **最小故事点**：0个故事点（纯配置/运营任务）
- **最大故事点**：8个故事点
- **超出范围**：如果任务超过8个故事点（纯开发时间 ≥5天），应拆分为多个任务

## 2. 敏捷估点档位定义

### 2.1 归属原则

故事点归属基于**纯开发时间**（实际编码时间）：

| 纯开发时间 | 故事点 | 说明                 |
| ---------- | ------ | -------------------- |
| < 0.5天    | 0点    | 纯配置/运营/极小改动 |
| 0.5-1天    | 1点    | 极简单任务           |
| 1-2天      | 2点    | 简单任务             |
| 2-3天      | 3点    | 标准任务（基准）     |
| 3-5天      | 5点    | 复杂任务             |
| ≥ 5天      | 8点    | 高复杂度（建议拆分） |

**说明**：

- **纯开发时间**：指实际编码时间
- **完整流程时间**：包含需求理解、技术方案、开发、自测、联调、测试、文档、Showcase等（不含提交和Code Review）
- 纯开发时间是归属的唯一依据

### 2.2 各档位详细定义

#### 0点（纯开发 < 0.5天）：纯运营/配置/极小改动

- **纯开发时间**：< 0.5天（< 4小时）
- **典型场景**：
  - 修改配置文件参数（如超时时间、开关状态）- 5-15分钟
  - 调整权限开关 - 5-10分钟
  - 修改文案内容 - 10-30分钟
  - 替换单个静态资源（图片、图标、logo）- 15-30分钟
  - 修改单个常量值 - 10-20分钟
  - 调整简单CSS样式（颜色、字号、间距）- 20-40分钟
  - 修复极简单bug（仅涉及1个文件，1-5行代码）- 1-2小时
- **特点**：无需编码或极少编码，无技术风险，几乎无测试工作量

#### 1点（纯开发 0.5-1天）：极简单任务

- **纯开发时间**：0.5-1天（4-8小时）
- **典型场景**：
  - 新增一个简单的静态页面（关于我们、帮助页面）- 4-6小时
  - 新增一个简单的表单页面（无后端交互）- 4-6小时
  - 实现一个简单的UI组件（按钮组、卡片等）- 3-5小时
  - 修复一个简单的bug（涉及2-3个文件）- 3-4小时
  - 新增简单的本地存储功能 - 3-4小时
- **特点**：涉及1-3个文件，不涉及复杂业务逻辑，通常无需前后端协作

#### 2点（纯开发 1-2天）：简单任务

- **纯开发时间**：1-2天（8-16小时）
- **典型场景**：
  - 新增多条件筛选功能（时间、状态、类型筛选）- 1-1.5天
  - 新增完整的表单页面（含前后端验证）- 1-1.5天
  - 新增简单的查询列表页面（分页 + 单条件筛选）- 1-1.5天
  - 新增用户个人信息编辑功能（含头像上传）- 1-2天
  - 实现简单的数据统计展示（图表组件）- 1-1.5天
- **特点**：涉及3-5个文件，需要简单的前后端协作，涉及1-2个接口

#### 3点（纯开发 2-3天）：标准任务（基准点）

- **纯开发时间**：2-3天（16-24小时）
- **典型场景**：
  - 应用更新功能（详见第3章）- 涉及5个接口，开发2-3天
  - 用户密码修改功能（含短信验证）- 涉及4个接口，开发2-3天
  - 简单的列表页面（增删改查 + 分页 + 多条件筛选）- 涉及4个接口，开发2-3天
  - 单一功能模块的完整实现 - 开发2-3天
- **特点**：涉及3-5个接口，需要前后端完整协作，包含1-2个UI页面

#### 5点（纯开发 3-5天）：复杂任务

- **纯开发时间**：3-5天（24-40小时）
- **典型场景**：
  - 消息通知系统（推送、列表、已读、分类、WebSocket）- 涉及7-8个接口，开发3-5天
  - 用户权限管理功能（角色、权限、分配）- 涉及6-7个接口，开发3-4天
  - 数据导入导出功能（文件上传、解析、校验、导出）- 涉及5-6个接口，开发3-4天
  - 工作流审批功能（提交、审批、驳回、流转）- 涉及7-8个接口，开发3-5天
- **特点**：涉及6-8个接口，需要多模块协作，包含3-4个UI页面

#### 8点（纯开发 ≥ 5天）：高复杂度任务（建议拆分）

- **纯开发时间**：≥ 5天（≥ 40小时）
- **典型场景**：
  - 订单管理系统（创建、支付、发货、退款、状态跟踪）- 涉及15+个接口
  - 支付集成功能（多支付方式、回调、对账、退款）- 涉及10+个接口
  - 复杂的工作流引擎（节点配置、流转规则、条件分支）- 涉及12+个接口
- **特点**：涉及10+个接口，业务逻辑非常复杂，**强烈建议拆分**为多个3-5点的子任务

## 3. 基准示例：应用更新功能（3个故事点）

### 3.1 需求概述

实现设备应用更新功能，包括：

- 显示待更新应用列表
- 支持单个和批量更新
- 显示更新状态（等待中、下载中、安装中等）
- 更新完成后自动刷新列表

### 3.2 后端任务（1.2个故事点）

#### 3.2.1 接口开发清单

1. **新增应用待更新列表查询接口**
   - 获取设备已安装应用信息
   - 过滤出需要更新的应用列表
   - 按版本更新时间倒序返回

2. **三方应用策略接口**
   - 通过应用状态返回对应的 buildNum
   - 如果是 prepareUpdate 状态，返回最新 buildNum

3. **应用更新接口修改**
   - 应用更新时，更新应用安装状态为 prepareUpdate

4. **新增批量应用更新接口**
   - 批量更新应用安装状态
   - 支持批量操作的事务处理

5. **已安装应用列表接口修改**
   - 新增待更新状态返回
   - 在应用信息中包含更新状态标识

#### 3.2.2 工作量说明

- 5个接口的开发、自测、联调
- 数据库查询优化
- 状态管理逻辑
- 错误处理和异常场景处理

### 3.3 客户端任务（1.2个故事点）

#### 3.3.1 开发任务清单

1. **不同状态的UI显示**
   - 待更新：显示"更新"按钮
   - 下载中：显示下载进度（如"40%"）
   - 下载暂停：显示"继续"按钮
   - 安装中：显示"安装中"（不可点击）
   - 下载等待中：显示"等待中"（不可点击）
   - 安装成功：从列表中移除

2. **接口对接**
   - 获取待更新应用列表接口对接
   - UI展示和空数据页面展示
   - 批量更新请求接口对接
   - 请求完成后发送下载事件

3. **更新完页面刷新**
   - 监听应用安装完成广播
   - 刷新UI页面
   - 更新应用状态显示

#### 3.3.2 工作量说明

- UI界面开发（多种状态展示）
- 接口对接和数据绑定
- 状态管理和页面刷新逻辑
- 用户体验优化

**备注**：

- 具体的下载逻辑、与管控进程通信的逻辑不计算在此需求内
- 默认这些功能已经提供好了

### 3.4 测试任务（0.6个故事点）

#### 3.4.1 测试用例编写

- 功能测试用例：单个更新、批量更新、状态切换
- 边界条件测试：空列表、网络异常、安装失败
- 异常场景测试：并发更新、状态冲突

#### 3.4.2 测试执行

- 后端接口测试
- 前端功能测试
- 前后端联调测试
- 回归测试

## 4. 评估方法

### 4.1 核心原则

故事点归属的**唯一标准是纯开发时间**：

- 纯开发时间 < 0.5天 → 0个故事点
- 纯开发时间 0.5-1天 → 1个故事点
- 纯开发时间 1-2天 → 2个故事点
- 纯开发时间 2-3天 → 3个故事点（基准）
- 纯开发时间 3-5天 → 5个故事点
- 纯开发时间 ≥ 5天 → 8个故事点（建议拆分）

**重要说明**：

- **纯开发时间**：指实际编码时间，不包括需求理解、技术方案、测试、文档等
- 复杂度评估（接口数量、UI页面数等）仅作为**辅助工具**，用于帮助估算纯开发时间
- 不能直接根据复杂度确定故事点，必须先估算纯开发时间，再归属故事点

### 4.2 评估流程

#### 步骤1：估算纯开发时间

根据需求内容，估算实际编码所需时间：

1. **分析需求内容**
   - 识别需要开发的接口、页面、组件
   - 识别业务逻辑复杂度
   - 识别技术难点和依赖

2. **参考复杂度维度**（辅助工具）

   使用以下维度帮助估算开发时间：

   | 维度         | 参考开发时间范围  | 说明                     |
   | ------------ | ----------------- | ------------------------ |
   | **接口数量** | 1-2个：0.5-1天    | 简单接口，纯开发时间较短 |
   |              | 3-5个：2-3天      | 标准接口，纯开发时间中等 |
   |              | 6-8个：3-5天      | 复杂接口，纯开发时间较长 |
   |              | 9+个：≥5天        | 非常复杂，建议拆分       |
   | **UI页面数** | 1个：0.5-1天      | 简单页面                 |
   |              | 2-3个：1-2天      | 标准页面                 |
   |              | 4-5个：2-3天      | 复杂页面                 |
   |              | 6+个：≥3天        | 非常复杂，建议拆分       |
   | **业务逻辑** | 简单CRUD：0.5-1天 | 简单逻辑                 |
   |              | 中等复杂度：2-3天 | 标准逻辑                 |
   |              | 复杂流程：3-5天   | 复杂逻辑                 |
   |              | 非常复杂：≥5天    | 建议拆分                 |

   **注意**：以上时间仅为参考，实际估算需要结合具体需求和技术栈。

3. **综合估算纯开发时间**
   - 前端开发时间 + 后端开发时间 + 联调时间 = 总纯开发时间
   - 考虑技术难度、团队熟悉度等因素调整

#### 步骤2：归属故事点

根据估算的纯开发时间，按照第2章的归属原则确定故事点：

- 如果纯开发时间在边界值（如0.5天、1天、2天等），建议向上取整
- 如果纯开发时间 ≥ 5天，强烈建议拆分为多个子任务

#### 步骤3：需求拆分（如需要）

如果估算的纯开发时间 ≥ 5天（对应8个故事点），建议拆分：

1. **按功能模块拆分**
   - 将大需求拆分为多个独立的功能模块
   - 每个模块单独估算纯开发时间并归属故事点

2. **按前后端拆分**
   - 前端和后端分别估算纯开发时间
   - 分别归属故事点（但通常前后端需要协作，不建议完全分离）

### 4.3 评估示例

#### 示例0：配置类任务（0个故事点）

**需求**：修改应用配置文件中的超时参数从30秒改为60秒

**评估**：

- 工作内容：仅修改配置文件，无需编码
- 风险：无
- 纯开发时间：5-10分钟
- **评估结果**：纯开发时间 < 0.5天 → 0个故事点

#### 示例1：极简单任务（1个故事点）

**需求**：新增一个简单的静态页面（关于我们页面）

**评估**：

- 接口数量：0个
- UI修改：新增1个简单的静态页面
- 业务逻辑：无
- 纯开发时间：0.5-1天（页面开发 + 路由配置 + 样式调整）
- **评估结果**：纯开发时间 0.5-1天 → 1个故事点

#### 示例2：简单任务（2个故事点）

**需求**：在用户列表页面新增多条件筛选功能（按时间、状态、类型筛选）

**评估**：

- 接口数量：1个（修改现有查询接口，增加多个筛选参数）
- UI修改：增加多个筛选组件（日期选择器、下拉框、搜索框）
- 业务逻辑：筛选条件组合、联动查询
- 纯开发时间：1-2天（前端1天 + 后端0.5天 + 联调0.5天）
- **评估结果**：纯开发时间 1-2天 → 2个故事点

#### 示例3：标准任务（3个故事点）

**需求**：应用更新功能（基准示例）或用户密码修改功能（含短信验证）

**评估**：

- 接口数量：4-5个
- UI页面：1-2个
- 业务逻辑：中等复杂度
- 纯开发时间：2-3天（前端1天 + 后端1.5天 + 联调0.5天）
- **评估结果**：纯开发时间 2-3天 → 3个故事点（基准）

#### 示例4：复杂任务（5个故事点）

**需求**：消息通知系统（推送、列表、已读、分类、实时推送）

**评估**：

- 接口数量：7-8个
- UI页面：3个（消息中心、消息详情、消息设置）
- 业务逻辑：复杂（消息状态管理、WebSocket连接）
- 数据表：2-3张
- 纯开发时间：3-5天（前端2天 + 后端2天 + WebSocket集成 + 联调）
- **评估结果**：纯开发时间 3-5天 → 5个故事点

#### 示例5：高复杂度任务（8个故事点）

**需求**：完整的订单管理系统，包括订单创建、支付、发货、退款、状态跟踪等

**评估**：

- 接口数量：15+个
- UI页面：6+个
- 业务逻辑：非常复杂（订单状态机、支付流程、库存管理）
- 数据表：6+张
- 纯开发时间：≥ 5天（前端3天 + 后端3天 + 联调1天）
- **评估结果**：纯开发时间 ≥ 5天 → 8个故事点（**强烈建议拆分**为多个3-5点子任务）

## 5. 使用说明

### 5.1 评估流程

按照以下步骤进行故事点评估：

1. **理解需求**
   - 明确需求范围和目标
   - 识别需要开发的功能模块
   - 识别技术依赖和难点

2. **估算纯开发时间**
   - 分析需要开发的接口、页面、组件
   - 参考复杂度维度（接口数量、UI页面数、业务逻辑等）辅助估算
   - 估算前端开发时间、后端开发时间、联调时间
   - 综合得出总纯开发时间

3. **归属故事点**
   - 根据纯开发时间，按照第2章的归属原则确定故事点
   - 如果纯开发时间 ≥ 5天，建议拆分为多个子任务

4. **团队评审**
   - 评估结果需团队评审确认
   - 确保评估标准的一致性

### 5.2 注意事项

- ✅ **纯开发时间是唯一标准**：故事点归属必须基于纯开发时间，不能直接根据复杂度确定
- ✅ **复杂度评估是辅助工具**：接口数量、UI页面数等维度仅用于帮助估算开发时间
- ✅ **拆分原则**：如果纯开发时间 ≥ 5天（对应8个故事点），应拆分为多个任务
- ✅ **评估一致性**：团队应统一理解"纯开发时间"的定义，确保评估标准一致

**归属原则**（基于纯开发时间）：

- 纯开发时间 0.5-1天 → 1个故事点
- 纯开发时间 1-2天 → 2个故事点

### 6.2 常见问题

**Q1：如果需求只有前端或只有后端，如何评估？**

A：估算纯开发时间，然后归属故事点。例如：

- 如果只有前端，估算前端开发的纯开发时间（如1.5天），则归属为2个故事点
- 如果只有后端，估算后端开发的纯开发时间（如2.5天），则归属为3个故事点
- **不能**直接按比例分配故事点，必须基于纯开发时间

**Q2：如果需求涉及多个端（Web、移动端、小程序），如何评估？**

A：每个端单独估算纯开发时间并归属故事点，然后汇总。例如：

- Web端纯开发时间2天 → 2个故事点
- 移动端纯开发时间2.5天 → 3个故事点
- 总计5个故事点，但建议拆分为两个独立任务

**Q3：如果需求包含性能优化，如何评估？**

A：性能优化的纯开发时间单独估算并归属故事点。例如：

- 功能开发纯开发时间2天 → 2个故事点
- 性能优化纯开发时间1天 → 1个故事点
- 总计3个故事点

**Q4：如果需求涉及第三方集成，如何评估？**

A：估算第三方集成的纯开发时间，然后归属故事点。例如：

- 如果第三方集成简单（如调用API），纯开发时间0.5天 → 1个故事点
- 如果集成复杂（如需要深度定制），纯开发时间2天 → 2个故事点
- 与功能开发的故事点相加得到总故事点

**Q5：如果涉及技术债务或重构，如何评估？**

A：估算重构的纯开发时间，然后归属故事点。例如：

- 轻微重构纯开发时间0.5天 → 1个故事点
- 中等重构纯开发时间1.5天 → 2个故事点
- 与功能开发的故事点相加得到总故事点

**Q6：如果存在不确定性或风险，如何评估？**

A：不确定性或风险会影响纯开发时间的估算。建议：

- 低风险：按正常估算纯开发时间
- 中风险：在估算纯开发时间时适当增加缓冲（如增加20-30%）
- 高风险：先解决风险，再估算纯开发时间
