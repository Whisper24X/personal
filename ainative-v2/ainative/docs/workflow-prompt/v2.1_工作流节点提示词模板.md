# v2.1 工作流节点提示词模板

这份文档面向**当前版本**的工作流模板能力，不再沿用 `v1_CLI执行真实提示词.md` 里那种"后端写死一句话 skill 触发词"的方式。

当前版本的实际执行模型是：

```text
最终发给 Agent 的 prompt =
节点级 prompt(node.input.prompt / nodeInput)
+
依赖状态报告(后端自动注入，仅 V2 标准节点)
+
续写消息(runtime.pendingUserMessage，仅在继续对话时出现)
+
项目记忆(memoryBlock，如果启用)
```

也就是说：

- 任务级 prompt 适合放"原始需求、业务背景、统一约束"，供节点 prompt 通过变量显式引用
- 节点级 prompt 适合放"这个节点此刻要做什么"，实际执行时只会发送节点级 prompt
- 节点级 prompt 可以引用工作流变量
- 后端会在 prompt 组装时自动注入上游依赖状态报告（V2 标准节点），Agent 无需自行探测上游文件是否存在

另外，这一版模板按你的要求统一采用**技能驱动**方式设计：

- 所有节点都可以使用技能处理
- 节点 prompt 应明确告诉 Agent 优先使用哪个技能
- 如果一个节点本身就是多阶段执行，则允许在一个节点内按顺序调用多个技能

## 1. 当前版本可直接使用的变量

支持以下变量：

```text
{{taskId}}
{{taskTitle}}
{{taskPrompt}}
{{gitBranch}}
{{gitBaseBranch}}
{{gitWorktree}}
{{gitWorktreePath}}
{{projectId}}
{{projectName}}
{{projectGitUrl}}
{{projectDefaultBranch}}
```

建议：

- `{{taskPrompt}}` 放原始需求正文
- `{{taskTitle}}` 放任务标题
- `{{projectName}}`、`{{gitBranch}}`、`{{gitWorktreePath}}` 放执行上下文

文档产出目录建议统一按分支隔离：

```text
docs/{{gitBranch}}/
```

这样同一项目下不同任务分支的 MRD / PRD / TEST / DESIGN / 原型 / 部署记录不会互相覆盖。

## 2. 建议的任务级 Prompt 写法

创建任务时，`task.prompt` 建议写成这类内容，而不是把所有节点说明都塞进去：

```text
目标：
<一句话描述这次要交付什么>

业务背景：
<为什么做这件事，给谁用，解决什么问题>

范围要求：
- <范围 1>
- <范围 2>

交付要求：
- 需要产出 MRD / PRD / 原型 / 测试 / 设计 / 代码 / 部署结果

约束：
- 遵循当前仓库既有技术栈与代码风格
- 优先复用现有实现，不要凭空发明不存在的基础设施
- 若需求存在冲突或信息不足，先在文档中标注假设与待确认项
```

下列模板是**节点级 Prompt**，可以直接填到工作流模板节点的 `input.prompt`。

技能映射建议如下：

```text
Brainstorm -> brainstorm
WriteMRD -> mrd
WritePRD -> prd
GeneratePrototype -> prototype
WriteTest -> test
WriteDesign -> design

WriteCode -> code-task-apply / code-evaluate-completion / code-task-check
ImproveCode -> improve-review / improve-analyze / improve-execute / improve-verify

TESTPathGuide（自动化就绪） -> path-guide
TESTPlaywright（浏览器自动化） -> playwright-skill
```

## 2.5 上下文继承协议

所有节点共享同一个 git worktree，通过 `docs/{{gitBranch}}/context-snapshot.md` 维护跨节点的累积上下文。每个节点在执行阶段（非审批阶段）负责读取和写入。

**读取规则**（节点开始时）：

1. 读取 `docs/{{gitBranch}}/context-snapshot.md`（上游节点的累积上下文）
2. 检查本节点所需的上游产物是否存在（后端会在 prompt 中注入依赖状态报告，显示 valid / thin / missing）
3. 对于 valid 的产物，正常读取使用
4. 对于 thin 或 missing 的产物，按以下优先级降级：
   - 优先从 context-snapshot.md 中提取相关摘要
   - 其次从 `{{taskPrompt}}` 原始需求中推导
   - 最后做最小必要假设，并在"假设与待确认项"中标注来源

**写入规则**（节点完成时）：

将关键决策摘要追加到 `docs/{{gitBranch}}/context-snapshot.md`，格式：

```text
## [节点名] - [时间戳]
### 关键决策
- ...
### 核心产出摘要
- ...
### 未解决项（如有）
- ...
```

**注意**：context-snapshot 在 Agent 执行中写入。如果节点因产物校验失败进入 `in_review`，用户审批后后端只推进状态，不会再跑 Agent 补写 snapshot。

## 2.6 产物自检协议

每个文档产出节点在完成主任务后，必须自检预期输出文件。

**自检流程**：

1. 检查预期输出文件是否存在（路径见各节点的"输出文件"说明）
2. 检查文件内容是否非空且包含有效结构（不是空文件或仅有标题）
3. 如果检查不通过：
   - 分析原因（上游信息不足 / 技能执行异常 / 路径错误）
   - 基于可用上下文重新生成该文件
   - 在文件开头标注 `<!-- 自检补生成：[原因] -->`
4. 最终确保文件存在且内容有效后，方可结束节点

**后端兜底**：如果 Agent 自检仍未生成有效产物，后端会通过 V2 契约校验拦截节点进入 `in_review`，通知用户产物缺失详情。

## 2.7 渐进自主与提问预算协议

每个节点标注一个自主级别（Tier），控制 Agent 是否可以向用户提问。

**Tier 1 -- 交互型（Brainstorm、WriteMRD）**：
- 必须向用户提问来澄清需求
- 每个问题**必须附带 AI 推荐选项**
- 若用户不回复，按推荐选项继续

**Tier 2 -- 半自主型（WritePRD、WriteDesign、ProjectManager）**：
- 仅在遇到"阻断性未知"时允许提问（技术路线选择、需求范围严重模糊）
- 其他不确定性由 AI 自行决策，决策记录在产出文档的"AI 决策记录"小节中
- 提问时同样必须附带建议选项

**Tier 3 -- 全自主型（其余节点）**：
- **禁止向用户提问**
- 所有不确定性基于上游上下文 + context-snapshot 自行解决
- 假设记录在产出文档的"假设与待确认项"中

**建议式提问格式**（Tier 1 和 Tier 2 必须遵循）：

```text
每个问题按以下格式输出：

> **[问题标题]**
> [问题描述，1-2 句]
>
> - A. [选项 A] -- [简要理由] -- **推荐**
> - B. [选项 B] -- [简要理由]
> - C. [选项 C] -- [简要理由]
>
> 若您不做选择，我将采用推荐选项继续。

规则：
- 每次最多 3 个问题
- 每个问题必须有推荐选项
- 若用户未回复，按推荐选项继续执行
```

## 2.8 结果文件最小格式协议

以下结果文件不走 Markdown 厚度校验，使用固定行格式：

**`taskResult.md`**（WriteCode 产出）：

```text
第 1 行：状态（已完成 / 未完成 / 部分完成）
第 2 行：原因摘要（一句话说明）
```

**`improveVerifyResult.md`**（ImproveCode 产出）：

```text
第 1 行：状态（已完成 / 未完成 / 部分完成）
第 2 行：原因摘要（一句话说明）
第 3 行：详情（可选，补充说明）
```

后端校验规则：首行和次行均非空即为有效。

- `maxLoops: 1`

## 5. 使用建议

### 5.1 基础原则

- 任务级 prompt 只放"全局上下文"，不要把各节点说明全都塞进任务级
- 需求不够稳定或信息不完整时，把 `Brainstorm` 放在第一个环节
- 节点级 prompt 只放该节点职责，并明确对应技能，避免一个节点同时承担分析、设计、编码、部署所有职责
- `WriteCode`、`ImproveCode`、`Deploy`、`TESTPlaywright` 才比较适合开循环
- 上游文档路径尽量固定，这样下游节点才能稳定引用

### 5.2 3+1 防护机制

本版模板配合后端 V2 节点契约校验，形成 3+1 防护：

**+ 依赖状态报告（节点执行前）**：后端自动扫描上游文件状态（valid / thin / missing），注入到 prompt 中。Agent 不需要自己探测上游文件是否存在。

**第一层 -- Prompt 产物自检（Agent 执行中）**：每个节点 prompt 中要求 Agent 完成后自检产物文件是否存在且有效。不通过则当场重新生成。

**第二层 -- V2 契约校验（节点执行后）**：后端按节点名匹配 V2 契约，精确检查指定文件是否存在且结构有效（Markdown 厚度、HTML 结构、结果文件行格式）。不通过则节点进入 `in_review`，通知用户缺失详情。

**第三层 -- context-snapshot 累积上下文（Agent 执行中）**：每个节点在执行过程中将关键决策写入 `context-snapshot.md`。即使某个节点产物质量不高，下游节点仍有累积上下文可参考。

### 5.3 审批与产物的关系

- `requiresApproval: true` 的节点：Agent 执行完 -> 人工审批 -> 才推进到下一个节点
- `requiresArtifact: true` 的节点：Agent 执行完 -> 后端校验产物 -> 产物无效则进入 `in_review` 等待用户审核
- 两者可以同时开启，`requiresApproval` 优先级更高（先过审批门）
- 建议 3.1-3.9 都开启 `requiresArtifact: true`，确保 V2 契约校验生效

### 5.4 提问策略

- Tier 1 节点（Brainstorm、WriteMRD）：鼓励提问，但必须给建议选项
- Tier 2 节点（WritePRD、WriteDesign、ProjectManager）：只在阻断性未知时提问
- Tier 3 节点（其余）：禁止提问，自行决策并记录假设
- 所有提问必须附带 AI 推荐选项，用户不回复按推荐继续

### 5.5 context-snapshot 注意事项

- context-snapshot 在 Agent 执行中写入，审批动作不会补写
- 如果一个节点因产物缺失进入 `in_review`，但 Agent 已在执行中写了 snapshot，那么审批通过后下游仍然能读到 snapshot
- 如果 Agent 连 snapshot 都没写就失败了，下游只能依赖 `{{taskPrompt}}` 原始需求兜底

## 6. 与 v1 的关系

`v1_CLI执行真实提示词.md` 记录的是旧版默认工作流里"后端实际发给 CLI 的固定提示词"。

这份文档给的是**当前版本工作流模板可直接填写的节点 Prompt 模板**。两者的核心差异是：

- v1：后端 action 写死 prompt
- v2：由节点 prompt 主导执行，任务 prompt 通过 `{{taskPrompt}}` 等变量在节点中按需引用

如果你要在当前版本里复刻旧版流程，优先使用本文件中的节点模板，而不是直接照搬 v1 里那几句短 prompt。
