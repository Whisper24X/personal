# Code Task Check Validator

检查 `openspec/changes/*/tasks.md` 文件中的任务是否全部执行完成，并将结果写入文件。

## 输出规范

**文档路径**：输出路径**必须**从 prompt 获取（如 `docs/{{gitBranch}}/taskResult.md`）。

## 完成判断规则

**只有标记为 `- [x]` 的任务才算完成，其他一律不算完成。**

- `- [x]` → 已完成
- `- [ ]` → 未完成（无论描述中写了什么）

## 输出方式

**必须将结果写入文件**（路径由 prompt 指定，如 `docs/{{gitBranch}}/taskResult.md`），文件内容固定两行：

```
{状态}
{原因}
```

其中 `{状态}` 必须是：`已完成` | `未完成` | `未找到`（三选一）

## 检查步骤

### Step 1：任务完成状态检查

1. 使用 glob 查找 `openspec/changes/*/tasks.md` 文件
2. 如果文件不存在 → 写入"未找到"状态，结束
3. 读取文件内容，统计 `- [x]` 和 `- [ ]` 任务数量
4. 存在 `- [ ]` → 写入"未完成"状态，**不做服务检查**，结束
5. 全部 `- [x]` → 进入 Step 2

### Step 2：各端服务健康检查（仅在全部任务 [x] 时执行）

#### 2.1 判断是否有 sandbox 环境

检查 `sandbox/supervisord.conf` 是否存在：
- 不存在 → 跳过服务检查，直接进入 Step 3 写"已完成"

#### 2.2 读取项目配置，自主发现服务信息

读取以下配置，自主理解当前项目的服务结构：

- `sandbox/supervisord.conf`：了解有哪些服务进程、各自的日志文件路径
- `sandbox/.env`：了解端口、访问地址等环境变量
- `sandbox/nginx.conf`（如存在）：了解各服务的路由规则和统一入口

根据以上配置，自主判断：
- 项目包含哪些服务
- 各服务对应的日志文件在 `./logs/` 下的路径
- 各服务的访问入口地址（统一端口、各自路径）

#### 2.3 读取日志，判断各服务当前状态

读取 `./logs/` 目录下各服务的日志文件，由 AI 自主分析每个服务的当前状态：

- **正在构建/启动中**：日志有构建进行中的迹象，但尚无完成或报错信号
- **启动成功**：日志显示服务已就绪、正在监听
- **启动失败/报错**：日志中有明确的错误信息、异常堆栈、编译失败等

> AI 根据日志内容自主判断，不依赖预设的特定关键词或框架信号。

#### 2.4 针对不同状态采取对应策略

| AI 判断的服务状态 | 策略 |
|----------------|------|
| 正在构建/启动中 | 等待 10 秒后重新读日志，最长等待 60 秒；超时后按当前日志内容判断 |
| 启动成功 | 对该服务发起 curl 访问验证（重试 3 次，间隔 5 秒）；2xx/3xx 为正常，否则异常 |
| 启动失败/报错 | 直接记录为异常，保留日志错误内容 |

#### 2.5 操作 tasks.md 中的"服务修复"区块

| 检查结果 | tasks.md 中是否有"服务启动修复"区块 | 操作 |
|---------|-------------------------------|------|
| 全部服务正常 | 有（`[x]`）或无 | 不动 tasks.md |
| 有服务异常 | 无 | 在文件末尾追加新区块 + `[ ]` 任务 |
| 有服务异常 | 有，且是 `[ ]` | 原地更新任务描述（覆盖为最新日志） |
| 有服务异常 | 有，且是 `[x]` | 重置为 `[ ]`，更新任务描述为最新日志 |

**追加/更新格式**（异常端附上日志，正常端简单标注）：

```markdown
## 服务启动修复（自动追加）

- [ ] 修复服务启动异常，请根据以下日志分析并修复：

  **[服务名]**：访问失败
  ```
  [该服务日志最后 80 行原文]
  ```

  **[服务名]**：正常
```

**严格约束**：tasks.md 中"服务启动修复"区块**始终最多一个**，异常时追加或更新，不重复新增。

### Step 3：写入结果

将结果写入 prompt 指定的路径（如 `docs/{{gitBranch}}/taskResult.md`），固定两行。

## 写入示例

```
已完成
所有 23 个任务已标记为 [x]
```

```
已完成
所有 23 个任务已标记为 [x]，各端服务均正常启动
```

```
未完成
3 个任务未标记为 [x]：任务 2.1、3.4、3.6
```

```
未完成
所有任务已标记为 [x]，但后端服务访问失败，已附日志至 tasks.md 修复任务，请根据日志排查
```

```
未找到
openspec/changes/ 目录不存在
```

## 重要提醒

1. **必须写入文件**：结果必须写入 prompt 指定的路径，不是输出到终端
2. **文件格式固定**：只有两行，第一行是状态，第二行是原因
3. **确保目录存在**：若输出目录不存在，需先创建
4. **服务检查仅在全部 [x] 时触发**：有未完成任务时直接写"未完成"，不做服务检查
5. **服务与入口自主发现**：从 supervisord.conf、.env、nginx.conf 等配置中自主识别服务结构，不依赖硬编码的服务名或路径
6. **日志状态由 AI 自主判断**：不预设关键词，AI 根据日志内容自行区分"构建中"、"启动成功"、"报错"三种状态
7. **服务修复区块唯一性**：tasks.md 中"服务启动修复"区块始终最多一个，异常时追加或更新，不重复追加
