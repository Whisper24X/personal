# MRD 转 PRD

将 MRD 转换为符合团队规范的 AI-first PRD 文档。

## 输出规范（强制）

> **重要**：以下规范必须严格遵守，不可违反。

| 项目           | 规范                                                                        |
| -------------- | --------------------------------------------------------------------------- |
| **输出文件名** | `PRD.md`（必须使用此文件名，不可使用其他名称如"产品需求文档.md"）           |
| **文件数量**   | 只生成 1 个文件，禁止创建额外的说明文件或拆分文件                           |
| **文档结构**   | 必须严格按照 [prd-template.md](references/prd-template.md) 的 16 个章节结构 |

## 核心原则

1. **PRD 关注 What / Why / Experience / Rules**，不写代码与技术选型
2. **减少自由发挥空间**：每个需求点必须明确、可验收
3. **P0 功能必须完整**：用户目标、系统行为、体验约束、验收标准缺一不可
4. **不确定项只能出现在「15. 开放问题」**

## 转换流程

### Step 1: 读取模板 + 分析 MRD

首先读取 [prd-template.md](references/prd-template.md) 获取完整的 PRD 结构和填写规范。

同时从 MRD 中提取：

- 目标用户与核心问题
- 市场机会与业务目标
- 关键假设与验证方式
- 功能范围与优先级

### Step 2: 检索知识库内容

在生成 PRD 前，检索以下知识库内容以确保一致性和合规性：

1. **历史 PRD**（docs-archive/prd/）：复用现有流程命名、状态定义、数据模型，确保新功能与现有功能一致
2. **业务规则**（docs/business-knowledge/）：确保功能设计符合业务规则，规则需可编码、可测试
3. **技术约束**（docs/dev-spec/）：确保功能设计在技术边界内，性能指标需在技术边界内
4. **现有功能**（代码实现 + docs-archive/prd/）：明确新功能与现有功能的关系（扩展/替代/并行），并用于撰写 2.2 的「当前实现」差异比对
5. **术语定义**（docs/business-knowledge/）：必须使用知识库中的标准术语，不得自创同义词

**冲突处理**：如检索到历史知识与当前 MRD 存在冲突，必须在 PRD 第 2.3.2 章"知识库冲突标注"中显式说明：

- **冲突类型**：逻辑冲突 / 功能冲突 / 数据口径冲突 / 术语冲突
- **冲突描述**：历史知识的已有定义 vs. 当前 MRD 的新需求
- **影响范围**：涉及模块、端、用户角色
- **建议处理方式**：沿用历史定义 / 按新需求覆盖 / 需人工决策（标注 Owner）

若无冲突，第 2.3.2 章填写"无"，禁止留空。

### Step 3: 按模板生成 PRD

依据模板的 16 个章节结构填充内容，确保：

- **2.2 现状与动因**：必须通过比对「当前代码/实现所体现的产品行为」与「本次需求/改动」完成**前后差异**描述；撰写时结合现有功能/代码实现（来自检索或工作区）与本次 MRD/需求描述的改动；**禁止使用技术用语**，必须让非技术人员能直接读懂。
- 每个 P0 功能包含完整的 A-E 规格（用户视角、系统行为、体验约束、验收标准、数据归因）
- 第 4 章体验规格完整（UX 指标、MUST 原则、UI 约束）
- 不确定项仅出现在第 15 章

### Step 4: 验收检查

- [ ] 所有 P0 功能都有完整规格
- [ ] 每个 KPI 都有对应埋点事件
- [ ] 验收标准具体、可测试
- [ ] 无技术实现细节

## 常见问题处理

| 情况             | 处理方式                         |
| ---------------- | -------------------------------- |
| MRD 缺少用户画像 | 在第 15 章标记为开放问题         |
| MRD 无明确 KPI   | 根据业务目标推导，标注需确认     |
| 功能边界模糊     | 主动明确 In Scope / Out of Scope |
| 体验要求不清晰   | 填充默认 MUST 原则，标注需评审   |

## 禁止事项

1. ❌ 使用非 `PRD.md` 的文件名（如"产品需求文档.md"、"需求规格.md"等）
2. ❌ 省略模板中的任何章节（16 个章节必须完整）
3. ❌ 包含技术实现细节（代码、技术选型等）
4. ❌ **2.2 现状与动因**使用技术用语（接口名、字段名、实现术语等）；该节必须让非技术人员能直接读懂
