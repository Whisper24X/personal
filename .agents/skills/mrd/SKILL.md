# 生成 MRD

将产品想法或需求描述转化为结构化的市场需求文档（MRD）。

## 输出规范（强制）

> **重要**：以下规范必须严格遵守，不可违反。

| 项目           | 规范                                                                       |
| -------------- | -------------------------------------------------------------------------- |
| **输出文件名** | `MRD.md`（必须使用此文件名，不可使用其他名称如"市场需求文档.md"）          |
| **文件数量**   | 只生成 1 个文件，禁止创建额外的说明文件或拆分文件                          |
| **文档结构**   | 必须严格按照 [mrd-template.md](references/mrd-template.md) 的 5 个章节结构 |

## 核心原则

1. **聚焦 Why 和 What**：MRD 关注问题定义、用户价值、业务目标，不涉及具体实现
2. **可量化**：成功标准必须有基线和目标值
3. **边界清晰**：明确做什么、不做什么
4. **边界交叉识别**：如果当前需求和用户提出的需求有边界上的交叉，必须明确描述出来
5. **状态和边界变化描述**：如果有状态或边界上的变化，必须详细描述变化后的规则和状态
6. **风险前置**：识别不确定点和风险

## 生成流程

### Step 0: 检查是否存在版本评审总结文档

**检测逻辑**：

- 扫描 `docs/version-review/` 目录，查找匹配 `*-review-summary.md` 的文件
- 如存在，读取最新一份（按修改时间排序）
- 路径相对于当前版本工作区根目录（如 `docs/version-review/`）

**评审总结到 MRD 章节映射**：

| 评审总结部分          | MRD 章节         | 用途说明             |
| --------------------- | ---------------- | -------------------- |
| 版本信息 > 版本想法   | 第1章 问题与背景 | 核心问题定义         |
| 问答记录（全部 5 轮） | 第1-5章          | 通用上下文与决策依据 |
| 评审结论 > 冲突分析   | 第5章 约束与风险 | 已识别冲突与风险     |
| 评审结论 > 建议       | 第3章 需求范围   | P0/P1 功能与需求点   |
| 评审结论 > 行动项     | 第3章 需求范围   | 作为功能需求点       |

**优先级规则**：

- 评审总结中的结论 **优先于** 用户当前输入（冲突时以评审结论为准）
- MRD 信息来源优先级：**评审总结文档 > 用户当前输入 > 其他已知上下文**

**一致性检查**：

- MRD 不得与评审中用户已确认的决策矛盾（如用户选择的「方案 A」、术语统一约定等）

### Step 1: 读取模板

首先读取 [mrd-template.md](references/mrd-template.md) 获取完整结构。

### Step 2: 收集信息

**如存在评审总结文档**（`docs/version-review/*-review-summary.md`），必须优先从中提取：

- **用户已确认的决策**：如选择了哪个方案（方案 A/B/C）、最终采纳的规则
- **已识别的冲突及解决方案**：从「冲突分析」和「建议」中提取
- **第 3 轮术语统一协议**：各场景下的术语区分、帮助文案中的统一用词等
- **第 4 轮业务数据/系统兼容性关注点**：降级展示规则、导出逻辑、性能考虑等

**从用户输入中提取**（无评审总结时，或作为补充）：

- 要解决的核心问题
- 目标用户是谁
- 典型使用场景
- 期望达成的目标
- 已知的约束条件
- **边界交叉情况**：当前需求与用户提出需求之间的边界交叉点（如有）
- **状态和边界变化**：识别是否存在状态或边界上的变化，如有则收集变化前后的对比信息

### Step 2.5: 检索知识库内容

在生成MRD前，必须检索以下知识库内容：

1. **业务规则**（`docs/business/`，如目录为空则补充使用 `docs/dev-spec/README.md` 与各子项目规范）：
   - 检索与当前需求相关的业务规则
   - 确保新需求符合现有业务规则
   - 如果发现冲突，必须在第5章"约束与风险"中说明

2. **历史上下文**（`docs/version-review/` 中已有总结文档，或其他现存文档）：
   - 优先检索历史版本评审总结
   - 避免重复定义已确认过的需求边界
   - 参考已有文档中的问题定义、用户场景、成功标准

3. **术语定义**（`docs/business/`，如缺失则补充使用 `docs/dev-spec/` 与现有评审文档）：
   - 检索相关术语的标准定义
   - 确保使用统一的术语表达
   - 必须使用知识库中的标准术语，不得自创同义词

4. **系统约束与开发规范**（`docs/dev-spec/` 与 `knowledge/`）：
   - 检索相关的系统边界、实现约束和已有规范
   - 用于识别需求范围、限制条件与风险来源
   - 如引用，必须标注具体来源文件

5. **缺失处理要求**：
   - 如仓库中不存在历史 MRD、竞品分析或专项业务资料，必须明确标注“资料缺失”或“仓库未提供”
   - 不得因为目录约定存在于旧规则中，就臆造不存在的文档内容

**检索方式**：

- 使用CLI工具在指定目录中搜索相关内容
- 对于每个章节，参考对应的知识类型（见章节知识映射）：
  - 第1章（问题与背景）：版本评审总结、业务规则、历史上下文
  - 第2章（目标用户与场景）：版本评审问答、历史上下文、术语定义
  - 第3章（需求范围）：版本评审建议与行动项、业务规则、系统约束与开发规范、术语定义
  - 第4章（目标与成功标准）：版本评审行动项、业务规则、历史上下文
  - 第5章（约束与风险）：版本评审冲突分析、系统约束与开发规范

**知识库使用要求**：

- 在文档中引用知识库内容时，使用格式：> 📚 来源：[知识类型] - 文档名称
- 如发现冲突，必须在第5章"约束与风险"中说明：
  - 冲突点描述
  - 影响范围
  - 建议的解决方案
- 必须使用知识库中的术语定义，保持术语一致性
- 必须检查与现有功能的功能冲突，明确新功能与现有功能的关系
- 如某类知识在仓库中不存在，必须在 MRD 中以“待确认”或“仓库未提供”标注，不能补写虚构内容

### Step 3: 按模板生成 MRD

依据模板的 5 个章节填充内容。**若存在评审总结文档**，各章节需按以下方式使用评审数据：

| 章节              | 核心要点                                                                                     | 评审总结使用指导                                                                |
| ----------------- | -------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------- |
| 1. 问题与背景     | 核心痛点、行业背景、不解决的后果                                                             | 使用「版本想法」作为问题定义；使用第 1 轮冲突分析作为背景                       |
| 2. 目标用户与场景 | 用户画像、2 个典型场景                                                                       | 从问答记录上下文推导用户场景与诉求                                              |
| 3. 需求范围       | P0/P1 功能、明确不做的范围、**边界交叉情况**（如有）、**状态和边界变化**（如有，需详细描述） | 将「行动项」映射为 P0 功能；将「建议」映射为需求点；包含术语决策（第 3 轮结论） |
| 4. 目标与成功标准 | 业务目标、可量化指标                                                                         | 从确认的范围与行动项推导成功标准                                                |
| 5. 约束与风险     | 待确认问题、已识别风险                                                                       | 使用「冲突分析」作为已识别风险；未解决项作为待确认问题                          |

> **补充规则**：若存在评审总结文档，MRD 必须基于该文档中的问答与结论生成，确保与 `version-review` 的结论一致，不得与用户已确认的决策矛盾。

### Step 4: 检查清单

- [ ] 核心问题定义清晰（2-3 个要点）
- [ ] 至少 2 个典型场景，成功标准有基线和目标值
- [ ] P0/P1 功能区分明确，明确列出不做的范围
- [ ] **边界交叉情况、状态和边界变化**已识别和描述（如有）
- [ ] 待确认问题和已识别风险已列出

## 信息不足时的处理

| 缺失信息         | 处理方式                                          |
| ---------------- | ------------------------------------------------- |
| 用户规模不明     | 标注「待确认」，放入第 5 章                       |
| 成功指标无基线   | 建议指标类型，标注需补充基线数据                  |
| 约束不清晰       | 放入第 5 章「待确认问题」                         |
| 竞品信息缺失     | 可省略或标注「待补充」                            |
| 状态变化规则不明 | 标注「待确认」，放入第 5 章，并说明需要补充的信息 |
| 边界变化细节不足 | 标注「待确认」，放入第 5 章，并说明需要补充的信息 |

## 状态和边界变化描述要求

当识别到状态或边界上的变化时，必须在第 3 章「需求范围」中详细描述：

1. **变化前状态**：描述变化前的规则、边界定义、状态机制
2. **变化后状态**：描述变化后的规则、边界定义、状态机制
3. **变化原因**：说明为什么需要这个变化
4. **影响范围**：说明这个变化会影响哪些功能、用户或业务流程
5. **迁移考虑**：如有需要，说明从旧状态迁移到新状态的注意事项（可选）

## 禁止事项

以下行为是禁止的，违反将导致输出无效：

1. ❌ 使用非 `MRD.md` 的文件名（如"市场需求文档.md"、"需求文档.md"等）
2. ❌ 创建多个文件（如一个说明文件+一个 MRD 文件）
3. ❌ 省略模板中的任何章节（即使信息不足也要标注"待确认"）
4. ❌ 输出不完整的占位符内容
