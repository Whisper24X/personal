# 生成测试用例

基于 PRD 和系统设计文档生成测试用例，确保功能覆盖率和质量标准。

## 引用文件

| 文件 | 何时读取 |
| --- | --- |
| [test-template.md](references/test-template.md) | Step 1 必须；生成前获取用例格式、优先级/类型/场景类型定义 |

## 流程概览

1. 读 template → 2. 读 PRD → 3. 生成用例（第一部分 + 附录）→ 4. 自检 → 5. 验收

## 执行前必读（强制）

生成前必须：1）读取 [test-template.md](references/test-template.md)；2）确认输出范围为「第一部分：测试用例」+ 可选附录（禁止测试计划、接口测试用例、测试数据）；3）按 Given-When-Then 与属性表格输出。

## 输出范围（强制）

**仅输出**：

- 「第一部分：测试用例」（含用例编写规范、各模块用例）
- 可选「附录：测试用例生成指南」

**禁止输出**（不得出现在 TEST.md 中）：

- 第一部分：测试计划
- 第三部分：接口测试用例
- 第四部分：测试数据

## 输出规范（强制）

> **重要**：以下规范必须严格遵守，不可违反。

| 项目           | 规范                                                                            |
| -------------- | ------------------------------------------------------------------------------- |
| **输出范围**   | 见上方输出范围 |
| **输出文件名** | `TEST.md`（必须使用此文件名，不可使用其他名称如"测试用例.md"）                  |
| **文件数量**   | 只生成 1 个文件，禁止创建额外的说明文件或拆分文件                               |
| **文档结构**   | 必须严格按照 [test-template.md](references/test-template.md) 仅包含测试用例部分 |
| **用例格式**   | 必须使用 Given-When-Then（BDD）格式，包含属性表格                               |

## 文档结构（必须严格遵循）

输出的 TEST.md 仅包含测试用例部分，标题格式必须一致：

```markdown
# 测试文档

---

## 第一部分：测试用例

（使用 Given-When-Then 格式，每个用例必须包含属性表格）
```

## 测试用例格式（必须严格遵循）

**每个测试用例必须使用以下格式，不得使用"测试步骤/预期结果"的传统格式：**

```markdown
#### TC-001：[用例标题] - [场景描述]

| 属性     | 值                             |
| -------- | ------------------------------ |
| 用例ID   | TC-[模块]-001                  |
| 类型     | Web端/App端/PC端/管理后台/通用 |
| 场景类型 | 正向场景/边界场景/异常场景/端到端场景 |
| 优先级   | P0                             |
| 前置条件 | [前置条件描述]                 |
| 关联需求 | PRD-[需求编号]                 |

**Given**：

- [系统状态/数据准备]
- [用户角色/权限]

**When**：

- [操作步骤]

**Then**：

- [预期结果验证]
```

## 核心原则

1. **测试覆盖完整性**：每个 PRD 功能点必须有对应的测试用例
2. **用例可执行性**：测试用例必须具体、可操作、可验证
3. **场景全面性**：包含正向场景、边界条件、异常场景
4. **格式统一性**：采用 Given-When-Then（BDD）格式，禁止使用"测试步骤/预期结果"传统格式
5. **类型必填**：每个测试用例必须填写「类型」，取值根据 PRD 覆盖端（Web、H5/App、PC、管理后台等）选择，多端适用可填「通用」
6. **场景类型必填**：每个测试用例必须填写「场景类型」，取值见 [test-template.md](references/test-template.md) 用例编写规范

## Then 断言规范

Then 部分**只写用户在页面上可直接观测到的结果**，确保每条断言都能被 UI 自动化工具验证。

### 正确写法

| 类型 | 示例 |
|------|------|
| 页面提示 | 出现保存成功提示 |
| 列表更新 | 设备列表中该设备的默认模式列显示为「自主学习」 |
| 元素状态 | 「提交」按钮变为不可点击状态 |
| 页面跳转 | 页面跳转到设备详情页 |
| 内容展示 | 筛选结果仅展示自主学习模式的设备 |

### 禁止写法

| 禁止类型 | 错误示例 | 原因 |
|---------|---------|------|
| 数据库断言 | `数据库中 defaultMode 已更新为 free_learning` | Playwright 无法查询数据库 |
| 硬编码时间 | `2秒内出现提示` | 环境差异导致 flaky test，改为 `出现xxx提示` |
| 接口断言 | `接口返回数据包含 defaultMode 字段` | UI 测试不直接验证接口 |
| 主观描述 | `便于快速找到老师专用设备` | 无法自动化验证 |
| 预设数据量 | `设备数量与未筛选时一致` | 依赖运行时数据，不可断言 |

### Given/Then 职责分离

- **Given** 负责描述数据前提（设备数量、初始状态、用户角色等）
- **Then** 只负责描述操作后页面上可见的变化

### When-Then 联动原则

Then 断言的验证对象必须存在于 When 最后一步所在的页面上。用例的 When → Then 应能直接映射为 Playwright 的 action → assertion。

| 原则 | 说明 |
| --- | --- |
| **页面一致** | 如果 When 步骤包含页面跳转，Then 只能断言最终页面的状态，不能断言跳转前页面 |
| **操作对应** | When 中每个关键操作在 Then 中应有对应的可观测结果 |
| **自动化映射** | 每条 Then 需能映射为一种 Playwright 断言：元素可见、文本包含、元素状态变化等 |

附录强制要求 4 的预期结果要求与本节一致，可一并参考。

### 自动化可行性标注

对于非 UI 可验证的用例（后台定时任务、cron job、数据库直接操作等），在属性表 `类型` 列标注为 `通用（不可UI自动化）`，帮助自动化脚本生成流程跳过这类用例。

**定义速查**：优先级、类型、场景类型取值见 [test-template.md](references/test-template.md) 用例编写规范。

## 生成流程

### Step 1: 读取模板（必须执行）

**必须首先读取** [test-template.md](references/test-template.md) 获取测试用例部分的结构和编写规范。未读模板不得开始生成。

### Step 2: 读取 PRD 文档

读取用户指定的 PRD 文件，提取：

- 功能模块清单与优先级
- 用户角色与权限矩阵
- 业务流程与状态转换
- 接口定义与数据模型
- 验收标准与 KPI 指标

### Step 3: 生成测试用例（仅第一部分 + 附录）

依据模板**仅生成**「第一部分：测试用例」及可选「附录：测试用例生成指南」。**禁止**在 TEST.md 中写入「第一部分：测试计划」「第三部分：接口测试用例」「第四部分：测试数据」。确保：

- 每个功能模块至少 3 个用例（正向、边界、异常）
- **必须使用 Given-When-Then 格式**
- **必须包含属性表格**（用例ID、类型、场景类型、优先级、前置条件、关联需求）

### Step 4: 输出前自检（必须执行）

在写入 TEST.md 之前，必须自检以下项，任一项不通过则不得输出：

- [ ] 文档中**不包含**「第一部分：测试计划」
- [ ] 文档中**不包含**「第三部分：接口测试用例」
- [ ] 文档中**不包含**「第四部分：测试数据」
- [ ] 仅包含「第一部分：测试用例」及可选「附录：测试用例生成指南」

### Step 5: 验收检查

- [ ] 文档仅包含测试用例部分（+ 附录），与模板一致
- [ ] 每个用例都有属性表格
- [ ] 每个用例都使用 Given-When-Then 格式
- [ ] 覆盖 PRD 所有 P0/P1 功能点
- [ ] 无模糊描述（如"某用户"、"正常显示"）
- [ ] 每个用例属性表包含场景类型（正向场景/边界场景/异常场景/端到端场景）

## 可选：自动化校验（长期防范）

若在 CI 或 pre-commit 中校验 TEST.md，可检查是否存在以下违规标题，存在则报错或告警：

- `## 第一部分：测试计划`
- `## 第三部分：接口测试用例`
- `## 第四部分：测试数据`

通过脚本或 grep 检测上述字符串即可拦截不符合规范的输出。

## 常见问题处理

| 情况               | 处理方式                       |
| ------------------ | ------------------------------ |
| PRD 验收标准不清晰 | 根据功能描述推导，标注需确认   |
| 接口文档不完整     | 基于 Design 推导，标注需补充   |
| 测试数据依赖复杂   | 明确数据准备步骤，列出依赖关系 |
| 性能指标未定义     | 填充合理默认值，标注需评审     |

## 禁止事项

以下行为是禁止的，违反将导致输出无效：

1. ❌ 使用非 `TEST.md` 的文件名（如"测试用例.md"、"test-cases.md"等）
2. ❌ 创建多个文件（如一个说明文件+一个用例文件）
3. ❌ 使用传统的"测试步骤/预期结果"格式替代 Given-When-Then
4. ❌ 输出测试计划、接口测试用例或测试数据（仅输出测试用例部分）
5. ❌ 用例缺少属性表格（用例ID、类型、场景类型、优先级、前置条件、关联需求）
6. ❌ 用例属性表缺少场景类型
7. ❌ 不读取模板文件就直接生成内容
8. ❌ 自定义文档结构，不遵循模板的测试用例部分结构
9. ❌ Then 中写数据库断言、接口断言、硬编码时间或主观描述（参见「Then 断言规范」）
