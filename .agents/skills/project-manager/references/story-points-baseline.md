# 故事点评估基准（基于技术模块拆分）

> 适用于研发任务复杂度与产出规模评估
> 评估逻辑基于技术模块拆分结构，而非主观时间判断

**文档版本**: v4.1
**核心模型**: 故事点 = 技术模块规模 × 模块复杂度 × 协作深度

---

# 一、核心原则

## 1.1 故事点衡量的本质

故事点衡量的是：

- 技术模块数量
- 模块内部复杂度
- 跨模块协作深度
- 状态与数据流复杂度

而不是：

- 个人编码速度
- 主观感觉
- 临时工作时长

---

# 二、技术模块拆分模型

一个技术任务通常可拆为以下模块类型：

| 模块类型     | 示例                        |
| ------------ | --------------------------- |
| 数据模型模块 | 数据表、索引、ORM           |
| 接口模块     | API设计、参数校验、返回结构 |
| 业务逻辑模块 | 状态流转、规则计算          |
| UI模块       | 页面、组件、交互            |
| 状态管理模块 | 状态同步、缓存、订阅        |
| 集成模块     | 第三方接入、消息系统        |
| 权限模块     | 角色校验、访问控制          |

---

# 三、模块复杂度分级

每个模块分为三个等级：

## 3.1 L1：简单模块

- 单一职责
- 无复杂状态
- 无跨模块依赖

示例：

- 单表CRUD
- 静态页面
- 单接口查询

复杂度权重：1

---

## 3.2 L2：中等模块

- 包含多个子逻辑
- 存在状态变化
- 涉及2–3个模块协作

示例：

- 带筛选的列表 + 后端接口
- 带校验的表单提交
- 状态字段流转

复杂度权重：2

---

## 3.3 L3：复杂模块

- 多状态机
- 多表关联
- 多端交互
- 跨系统依赖

示例：

- 订单状态流转
- 消息通知系统
- 工作流审批引擎

复杂度权重：3

---

# 四、故事点计算模型（斐波那契数列版本）

## 4.1 基础计算公式

总复杂度值 = Σ（模块复杂度权重） + 协作加权（最多 +3）

然后根据总复杂度值映射到故事点：

| 总复杂度值 | 故事点（斐波那契数列） |
| ---------- | ---------------------- |
| 1–4        | 0                      |
| 5–8        | 1                      |
| 9–12       | 2                      |
| 13–16      | 3                      |
| 17–20      | 5                      |
| ≥21        | 8（必须拆分）          |

---

# 五、协作加权规则

如果存在以下情况，增加 +1 复杂度值：

- 前后端协作
- 跨服务调用
- 涉及权限系统
- 涉及缓存一致性
- 涉及异步消息机制

最多加 3。

---

# 六、拆分原则（更新）

当出现：

- 模块复杂度总值 ≥ 15
- 存在 2个以上 L3模块
- 涉及3个以上系统域

必须拆分为多个子任务，且单个子任务故事点不应超过 13。

---

# 七、估点流程

## 步骤1：拆分模块

明确任务包含：

- 数据模块
- 接口模块
- 业务模块
- UI模块
- 集成模块

## 步骤2：评估每个模块等级

给每个模块赋 L1/L2/L3。

## 步骤3：计算总复杂度值

累加权重及协作加权。

## 步骤4：映射故事点

按照第4章映射表归属。

---

# 八、示例（对应斐波那契数列）

## 示例1：设计 task_task 表

- 数据模型模块（L1）= 1
- ORM模型（L1）= 1

总复杂度值 = 2

→ 故事点 0

---

## 示例2：用户列表 + 多条件筛选

- 后端接口（L2）= 2
- 数据查询逻辑（L2）= 2
- 前端页面（L2）= 2
- 前后端协作加权 +1

总复杂度值 = 7

→ 故事点 1

---

## 示例3：权限管理模块

- 数据模型（L2）= 2（用户-角色-权限多表）
- 后端接口（L2）= 2
- 权限校验逻辑（L2）= 2
- 前端页面（L2）= 2
- 前后端协作加权 +1

总复杂度值 = 9

→ 故事点 2

---

## 示例4：消息通知系统

- 数据模型（L2）= 2
- 消息状态逻辑（L3）= 3
- WebSocket模块（L3）= 3
- 通知推送服务（L2）= 2
- 前端页面（L2）= 2
- 协作加权 +2（前后端协作 +1，异步消息机制 +1）

总复杂度值 = 14

→ 故事点 3

---

## 示例5：订单流转系统

- 数据模型（L3）= 3（多表关联：订单表、订单项表、支付记录表）
- 订单状态机逻辑（L3）= 3
- 支付集成模块（L3）= 3
- 后端接口（L2）= 2
- 前端订单管理页面（L2）= 2
- 权限校验模块（L2）= 2
- 协作加权 +3（前后端协作 +1，跨服务调用 +1，涉及权限系统 +1）

总复杂度值 = 18

→ 故事点 5

---

# 九、与时间模型的关系

技术模块模型决定复杂度结构，
纯开发时间只是最终表现。

即：
模块结构 → 决定复杂度 → 映射故事点 → 反映开发时间

而不是：
感觉多久 → 给故事点

---

# 十、最终原则

- 故事点基于技术结构，而非个人速度
- 复杂度由模块数量与深度决定
- 8点是强制拆分阈值
- 3点任务是标准功能模块规模
