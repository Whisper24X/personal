# OpenSpec Validator

基于 PRD 和 design 文档审查 openspec 下所有规范文件，检查冲突、缺失和错误，并自动修正确保完整覆盖需求。

## 输出规范（强制）

> **重要**：审查报告必须写入文件，不是仅输出到终端。

**文档路径**：**必须**从 prompt 中获取 PRD、DESIGN、审查报告输出路径（如 `docs/{{gitBranch}}/` 结构）。

| 项目         | 规范                                                       |
| ------------ | ---------------------------------------------------------- |
| **报告文件** | 路径由 prompt 指定（如 `docs/{{gitBranch}}/openspecValidatorReport.md`） |
| **目录**     | 若报告所在目录不存在，需先创建                             |
| **内容**     | 完整的审查报告（审查范围、审查结果、验证清单、下一步行动） |
| **时机**     | 审查完成后立即写入，覆盖写入（非追加）                     |

## 工作流程

### 第 1 步：定位 openspec 变更目录

识别用户当前工作的变更目录：

```
workspace/{project-id}/{app-id}/versions/{version-id}/ainative-workspace/openspec/changes/{change-name}/
```

典型结构：

```
changes/{change-name}/
├── proposal.md          # 变更说明
├── design.md            # 技术设计
├── specs/               # 具体规范
│   ├── {spec-1}/spec.md
│   └── {spec-2}/spec.md
└── tasks.md             # 任务清单
```

### 第 2 步：收集基准文档

读取以下基准文档（按优先级）：

1. **PRD 文档**（最高优先级）
   - 查找路径：由 prompt 指定（如 `docs/{{gitBranch}}/PRD.md`）
   - 内容：业务需求、用户场景、功能规格

2. **DESIGN 文档**（技术基准）
   - 位置：由 prompt 指定（如 `docs/{{gitBranch}}/DESIGN.md`）
   - 内容：技术决策、架构设计、实现方案

### 第 3 步：遍历审查所有 openspec 下所有文件

对 `openspec/` 下的每个文件：

#### 3.1 冲突检查

查找与 PRD/design 冲突的内容：

**检查项**：

- [ ] 需求描述是否与 PRD 一致
- [ ] 技术方案是否与 design.md 决策一致
- [ ] API 定义是否与设计文档匹配
- [ ] 数据模型是否与设计文档匹配
- [ ] 业务规则是否与 PRD 一致

**冲突处理原则**：

1. PRD/design 为准，修改涉及到的文件
2. 保留文件中额外的实现细节（不冲突的部分）
3. 记录修改原因

#### 3.2 缺失检查

查找 PRD/design 中有但文件中缺失的内容：

**检查项**：

- [ ] PRD 中的所有需求是否都有对应的规范
- [ ] design 中的技术决策是否都被反映在规范中
- [ ] 关键业务场景是否完整覆盖
- [ ] 数据字段定义是否完整
- [ ] 接口定义是否完整
- [ ] 错误处理规范是否完整

**缺失处理**：

1. 在对应的文件中新增缺失内容
2. 如果不确定归属哪个文件，新增到最相关的 文件 中
3. 如果需要新的文件，创建新的规范文件，但要符合openspec的规范

#### 3.3 错误检查

查找规范中的逻辑错误或不一致：

**检查项**：

- [ ] 内部逻辑是否一致（前后文不矛盾）
- [ ] 跨 文件 引用是否正确
- [ ] 枚举值定义是否一致
- [ ] 字段类型定义是否准确
- [ ] 必填/可选字段标识是否明确

**错误处理**：

1. 修正明显的逻辑错误
2. 对于不确定的问题，基于 PRD/design 上下文和现有规范推断最优解，直接修正

### 第 4 步：生成审查报告

创建审查清单，跟踪进度：

```markdown
## OpenSpec 审查报告

### 审查范围

- 变更：{change-name}
- 基准文档：PRD, design.md, proposal.md
- 审查文件：{列出所有 spec 文件}

### 审查结果

#### ✅ 已修正的冲突

1. [spec-name] {具体冲突描述} → 已修正为：{修正内容}
2. ...

#### ✅ 已补充的缺失

1. [spec-name] {缺失内容描述} → 已新增：{新增内容}
2. ...

#### ✅ 已修正的错误

1. [spec-name] {错误描述} → 已修正为：{修正内容}
2. ...

#### ✅ 已自动选择最优解

1. [spec-name] {原问题描述} → 已采用：{最优解及理由}
2. ...

### 验证清单

- [ ] 所有 PRD 需求已覆盖
- [ ] 所有 design 决策已反映
- [ ] 跨 spec 引用一致
- [ ] 数据模型定义完整
- [ ] API 定义完整
- [ ] 错误场景已覆盖
```

### 第 5 步：验证完整性

最终验证确保规范完整覆盖需求：

#### 需求覆盖验证

逐条检查 PRD 中的需求：

- 每个需求场景都有对应的规范描述
- 每个用户故事都有对应的接口定义
- 每个业务规则都有对应的校验逻辑

#### 技术覆盖验证

逐条检查 design.md 中的决策：

- 每个技术决策都被规范化
- 每个数据模型变更都有定义
- 每个接口变更都有规范

#### 一致性验证

检查跨文件一致性：

- 同一概念在不同 spec 中定义一致
- 数据类型定义一致
- 枚举值定义一致
- 字段命名一致

### 第 6 步：同步更新 tasks.md

**目标**：当本次审查对 spec 做了结构性变更时，自动更新 `openspec/changes/{变更名}/tasks.md`，确保任务清单与规范一致。

**触发条件**（满足任一则执行更新）：

1. **新建了 spec 文件**：在 `specs/` 下新增了规范目录和 spec.md
2. **补充了缺失需求**：在现有 spec 中新增了完整的 Requirement 或 Scenario
3. **新增了 API/数据模型**：在 spec 中新增了接口定义或数据表定义

**不触发更新的情况**：

- 仅修正冲突（如修改描述措辞、统一枚举值）→ 不更新
- 仅修正错误（如修正逻辑矛盾、字段类型）→ 不更新
- 仅补充说明性内容（如注释）→ 不更新

**更新规则**：

1. **新建 spec 文件**：在 tasks.md 中新增对应模块的后端任务和前端任务
   - 后端：定义 proto、实现 CRUD/业务接口
   - 前端：实现列表页、详情页、相关组件
   - 任务格式与现有任务一致，使用 `- [ ]` 未完成标记，暂不填故事点（由 project-management Step 5 统一估算）

2. **补充缺失需求**：若新增的 Requirement 对应独立的实现单元（新接口、新页面、新组件），在 tasks.md 对应模块下新增任务项

3. **保持现有任务**：已存在的任务不修改、不删除，只追加新任务

4. **任务编号**：新任务沿用所在章节的编号规则（如 3.x、6.x），序号递增

**示例**：若在 `specs/resource/spec.md` 中补充了「公共课件点赞」需求，且 tasks.md 的 3.1 未包含点赞接口，则：

- 在 3.1 下新增子任务：`- [ ] 3.1.x 实现公共课件点赞接口`，或
- 若 3.1 描述可涵盖，则扩展 3.1 描述，不新增任务

**验收标准**：

- 若本次有结构性变更，tasks.md 已同步更新
- 新任务格式正确，与现有任务风格一致
- 不破坏已有任务的 `- [x]` 完成状态

## 修改原则

### 1. 以文档优先级为准

```
PRD > design.md > proposal.md > 现有 spec
```

当文档之间有冲突时，采用优先级高的文档。

### 2. 保留实现细节

如果 文件 中包含不冲突的实现细节（PRD/design 未提及），保留这些细节。

### 3. 明确标注修改

修改 文件 时，保持清晰的版本控制意识：

- 重大修改要确保逻辑完整
- 新增内容要符合现有结构
- 删除内容要确认无依赖

### 4. 补充而非替换

优先补充缺失内容，而非完全重写现有内容。

## 常见场景

### 场景 1：新增需求未在 spec 中体现

**问题**：PRD 中新增了「定金商品无需预约」需求，但 `order-management/spec.md` 未提及。

**处理**：

1. 在 `order-management/spec.md` 的 ADDED/MODIFIED Requirements 中新增对应场景
2. 确保场景描述完整（WHEN/AND/THEN 结构）
3. 补充相关的校验规则

### 场景 2：design 决策与 spec 实现不一致

**问题**：design.md 决定「定金商品跳过预约字段校验」，但 spec 中仍要求校验。

**处理**：

1. 修改 spec 中的校验逻辑描述
2. 添加条件判断：「当商品类型为 deposit 时，跳过 courseId、appointmentTime 等字段校验」
3. 保留其他商品类型的校验逻辑

### 场景 3：跨 spec 概念定义不一致

**问题**：`good-management/spec.md` 中商品类型枚举为 `single/multi/deposit`，但 `order-management/spec.md` 中只提及 `single/multi`。

**处理**：

1. 更新 `order-management/spec.md`，添加 `deposit` 类型的处理逻辑
2. 确保枚举值在所有 spec 中一致
3. 补充 `deposit` 类型的订单创建场景

### 场景 4：缺少关键业务规则

**问题**：design.md 提到「定金商品可能不支持优惠券」，但所有 spec 中都未提及。

**处理**：

1. 基于 PRD/design 上下文和现有规范推断最优解
2. 若 design 有倾向性描述，在 spec 中补充对应实现
3. 若完全无依据，采用业界常见做法（如默认支持优惠券）并注明推断依据

## 输出格式

完成审查后，**必须**将报告写入 prompt 指定的路径，报告内容结构如下：

```markdown
## OpenSpec 审查完成

### 审查摘要

- 修正冲突：{数量} 处
- 补充缺失：{数量} 处
- 修正错误：{数量} 处
- 自动选择最优解：{数量} 处
- tasks.md 同步：{已更新/无需更新}（若已更新，简要说明新增/修改了哪些任务）

### 审查范围

- 变更：{change-name}
- 基准文档：PRD, design.md, proposal.md
- 审查文件：{列出所有 spec 文件}

### 审查结果

#### ✅ 已修正的冲突

[按第 4 步模板填写]

#### ✅ 已补充的缺失

[按第 4 步模板填写]

#### ✅ 已修正的错误

[按第 4 步模板填写]

#### ✅ 已自动选择最优解

[按第 4 步模板填写]

### 验证清单

- [ ] 所有 PRD 需求已覆盖
- [ ] 所有 design 决策已反映
- [ ] 跨 spec 引用一致
- [ ] 数据模型定义完整
- [ ] API 定义完整
- [ ] 错误场景已覆盖

### 下一步行动

- [ ] 提交变更
```

**重要**：

1. **必须写入文件**：报告必须写入 prompt 指定的路径，不是仅输出到终端
2. **确保目录存在**：若报告所在目录不存在，先创建该目录
3. **覆盖写入**：每次审查覆盖该文件，不追加
4. **tasks.md 自动更新**：若第 6 步判定需要更新，在写入报告前完成 tasks.md 的修改

## 注意事项

1. **保持规范格式一致性**：遵循项目现有的 spec 格式和结构
2. **自动选择最优解**：若 PRD/design 未明确，基于上下文和规范推断最优方案并直接修正，在报告中注明推断依据
3. **优先级管理**：先处理冲突，再补充缺失，最后修正错误
4. **完整性优先**：确保所有 PRD 需求都有对应的规范，即使实现细节待定
5. **版本意识**：修改时考虑向后兼容性和影响范围
6. **报告必须落盘**：审查完成后必须将报告写入 prompt 指定的路径，不可仅输出到终端
7. **tasks.md 同步**：若本次审查有结构性变更（新建 spec、补充缺失需求），必须执行第 6 步更新 tasks.md
